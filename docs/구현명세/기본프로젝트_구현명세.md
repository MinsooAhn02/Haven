# Haven 기본 프로젝트 구현 명세

상태: 구현 전 제안 명세. 아래 경로, 필드, CLI와 시험은 개발할 계약이며 현재 생성되거나 동작하는 기능을 뜻하지 않는다. 팀 검토 후 이 문서를 기준으로 구현한다.

[기본 프로젝트 계획서](../../기본프로젝트_계획.md) | [심화 프로젝트 계획서](../../심화프로젝트_계획.md)

## 1. 적용 범위와 설계 결정

기본 결과물은 Django Templates 기반 개인 기록 서비스, 읽기 전용 SG 설정 점검 CLI, 제한된 요청 재현 CLI와 검증 결과다. 운영자 웹 대시보드, 공개 글, 회원 간 공유, 첨부 파일, 자동 수정과 자동 차단은 구현하지 않는다. 아래 값은 이번 명세의 제안값이다. 과제의 공식 확정값이나 이미 배포한 설정으로 표현하지 않는다.

| 구분 | 구현 계약 | 확정 시점 |
|---|---|---|
| 앱 구조 | Django 기본 User와 Templates, 단일 Post 모델, Django 세션과 CSRF 재사용 | 첫 migration 전 검토 |
| 기본 입력 | 제목 1~200자, 공백만 있는 제목/본문 거부, 목록 20건 | UI 구현 전 |
| 크기 | 글 작성/수정의 전체 직렬화 HTTP body 최대 8,192바이트 | APP-11/WAF-09로 배포 전 대조 |
| 세션 | 브라우저 종료 시 만료, 서버 측 최대 수명 1시간, 로그인 시 세션 교체 | APP/DEP 시험 전 |
| 로그인 방어 | 실패 관찰창, 계정/출발지별 제한, 회복 시간을 수치로 기록 | M0 결정 전 공개 금지 |
| 버전 | 지원되는 Django/Python/driver/PostgreSQL 조합과 패치 고정 | M0에서 호환성, 지원 종료, 검토 담당 기록 |
| AWS | 실제 계정, 리전, AZ, 자원 ID, 출구, 예산, 로그 보존 기간 | M0, 출구는 비공개 배포 전 |
| 외부 연결 | 소유한 서비스 호스트, DNS 운영자, 메일 제공자와 발신/수신 조건 | 외부 서비스 구성 전 |

M0 결정 기록은 `decision_id, 선택, 이유, 제약, 확인자, 날짜, 재검토 조건`으로 남긴다. 로그인 제한은 계정과 출발지의 두 축을 시험하고 영구 잠금은 사용하지 않는다. WAF IP 빈도 제한만으로 계정별 로그인 방어를 완료하지 않는다.

작업 상태는 미착수, 진행, 검증 대기, 완료, 보류로 나눈다. 완료에는 시험 ID, 실제 환경/버전, 결과와 산출물 위치가 필요하다. 문서 작성이나 설정 캡처만 있는 상태는 서비스 완료가 아니다.

## 2. 화면, 경로와 응답 계약

### 2.1 공통 규칙

인증은 Django 세션을 사용한다. 비로그인 사용자의 보호 화면 GET은 로그인으로 302 이동시킨다. 보호 화면 POST는 CSRF middleware 검사를 먼저 적용해 누락/오류 토큰이면 인증 상태와 무관하게 403을 반환하고, CSRF가 유효하지만 비로그인이면 302로 로그인 이동시킨다. 두 경우 모두 상태를 변경하지 않는다. 이동 목적지 `next`는 허용한 같은 호스트 경로만 사용한다. 로그인 후 본인 목록으로 이동한다. 존재하지 않거나 다른 사용자가 소유한 글은 같은 404 화면을 반환한다. 인증된 일반 회원의 관리자 접근은 403이다. 허용하지 않은 HTTP 메서드는 405다.

성공한 가입, 로그인, 생성, 수정, 삭제와 상태 변경 POST는 302로 이동하는 POST/Redirect/GET을 사용한다. 필드 검증 실패는 HTTP 400과 같은 폼으로 응답하며 비밀번호를 제외한 안전한 입력을 보존한다. CSRF 실패는 403, 글 body 초과는 413, 처리되지 않은 서버/DB 오류는 500과 일반 오류 화면으로 응답한다. 오류를 성공 화면으로 바꾸지 않는다.

목록/상세 응답은 인증 사용자별 데이터이며 공유 캐시에 저장하지 않는다. 모든 변경 요청에 CSRF를 적용한다. 로그아웃도 POST다. UI에서 링크를 숨기는 것과 서버 권한 검사는 별개로 구현한다.

### 2.2 화면별 동작

| 경로 | 메서드 | 기능과 권한 | 실패/완료 기준 |
|---|---|---|---|
| `/` | GET | 로그인 사용자는 `/posts/`, 그 외 로그인으로 이동 | 비밀값이나 기록 미노출 |
| `/accounts/signup/` | GET/POST | 아이디, 비밀번호, 확인을 받아 가상 계정 생성 | 중복/형식 오류 안내, 계정 데이터 과다 노출 금지 |
| `/accounts/login/` | GET/POST | 인증과 세션 생성 | 존재하지 않는 계정, 잘못된 비밀번호, 비활성 계정에 일반화한 오류 |
| `/accounts/logout/` | POST | 세션 종료 후 로그인으로 이동 | GET 405, CSRF 실패 시 세션 변경 없음 |
| `/posts/` | GET | 본인 글 목록, 최신순, 페이지당 20건 | 타인 글 없음, 빈 목록은 작성 안내 |
| `/posts/new/` | GET/POST | 제목/본문 폼, owner는 로그인 주체로 저장 | 입력한 owner/author_id를 권한 근거로 사용하지 않음 |
| `/posts/{id}/` | GET | 본인 글 상세 | ID와 owner를 함께 조회, 타인/없는 글 404 |
| `/posts/{id}/edit/` | GET/POST | 본인 글 수정 | 조회와 저장 모두 소유권 확인, 실패 시 원본 유지 |
| `/posts/{id}/delete/` | GET/POST | GET은 본인 글 삭제 확인, POST만 삭제 | GET으로 데이터 미변경, 취소는 상세로 이동 |
| `/admin/accounts/` | GET | 제한된 관리자의 계정 상태 목록 | 일반 회원 403, 본문과 비밀번호 해시 미표시 |
| `/admin/accounts/{id}/status/` | POST | 허용한 회원의 활성/비활성 변경 | 권한, 대상 종류, CSRF 검사 후 변경과 감사 저장 |
| `/admin/account-events/` | GET | 계정 상태 변경 이력 조회, 최신순 페이지당 20건 | 관리자 상태 변경 기록만 노출 |
| `/healthz` | GET | 최소 프로세스 상태 | 버전/주소/Secret 미노출, DB 기능의 완료 증거로 대체 금지 |

`/admin/`은 위 제한된 계정 관리로 연결한다. Django 기본 UserAdmin의 광범위한 추가/변경 화면을 운영 사용자에게 공개하지 않는다. 일반 운영 흐름에 복구용 최고권한 계정은 포함하지 않는다.

### 2.3 UI와 사용성

Django 기본 템플릿을 공통 레이아웃, 인증 폼, 목록, 상세, 작성/수정 폼, 삭제 확인, 계정 관리/이력으로 나눈다. 화면 제목과 현재 위치, 로그인 계정, 내 기록, 로그아웃을 일관되게 배치한다. 버튼에는 실제 동작 이름을 쓴다. 삭제와 비활성화는 대상과 영향을 확인할 수 있어야 한다.

각 필드는 명시적인 label과 오류 연결을 갖고 키보드로 접근 가능해야 한다. 오류 후 첫 오류와 안내를 찾을 수 있어야 한다. 색만으로 상태를 구분하지 않는다. 긴 제목/코드/본문은 화면을 밀어내지 않고 줄바꿈한다. 모바일 폭에서도 폼, 주요 버튼, 목록 이동을 사용할 수 있게 한다. 실제 회원의 개인정보 대신 가상 계정과 가상 기록만 사용한다.

폼은 평문 텍스트만 받으며 사용자 HTML을 실행하지 않는다. 출력 자동 이스케이프를 유지하고 `safe` 처리나 임의 HTML 렌더링을 사용하지 않는다. 본문 바이트 안내는 실제 폼 인코딩과 CSRF overhead를 포함한 서버 제한을 대신하지 않는다.

## 3. 데이터와 앱 권한

### 3.1 최소 모델

| 모델/기록 | 필드와 제약 | 처리 |
|---|---|---|
| Django User | 기본 username unique, password hash, is_active 및 프레임워크 권한 | 별도 인증 테이블과 자체 해시 없음 |
| Post | id, owner FK(User), title(max_length=200), body, created_at, updated_at | owner 수정 금지, `-created_at, -id` 순서, owner/시각 조회 인덱스 |
| Django LogEntry | 관리자, 대상 계정 ID, 상태 변경 시각과 결과 | 성공한 계정 상태 변경 이력에 재사용, change_message에는 변경 전후 상태만 |
| 구조화 앱 로그 | UTC 시각, request_id, actor_id, action, resource_id, result | 로그인 성공/실패, 거부, 글 변경과 관리자 작업을 기록 |

username은 프레임워크 validator, 비밀번호는 Django password validator와 해시를 사용한다. 비밀번호와 확인 값은 실패한 폼에도 재표시하지 않는다. 사용자 삭제는 기본 기능에 없고 비활성화만 제공한다. 계정/글 삭제와 로그 보존 기간은 운영 정책에서 따로 정한다. profiles, roles, attachments, security_findings 같은 후보 모델은 미리 생성하지 않는다.

글 POST body는 CSRF와 폼 인코딩을 포함해 8,192바이트 이하여야 한다. 문자 수와 직렬화 바이트 수를 구분한다. Nginx와 앱의 글 경로 제한을 맞추고 프레임워크 전역 제한을 잘못 적용해 로그인 등 다른 폼을 깨뜨리지 않는다. 잘못된 Content-Length 헤더만 신뢰하지 말고 서버가 실제 읽는 크기를 제한한다. 8,191/8,192/8,193바이트 시험은 UTF-8 한국어와 폼 인코딩을 포함해 만든다.

### 3.2 소유권과 계정 상태

글 조회/수정/삭제의 DB 조회 조건에 `id`와 `owner=request.user`를 함께 넣는다. 클라이언트의 author_id, hidden field, 쿼리 파라미터로 소유자를 정하지 않는다. 변경 요청은 입력 검증, 권한 확인, 저장 성공을 확인한 뒤 성공 처리한다. 비활성화된 계정은 기존 세션으로도 보호 기능을 사용하지 못해야 한다.

운영 관리자에게 전용 `manage_account_status`, `view_account_status_events` 권한을 부여하고 `is_superuser=False`로 둔다. is_staff만으로 작업을 허용하지 않는다. 대상은 일반 회원으로 제한하고 관리자 자신, 다른 관리자, 최고권한 계정의 상태는 이 화면에서 변경하지 못하게 한다. 비밀번호 재설정, 그룹/권한/staff/superuser 변경은 허용하지 않는다.

상태 변경과 성공 감사 레코드는 하나의 DB transaction으로 처리한다. 감사 저장이 실패하면 상태 변경도 취소한다. 실패/거부 시도는 일반 구조화 로그로 남긴다. 이력 화면은 계정 상태 변경 action에 해당하는 LogEntry만 필터링하고 본문이나 비밀값을 표시하지 않는다. 원본 감사 로그를 관리자 화면에서 수정/삭제하는 기능은 두지 않는다.

## 4. 네트워크, AWS 권한과 배포 계약

### 4.1 주소와 연결

아래 주소는 충돌 검토 후 채택할 후보이며 실제 배포 주소로 확정한 것이 아니다.

| 영역 | 후보 | 조건 |
|---|---|---|
| VPC | `10.20.0.0/16` | VPN/로컬/기존 VPC와 중복 확인 |
| 공개 A/B | `10.20.0.0/24`, `10.20.1.0/24` | 서로 다른 실제 AZ의 ALB용 서브넷 |
| 비공개 Web | `10.20.10.0/24` | 공인 IP 없는 EC2 1대 |
| 비공개 DB | `10.20.20.0/24` | 공인 IP 없는 EC2 1대 |

| 대상 | 허용 inbound | 확인할 거부 |
|---|---|---|
| ALB SG | 외부 TCP443, TCP80은 HTTPS redirect용일 때만 | 불필요한 listener와 관리 포트 |
| Web SG | ALB SG에서 TCP80 | 외부/다른 내부 출발지의 직접 접근 |
| DB SG | Web SG에서 TCP5432 | 외부/허가되지 않은 내부 출발지 |
| 관리 | SSM용 IAM/Agent/outbound 연결 | 일반 계정 관리 세션, 기본 22/3389 개방 금지 |

ALB에서 TLS를 종료한다. Web의 Nginx는 80, Gunicorn은 loopback으로 제한한다. Web/DB 1대씩이므로 전체 HA나 무중단을 약속하지 않는다. outbound는 설치, DNS, SSM, 메일, AWS API 목적지를 기준으로 정한다.

공개 서브넷의 인터넷 기본 경로는 IGW다. 비공개 일반 인터넷 경로는 M0에서 고른 NAT 방식으로 구성한다. Interface Endpoint는 DNS로 연결되는 ENI이며 route next hop으로 쓰지 않는다. S3 Gateway Endpoint를 채택할 때만 해당 route table과 서비스 prefix list를 연결한다. Endpoint를 모든 인터넷 접속의 대체로 쓰지 않는다.

출구 명세에는 `목적지, NAT 필요, endpoint 종류, DNS, endpoint SG, route, IAM/endpoint policy, 실제 연결 시험`을 적는다. SSM, OS/Python 패키지, 메일, 필요한 AWS API를 따로 확인한다. NAT 인스턴스를 고르면 forwarding, source/destination check, SG/route, 재시작 복구까지 검증한다. NACL 변경은 선택 실습으로 두고 왕복 방향과 임시 포트, 복원 규칙을 기록한다.

### 4.2 권한 묶음

| 주체 | 허용 | 제한 |
|---|---|---|
| IAM 실습 | 사용자/그룹/정책 및 MFA 실습 | 일상 운영 전체 권한으로 자동 승격하지 않음 |
| Web 운영 | 지정 Web 관리/배포/SSM | DB 제어와 태그 변경을 통한 우회 거부 |
| DB 운영 | 지정 DB 관리/SSM, 승인된 백업/복원 | 무관 자원/버킷 변경 거부 |
| 보안 점검 Role | 필요한 Describe/List/Get | AWS 설정 쓰기, 자동 차단, Secret 원문 조회 거부 |
| 조회/감사 | 지정 설정과 가림 로그 | 데이터 본문과 비밀값 조회 제한 |
| Web EC2 Role | SSM, 필요한 메일/로그/선택 Secret | 정적 AWS 키와 무관 Secret 접근 금지 |
| DB EC2 Role | SSM, 선택 백업 prefix 쓰기/로그 | 복원 읽기/삭제/정책 변경은 별도 승인 |

사람은 이용 가능한 federation/Identity Center 임시 세션을 우선 검토한다. 교육 환경 제약 시 개인 IAM+MFA 예외와 키 회수 절차를 기록한다. EC2는 인스턴스 프로파일, 로컬 CLI는 승인된 profile/세션을 사용한다. 조회 작업에 필요한 `Resource:*`를 문자만 보고 과권한으로 판정하지 않고 Action/Resource/Condition과 실제 작업을 대조한다.

CloudTrail API 감사, SSM 세션 기록, 호스트 로그와 앱 로그의 범위를 구분한다. 모든 API 또는 세션 본문이 자동 기록된다고 가정하지 않는다. 태그 기반 권한은 태그 변경 권한도 제한한다. 백업 쓰기 권한은 같은 key 덮어쓰기 가능성까지 시험한다.

### 4.3 DB와 운영 배포

PostgreSQL은 앱 DB, migration 주체, runtime 주체를 분리한다. runtime은 필요한 CRUD 권한만 가지며 superuser/DDL 권한은 갖지 않는다. listener, pg_hba, 실제 Web 주소, SG와 인증을 일치시킨다. 가상 데이터 migration 후 재시작 영속성과 별도 DB 복원을 확인한다. 백업 파일 생성만으로 복원 성공을 기록하지 않는다.

Web은 비root 계정/venv, 고정 의존성, Nginx/Gunicorn/systemd로 운영한다. DEBUG, ALLOWED_HOSTS, CSRF origin, cookie Secure/HttpOnly/SameSite와 프록시 신뢰를 명시한다. ALB에서 온 원래 scheme을 제한된 신뢰 경계 안에서 반영한다. 신뢰하지 않는 요청 헤더만으로 HTTPS나 클라이언트 주소를 확정하지 않는다.

배포 전 `check --deploy` 경고를 조치하거나 근거/만료가 있는 예외로 기록한다. 서비스/서버 재시작, ALB health와 실제 로그인/CRUD를 각각 시험한다. rollback은 앱 버전, 설정과 DB migration 호환성을 확인하고 수행한다. 파괴적 migration과 실제 자원 종료는 별도 영향/복구 확인 없이 실행하지 않는다.

도메인과 ACM 대상 호스트를 맞추고 실제 HTTPS/인증서/redirect를 확인한다. 메일은 가상 수신자 대상 최소 알림 한 가지로 시작한다. SES 선택 시 sandbox, 리전, 발신/수신 인증과 필요한 DNS 설정을 확인한다. 발송 API 성공과 실제 도착, 실패 표시를 각각 검증한다.

## 5. 자체 SG 설정 점검 CLI

### 5.1 명령과 입력

예정 파일은 `scripts/network_audit.py`다. Python 표준 인자 파서와 AWS SDK를 사용하며 쓰기 API는 호출하지 않는다. 아래는 구현할 인터페이스이며 현재 실행 가능한 명령이 아니다.

```text
python scripts/network_audit.py live --region <region> --vpc-id <vpc> --profile <profile> --baseline <json> --output-dir <new-dir>
python scripts/network_audit.py live --region <region> --sg-id <sg> [--sg-id <sg> ...] --profile <profile> --baseline <json> --output-dir <new-dir>
python scripts/network_audit.py fixture --fixture <json> --baseline <json> --output-dir <new-dir>
```

`live`는 `--region`, `--profile`, `--baseline`, `--output-dir`가 필수이며 `--vpc-id`와 반복 `--sg-id` 중 하나만 받는다. 대상 계정 ID를 STS 읽기 호출로 확인하고 리전/범위와 함께 시작 시 출력한다. fixture 모드는 AWS 자격과 네트워크가 없어도 실행하며 수집 결과/오류를 fixture에서 주입한다. output-dir는 비어 있는 새 디렉터리만 허용하고 기존 결과를 덮어쓰지 않는다.

baseline은 `schema_version=1`, `assets`, `allowed_rules`를 가진다. assets는 `asset_id, asset_role, expected_sg_ids`로 실제 자산 역할을 매핑한다. allowed_rules는 `asset_role, direction, protocol, from_port, to_port, source_type, source_value`를 가진 명시 허용표다. direction은 ingress/egress이며 source_type/source_value는 ingress의 출발지 또는 egress의 목적지를 뜻한다. 자격 증명은 baseline/fixture에 넣지 않는다. baseline은 모든 IAM/NACL/route 해석을 제공하는 정책 언어로 확장하지 않는다.

자산별 inbound와 outbound 모두 baseline의 direction별 허용표와 대조한다. 수집한 ingress/egress 중 한 방향만 검사하고 전체 PASS로 표시하지 않는다. 선택 VPC의 SG/ENI 연결 정보를 페이지 끝까지 수집한다. SG ID 선택 시 같은 자산에 연결된 추가 SG도 읽어 유효 허용 합집합을 검사한다. 필요한 연결 정보가 없으면 SG 규칙만의 결과와 자산 접근 결과를 나누고 후자는 UNKNOWN으로 둔다. 이름/태그만으로 자산 역할을 임의 추정하지 않는다.

### 5.2 판정과 출력

| 규칙 | 검사 |
|---|---|
| SG-01 | `0.0.0.0/0` 또는 `::/0`에 관리/DB 포트가 열려 있는지, 포트 범위 포함 |
| SG-02 | 전체 프로토콜 허용, 포트가 없는 규칙의 처리 |
| SG-03 | Web TCP80의 허용 출발지가 ALB SG인지 |
| SG-04 | DB TCP5432의 허용 출발지가 Web SG인지 |
| SG-05 | 자산별 허용 protocol/port/source와 실제 규칙 차이 |
| SG-06 | 역할 미확정, 연결되지 않은 SG, 근거 부족의 구분 |

IPv4/IPv6, TCP/UDP/ICMP, SG 참조, CIDR, 범위 포트와 누락 필드를 구분한다. UDP80을 정상 TCP 웹 허용으로 처리하지 않는다. 정상 SG에 공개 SG를 추가한 자산은 합집합에서 위반을 찾아야 한다. 보안 그룹의 허용 설정만으로 실제 인터넷 도달을 확정하지 않고 공인 IP/route/NACL/listener 결과를 별도 시험한다.

결과는 `results.json`, `findings.csv` 두 파일이다. JSON envelope는 `schema_version, run_id, started_at_utc, finished_at_utc, tool_version, mode, account_id, region, scope, collection_status, counts, findings, errors`를 가진다. fixture의 account_id는 가상 식별자로 표시한다.

finding은 `check_id, region, vpc_id, sg_id, asset_id, asset_role, direction, protocol, from_port, to_port, source_type, source_value, expected, actual, verdict, reason, evidence`를 포함한다. direction은 ingress 또는 egress이며 egress의 source_type/source_value는 규칙의 상대 목적지를 뜻한다. CSV에도 direction을 포함한 같은 finding 필드를 한 행씩 기록한다. reason과 evidence에 Secret이나 과도한 raw 응답을 넣지 않는다.

- PASS: 필요한 근거를 수집했고 명시 기준을 통과했다.
- FAIL: 수집한 근거가 명시 기준을 위반했다.
- UNKNOWN: 역할, 기준, 연결 정보 등 판정 근거가 부족하다.
- ERROR: API/인증/네트워크/파일 처리 등 수집 또는 실행에 실패했다.

종료 코드는 `0=전체 수집 완료 및 PASS`, `1=FAIL 존재`, `2=입력/수집/실행 ERROR`, `3=UNKNOWN 존재`로 고정한다. 여러 상태가 섞이면 ERROR(2), UNKNOWN(3), FAIL(1), PASS(0) 순서로 결정하되 모든 개별 결과를 보존한다. 결과 없음은 PASS가 아니라 UNKNOWN이다. 출력 저장 실패 시 비정상 종료하고 성공을 출력하지 않는다.

## 6. 제한된 요청 재현 CLI

### 6.1 명령과 대상 제한

예정 파일은 `scripts/request_verify.py`이며 회귀 요청을 순차 실행한다. 임의 공격 생성기, 부하 시험기, 자동 정책 수정기로 만들지 않는다.

```text
python scripts/request_verify.py run --target <https-origin> --allowlist <json> --cases <json> --output-dir <new-dir> [--timeout 10] [--max-requests 100] [--rate 1] [--max-duration 300]
python scripts/request_verify.py correlate --run-json <results.json> --waf-log <local-jsonl> --app-log <local-jsonl> --output-dir <new-dir>
```

기본 제한은 요청 timeout 10초, 최대 100회, 초당 1회, 전체 300초다. 명령행의 상한은 각각 30초, 1,000회, 초당 5회, 900초다. 0/음수/상한 초과를 거부한다. M0에서 더 낮은 실행 한도를 정할 수 있다. 빈도 규칙 시험도 이 한도 안에서만 수행하고 충분하지 않으면 무리하게 증량하지 않고 별도 실행 조건 검토로 남긴다.

allowlist는 승인된 정확한 scheme+host+port 목록이다. 기본 공개 경로는 HTTPS만 허용하고 TLS 검증을 해제하는 옵션을 제공하지 않는다. 케이스는 `/`로 시작하는 같은 대상의 상대 path만 받으며 절대 URL, `//host`, 다른 origin으로 대상을 바꾸는 입력을 거부한다. redirect는 추적하지 않고 대상과 상태만 기록한다. ALB 우회 점검은 네트워크 시험으로 수행하며 일반 CLI 허용목록을 무단 확장하지 않는다.

실행 전에 대상, 케이스 수, 한도를 표시한다. 로그인/CSRF 준비 요청도 총 요청 수와 전체 시간에 포함한다. Ctrl+C, 한도 도달, 대상 검증 실패 또는 출력 저장 실패 시 중단한다. 완료한 요청은 부분 결과로 남기고 중단 사유/미실행 수를 기록한다. 다른 호스트를 따라가거나 실패한 변경 POST를 자동 재시도하지 않는다.

### 6.2 케이스, 인증과 결과

케이스 JSON은 `schema_version=1, suite_id, suite_kind, cases`를 가진다. suite_kind는 `regression` 또는 `confirmation`이다. 각 케이스는 `case_id, category, method, path, auth_role, input_reference, expected_app, expected_waf, max_requests, note`를 포함한다. method는 GET/POST, auth_role은 anonymous/member_a/member_b/operator다. input_reference는 승인한 로컬 가상 payload를 가리키며 파일 경로를 허용한 입력 디렉터리 안으로 제한한다. 파일 업로드는 없다.

로그인 계정과 비밀번호는 필요한 role별로 대화형 입력하고 비밀번호는 화면에 표시하지 않는다. 세션 쿠키와 CSRF token은 각 role의 메모리 세션에만 유지하며 파일/명령행 인자/공개 로그에 저장하지 않는다. 헤드리스 비대화형 인증은 기본 버전에 추가하지 않는다. 로그인/CSRF 준비 실패는 해당 인증 케이스의 실행 오류로 남기고 WAF 정상 통과로 계산하지 않는다.

run 출력은 JSON 상세와 CSV 요약이다. 필수 결과는 `run_id, request_id, case_id, timestamp_utc, elapsed_ms, auth_role, category, method, path, expected_app, expected_waf, http_status, redirect_target, response_summary, app_observed, waf_action, rule_id, waf_verdict, app_validity, transport_status, correlation_status, evidence_path`다. 응답 본문 원문은 저장하지 않고 상태와 필요한 가림 요약만 기록한다.

request_id는 도구가 생성한 상관 ID를 전용 헤더에 넣어 WAF/앱 로그와 연결한다. 앱은 헤더를 인증 근거로 사용하지 않고 길이/문자 검증 후 자체 서버 request_id와 함께 상관 정보만 남긴다. 클라이언트 IP와 인증된 사용자 정보는 신뢰 경계에서 따로 결정한다.

run 직후 WAF 로그가 없으면 waf_verdict는 UNKNOWN, correlation_status는 PENDING_LOG다. correlate는 같은 run_id/request_id와 시각, 대상 조건을 대조해 WAF와 앱 근거를 연결하고 원본 run 결과를 덮어쓰지 않는다. correlation_status는 PENDING_LOG(아직 로그 대조 전), MATCHED(필요 근거의 대응 확정), UNRESOLVED(대조 후 누락/중복/충돌)로 고정한다. 동일 ID 중복/로그 누락/충돌은 waf_verdict=UNKNOWN과 correlation_status=UNRESOLVED로 기록한다. 입력 로그는 접근 제한된 로컬 자료이며 결과는 가림 필드만 포함한다.

최종 판정은 응답 코드만으로 정하지 않는다. waf_verdict는 BLOCK/ALLOW/UNKNOWN, waf_action은 실제 로그의 COUNT/ALLOW/BLOCK 등을 보존하고 app_validity는 expected 결과와 실제 앱 처리의 일치/불일치/미확정으로 둔다. 앱 거부와 WAF 차단, 네트워크 오류를 별도 필드로 유지한다.

run/correlate 종료 코드는 `0=실행 완료 및 모든 기대 결과 확인`, `1=확인된 기대 불일치`, `2=입력/인증 준비/실행/출력 ERROR 또는 중단`, `3=로그 대기/근거 부족 UNKNOWN`이다. 우선순위는 2, 3, 1, 0이며 부분 결과와 개별 불일치를 함께 보존한다. run이 완료됐더라도 로그 대기 상태라면 종료 3을 정상적인 중간 상태로 표시한다.

## 7. WAF 관찰, 변경과 지표

ALB Regional web ACL을 구성하고 CloudWatch Logs 도착과 필드 가림을 확인한다. 규칙 후보의 이름/버전/priority/예외/WCU/비용 조건을 기록한 뒤 Count로 관찰한다. 정상 업무 입력이 매칭되면 경로/필드에 필요한 범위로 조정하며 전체 규칙을 근거 없이 끄지 않는다.

기본 글 요청은 전체 body 8,192바이트 이하를 앱/프록시에서 강제하고 WAF body/oversize 설정과 대조한다. 크기 한계는 연결 서비스와 실제 규칙 버전에 따라 확인하며 다른 연결 서비스에도 같은 값이 적용된다고 일반화하지 않는다. 글 크기 규칙을 끄는 것으로 정상 입력 문제를 덮지 않는다.

Count 관찰, 요청/규칙 로그 대조, 필요한 변경, 선택 Block, 같은 회귀 집합 재시험, 조정에 쓰지 않은 confirmation 집합 순으로 진행한다. 앱 commit, 요청, 인증, 속도, 환경을 유지하고 변경한 정책과 규칙 버전을 기록한다. 오탐/장애가 있으면 직전 정책으로 되돌리고 정상 기능부터 확인한다.

| 지표 | 분모와 분자 | 같이 기록할 내용 |
|---|---|---|
| 정상 요청 오탐 | WAF 판정 가능한 정상 요청 중 BLOCK / 판정 가능한 정상 요청 | 전체 수, 판정 가능 수, UNKNOWN/ERROR 수와 이유 |
| 시험 요청 차단 | WAF 판정 가능한 시험 요청 중 BLOCK / 판정 가능한 시험 요청 | 회귀/확인용 집합 분리, 앱 유효성 별도 |
| 설정 점검 품질 | fixture 기대/실제 결과와 실제 설정 수동 대조 | 수집 범위, 누락, 알려진 한계 |
| 전후 비교 | 같은 조건의 각 지표와 정책 diff | 분모/조건 차이, 제외 기준, 잔여 문제 |

분모 0은 N/A다. UNKNOWN/ERROR를 통과나 차단 성공에 섞지 않는다. 앱 인증 실패가 있어도 WAF 액션이 확정되면 WAF 분모에서 자동 제외하지 않는다. 결과는 이 시험 집합의 관찰이며 전체 공격 방어율이나 스캐너 finding 수와 같은 의미가 아니다.

## 8. 시험 목록과 합격 조건

모든 시험은 가상 사용자 A/B, 제한된 운영 관리자, 비로그인 상태를 사용한다. 앱 단위 시험과 실제 ALB 경로 시험을 구분한다. APP-05는 `Client(enforce_csrf_checks=True)`로 성공 대조군도 함께 실행한다. WAF가 먼저 차단한 결과는 앱 소유권/CSRF 로직 성공의 증거가 아니다.

ASVS는 인증/세션/객체 권한/입력/로그 중 적용 항목만 골라 `정확한 버전/ID, 요구, 적용/제외 이유, 시험 ID, 증거, 한계`를 기록한다. 공식 원문 확인 전 requirement ID를 만들지 않는다. 선택 매핑과 일부 시험 통과를 전체 준수/인증으로 표현하지 않는다.

## 9. 결과물, 재현과 운영 기록

예정 증거 묶음은 `evidence/<run-id>/` 아래 manifest, 가림 설정, 시험 결과, 가림 로그, 전후 비교다. manifest에는 commit, 환경, 도구/규칙 버전, 대상 범위, 실행 시각, 알려진 누락을 기록한다. raw 로그는 접근 제한 위치에 보관하고 공개 결과와 분리한다. 비밀번호, 세션, token, Secret, 실제 개인정보와 전체 공격 본문은 공개 자료에 넣지 않는다.

| 요구 | 시험 연결 | 결과물 |
|---|---|---|
| B1 | APP-01~11, UI-01~03, DB-01~05, DEP-01~05 | 서비스 화면/동작, 구축 결과, 배포/복원 |
| B2 | IAM-01~08 | 주체별 정책, MFA, 허용/거부 |
| B3 | NET-01~06 | 구성도, route/SG, 실제 연결 |
| B4 | WAF-01~09 | ACL/규칙, 요청/로그, rollback |
| C1 | EXT-01~04 | 도메인/인증서/메일 |
| C2 | IAM-02~08와 점검 재실행 | 과권한 근거/정책 diff/재시험 |
| C3 | AUD-01~11 | 소스/fixture/JSON/CSV/수동 대조 |
| C4 | WAF-02~09, APP-02/06/11, REP-01~04 | 동일 조건 전후 비교와 오탐/차단/UNKNOWN |

B/C는 내부 추적 번호이며 공식 과제 인정 여부를 확인한 표가 아니다. AWS WAF의 장비 인정 범위와 별도 IPS 요구는 실제 과제 확인 후 범위를 조정한다.

시연은 A의 UI 사용, B의 타인 접근 거부, AWS/DB 접근 통제, CLI 정상/위반/수집 실패, WAF Count/Block 로그 대조, 개선 전후와 복원 순으로 한다. 가림 녹화는 보조 자료이며 이전 결과를 현재 실행 성공으로 표현하지 않는다.

장애 기록은 `현상, 재현 조건, 관찰 로그, 원인 후보, 확인 방법, 실제 원인, 변경, 재시험, 남은 한계`를 남긴다. 서비스/WAF/배포 rollback은 변경 전 설정과 호환성을 확인한다. 예산 알림은 자동 지출 차단이 아니며 EC2 중지만으로 ALB/NAT/Endpoint/EBS 등 과금이 끝나지 않는다. 보존 범위 승인 후 잔여 자원을 점검하고 실제 삭제는 별도 확인한다.

기본 완료 후 암호화, 인증서와 키 교체/복원은 [심화 계획서](../../심화프로젝트_계획.md)와 해당 구현 명세에서 다룬다. 기본에서 정한 평문 저장과 내부 HTTP의 한계를 심화 완료 전 보호된 것으로 표현하지 않는다.
