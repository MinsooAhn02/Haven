# Haven 심화 구현 명세

**상태:** 팀 검토용 구현 계약. 아래 경로, 형식과 시험은 제안이며 구현 완료를 뜻하지 않는다.

[심화 계획서](../../심화프로젝트_계획.md)는 목적과 추진 순서를 설명한다. 이 명세는 개발 시 고정할 데이터 형식, 처리와 실패 계약, 키 교체, 인증서, 시험 기준을 정리한다. [기본 계획서](../../기본프로젝트_계획.md)와 [기본 구현 명세](기본프로젝트_구현명세.md)의 인증, 소유권, 크기 제한, 로그, 배포와 백업 계약을 그대로 적용한다.

## 1. 구현 경계와 착수 조건

- 기존 Django 앱과 PostgreSQL을 확장하며 별도 인증 서버나 회원 DB를 만들지 않는다.
- 실제 개인정보 대신 가상 보호 필드 하나를 사용한다. 기본 제목과 본문은 기존 기능을 유지한다.
- 보호 필드는 기존 작성과 수정 폼, 상세 화면에 연결한다. 목록과 계정 관리에는 원문을 추가하지 않는다.
- 기본 로그인과 소유권, CSRF, 안전한 출력, DB 복원 시험이 통과한 환경에서 시작한다.
- 심화 계획의 A-D1~A-D7 결정이 관련 구현 전에 채워져야 한다. 예시 설정을 실제 자원에 그대로 적용하지 않는다.

가상 필드 이름 후보는 `protected_note`다. 모델 이름과 저장 방식은 실제 기본 앱 구조를 따른다. 불필요한 별도 도메인이나 테이블을 만들지 않고 기존 기록과 일대일로 연결한 최소 필드 묶음을 우선 사용한다.

## 2. 암호화 데이터 계약

이 절의 저장 묶음과 nonce 및 AAD 계약은 앱에서 AEAD를 수행하는 경로에 적용한다. 키 공급은 로컬 제한 파일, Secrets Manager 또는 KMS envelope encryption 중 선택한 방식을 따른다. KMS 직접 암호화 호출은 서비스 관리 암호문을 사용하므로 이 계약과 혼합하지 않는다. 직접 호출을 채택하려면 암호문과 서비스 메타데이터, 키 참조와 암호화 컨텍스트, 재암호화와 복원 계약으로 이 절과 관련 시험을 변경한 뒤 구현한다.

### 2.1 저장 묶음

| 필드 | 의미와 제약 |
|---|---|
| `format_version` | 저장 형식과 AAD 직렬화 계약의 버전. 지원하지 않는 값은 실패 |
| `key_version` | 복호화에 사용할 승인된 키 버전 식별자. 키 원문과 혼동하지 않음 |
| `nonce` | 선택 AEAD가 요구하는 길이와 방식으로 생성. 같은 키에서 재사용하지 않음 |
| `ciphertext` | AEAD 인증 태그를 포함하거나 명시적으로 결합한 암호문. 방식은 A-D2에서 고정 |
| 연결 메타데이터 | 기록 식별자, 소유자 식별자, 필드명. AAD 구성에 필요한 값을 안정적으로 확보 |

DB의 bytes 저장을 우선 검토하고 텍스트 직렬화가 필요하면 인코딩을 한 가지로 고정한다. base64나 UTF-8 변환만 수행한 값은 암호문으로 인정하지 않는다. 선택 알고리즘이 nonce 또는 tag를 다른 형식으로 다루면 형식 명세와 시험을 함께 갱신한다.

보호 필드가 없는 상태는 `null`에 해당하는 일관된 상태로 표현하고, 입력값이 있는 암호화 레코드와 구분한다. 형식 필드 일부만 있는 행이나 빈 암호문으로 암호화 성공을 표현하지 않는다. 입력이 비어 있지 않은데 암호화가 실패하면 기존 데이터는 유지하고 저장을 실패시킨다. 원문을 대신 저장하는 fallback은 없다.

### 2.2 알고리즘과 nonce

검증된 라이브러리의 AES-GCM 등 AEAD를 후보로 두며 정확한 알고리즘, 키 길이, nonce 길이, 태그 형식, 라이브러리 버전을 A-D2에서 결정한다. 자체 암호 알고리즘이나 자체 인증 태그를 만들지 않는다. nonce는 라이브러리 권장 방식과 보안 난수원으로 생성하고 고정값, 시각만의 값, 재시도 시 무조건 재사용하는 방식을 금지한다. 동일 키 사용량과 충돌 위험을 검토해 교체 기준을 정한다.

암호화 전 입력 인코딩과 한도를 검증한다. 전체 작성과 수정 요청의 기본 크기 제한은 보호 필드 추가 후에도 적용하며, 문자 수만 보고 통과시키지 않는다. 기존 APP-11과 WAF-09의 실제 전송 바이트 시험을 다시 수행한다.

### 2.3 AAD와 기록 바인딩

AAD는 앱 이름, 형식 버전, 기록 ID, 소유자 ID, 필드명을 결정적 순서와 인코딩으로 직렬화한 bytes로 정의한다. 저장할 때와 읽을 때 정확히 같은 계약을 사용한다. 단순 구분자 결합의 모호성을 피하도록 형식을 고정하고 단위 시험을 남긴다.

기록 ID가 DB 저장 후 생성된다면 같은 트랜잭션 안에서 식별자를 먼저 확보한 뒤 암호화 필드를 저장한다. 실패 시 반쪽 레코드를 남기지 않는다. 실제 모델이 UUID를 이미 사용하면 그 구조를 재사용한다. AAD에 넣은 식별자를 바꿀 때는 인증 실패 또는 명시적인 재암호화가 필요하며 단순 복사로 다른 기록에 옮기지 않는다.

## 3. 저장과 조회 계약

### 3.1 저장

1. 세션, 계정 상태, CSRF와 기록 소유권을 먼저 검사한다.
2. 입력 한도와 전체 요청 크기를 검사한다. 제출한 소유자 식별자는 신뢰하지 않는다.
3. 현재 활성 쓰기 키 버전을 한 번 선택하고 그 버전을 해당 저장 전체에 사용한다.
4. 새 nonce와 해당 기록 AAD로 암호화한다.
5. 기본 변경과 암호화 필드 묶음을 하나의 트랜잭션으로 저장한다.
6. 성공 응답 전에 DB 결과를 확인한다. 오류 시 성공 화면으로 이동하지 않는다.

폼 오류 때 가상 입력은 허용한 화면 범위에서만 보존하고 로그와 오류 추적 메타데이터에 복사하지 않는다. 암호화 단계가 실패하면 예외 종류와 요청 ID 등 필요한 최소 정보만 내부 로그에 남긴다.

### 3.2 조회

기록 ID와 세션 소유자 조건으로 조회한 후 해당 행의 키 버전을 해석한다. 소유권이 없는 요청에 키 접근과 복호화를 시도하지 않는다. 지원하는 형식과 키 버전일 때만 인증된 복호화를 수행하고 성공한 평문만 템플릿의 안전한 출력으로 전달한다.

잘못된 키, tag 또는 AAD 불일치, 형식 손상, 키 서비스 접근 거부는 일반 오류 화면과 요청 ID로 처리한다. 부분 평문, 원시 암호문, 내부 stack trace는 응답하지 않는다. 실패를 정상적인 빈 보호 필드로 처리하지 않는다. 로그는 실패 범주를 구분하되 키와 원문을 포함하지 않는다.

## 4. 키 공급과 권한

| 선택지 | 구현 전에 정할 계약 |
|---|---|
| 제한된 로컬 파일 | 생성과 배포 주체, 파일 소유자와 권한, 런타임 접근, Git 및 백업 제외, 별도 복구 보존 |
| Secrets Manager | Secret 식별자 범위, 읽기 Role, 버전과 활성 상태 매핑, 접근 실패와 복구, 비용 |
| KMS 직접 호출 | 키 작업 권한, 데이터 크기 제약, 호출 실패와 비용, 버전 식별과 복구 |
| KMS envelope encryption | 데이터 키 생성과 포장, 포장된 키 저장, key context, 복호화 권한과 키 수명 |

동시에 모두 구현하지 않는다. 선택 결과에 따라 키 공급 코드 한 경로와 필요한 설정만 만든다. 구체 정책은 실제 서비스와 리소스 범위로 제한한다. 사람이 사용하는 AWS 운영 권한, EC2 실행 Role, DB 계정, 앱 회원 권한을 분리한다.

키 서비스가 선택됐다면 Web 실행 Role에 필요한 읽기 또는 암호 작업만 허용한다. DB가 암호문을 보관한다는 이유로 DB EC2 Role에 복호화 권한을 주지 않는다. 점검 CLI와 감사 주체에도 보호 필드 키 접근을 기본 허용하지 않는다.

키 사용 실패 시 평문 저장과 검증 해제를 금지한다. 캐시를 도입할 필요가 생기면 보존 기간, 폐기와 교체 반영을 먼저 정하고 그 전에는 임의의 영구 캐시를 추가하지 않는다. 키 유출 의심 시 쓰기 중지 범위, 새 키 전환, 복구와 재암호화 계획을 수립하며 노출 키의 단순 삭제부터 수행하지 않는다.

## 5. 키 교체와 재암호화

### 5.1 상태 계약

키 버전의 용도는 새 쓰기 가능, 기존 읽기만 가능, 폐기 후보로 구분한다. 실제 키 서비스의 상태명과 다를 수 있으므로 서비스 상태를 그대로 이 논리 상태와 혼동하지 않는다. 활성 쓰기 키는 하나로 정하고 각 행의 읽기는 행에 기록된 버전을 사용한다.

재암호화 작업은 대상 범위와 실행 ID를 명시하고 적용 전에 대상 수와 키 버전 분포를 확인한다. 실제 스크립트 명칭은 구현 시 기본 저장소 관례에 맞추되 아래 동작 계약은 유지한다.

| 모드 | 동작 |
|---|---|
| 점검 | 버전별 행 수와 처리 가능 여부 확인. DB 변경 없음 |
| 제한 적용 | 명시한 범위와 묶음 크기만 재암호화. 무한 순회 금지 |
| 재시도 | 이미 새 버전인 행은 건너뛰고 남은 구 버전만 처리 |
| 검증 | 대상 수, 성공, 실패, 건너뜀과 남은 구 버전 수를 대조 |

### 5.2 원자성과 동시 수정

행은 구 키 복호화가 성공하고 새 암호문이 준비된 경우에만 원자적으로 갱신한다. 원래 키 버전과 수정 상태를 확인하는 조건부 갱신 또는 행 잠금 중 기본 DB 구조에 맞는 방법을 선택한다. 사용자의 최신 수정을 재암호화 작업이 덮어쓰지 않아야 한다. 충돌은 건너뜀이나 재시도 대상으로 기록하고 성공으로 세지 않는다.

실패한 행의 구 암호문과 구 키 버전은 보존한다. 부분 실패 뒤 재실행해도 중복 손상 없이 완료되어야 한다. 종료 시 `대상 / 성공 / 실패 / 충돌 / 건너뜀 / 남은 구 버전`을 기록하고 원문은 기록하지 않는다.

### 5.3 롤백과 구 키 폐기

새 키를 활성화한 뒤 구 버전만 읽는 코드로 되돌리지 않는다. 롤백 후보 코드가 새 형식을 읽을 수 있는지 먼저 시험한다. 필요하면 새 쓰기를 일시 중지하고 키와 코드의 읽기 호환을 회복한 뒤 재개한다. 형식이 다른 버전 사이의 되돌리기는 별도 데이터 변환과 복원 계획이 필요하다.

구 키 폐기 전에는 다음을 모두 확인한다.

- 현재 행의 구 버전 잔존 수와 실패 및 미확정 행이 정리됨.
- 보존 중인 백업이 요구하는 키 버전 목록과 복구 수단이 확인됨.
- 별도 환경에서 해당 백업 시점의 키로 정상 복원 및 권한 거부 시험 통과.
- 코드 롤백과 사고 복구가 구 키에 의존하는지 확인됨.
- 보존 정책과 폐기 범위를 검토하고 별도 승인됨.

데이터와 키를 하나의 공개 백업 묶음에 넣지 않는다. 암호문 백업 메타데이터에는 필요한 키 버전 참조를 남기며 키 원문은 분리한 보존 절차를 따른다. 키를 잃은 암호문을 복구 가능하다고 안내하지 않는다.

## 6. 실습 CA와 인증서 계약

### 6.1 발급 대상

| 대상 | 인증서 용도 | 배포와 보관 |
|---|---|---|
| Root CA | 실습 신뢰 루트와 서명 | 개인키는 제한된 발급 위치에만 보관, 서버에 배포 금지 |
| 선택 Intermediate CA | 발급 역할 분리가 필요한 경우의 서버와 클라이언트 서명 | 필요가 확인될 때만 추가 |
| DB 서버 | Web DB 클라이언트가 검증할 서버 신원 | 실제 내부 접속 이름의 SAN, 서버 개인키 접근 제한 |
| Web 클라이언트 | DB가 검증할 승인된 연결 주체 | 클라이언트 용도와 DB 인증 주체 매핑, Web에서만 필요한 읽기 |

인증서에는 역할별 용도와 실제 호스트 식별자를 반영하고 서버와 클라이언트 인증서를 무작정 재사용하지 않는다. serial, 발급자, 주체, SAN, 용도, 유효기간, 배포 위치를 기록하되 개인키는 공개하지 않는다. 만료 시험용 인증서와 정상 인증서는 별도로 관리한다.

실습 CA를 모든 사용자 기기의 기본 신뢰 저장소에 배포하지 않는다. 내부 시험 클라이언트의 지정 신뢰 저장소를 사용하고 필요 없어진 신뢰 항목 회수 절차를 둔다. 서버 시각과 인증서 유효기간 검증도 확인한다.

### 6.2 PostgreSQL 서버 검증 TLS

기존 Web SG에서 DB TCP 5432로 연결하는 네트워크 경계는 유지한다. DB가 TLS를 제공하고 Web의 실제 driver가 CA 체인과 호스트를 검증하도록 구성한다. PostgreSQL 클라이언트의 `sslmode=verify-full`에 해당하는 계약을 사용하며 드라이버에 필요한 CA 경로와 실제 연결 호스트를 맞춘다. `require`에 해당하는 암호화만의 연결을 신원 검증 통과로 취급하지 않는다.

DB 접속 정책에서 TLS 요구 여부, 허용 Web 출발지와 DB 주체를 일치시킨다. 서버 옵션 변경, 평문 경로 거부, 서비스 재시작, 인증서 파일 권한을 시험한다. 실패 시 인증서 검증을 끄거나 Web/DB 포트를 전체 공개해 우회하지 않는다.

DB 서버는 클라이언트가 `verify-full`을 썼는지 암호화만 요구했는지를 TLS 연결 자체만으로 판별할 수 없다. 평문 접속 거부는 DB 정책으로 확인하고, 서버 신원 검증 유지 여부는 앱의 유효 연결 설정과 실제 미신뢰 CA, 만료, 호스트 불일치 시험으로 확인한다. 검증 해제와 평문 fallback 경로는 앱 설정과 코드에서 금지한다.

### 6.3 mTLS

서버 검증 TLS가 통과한 뒤 클라이언트 인증서를 요구하는 경로를 적용한다. 허용 CA와 클라이언트 인증서 주체의 DB 사용자 매핑을 명시한다. 비밀번호 인증을 함께 쓸지, 인증서 기반 인증을 사용할지는 실제 PostgreSQL 버전과 운영 목표에 맞춰 A-D6에서 하나로 정한다. 설정 키를 추가한 것만으로 양방향 인증 완료로 처리하지 않는다.

정상 인증서 연결과 함께 인증서 없음, 다른 CA, 만료, 주체 불일치, 승인되지 않은 DB 사용자 연결을 비교한다. 읽기와 CRUD 권한도 별도로 확인한다. mTLS 성공은 앱의 회원별 소유권 검사를 대체하지 않는다.

### 6.4 갱신과 ALB 경계

서버와 클라이언트 인증서는 유효기간과 갱신 시점을 정하고 새 인증서로 정상 및 실패 시험을 반복한다. CA 교체가 필요하면 구 신뢰와 새 신뢰의 전환 순서, 클라이언트 배포, 회수와 복구를 먼저 정의한다. 실제 폐기 또는 유효성 검증 메커니즘이 없는 상태에서 인증서가 즉시 무효화됐다고 주장하지 않는다.

ALB에서 외부 TLS가 종료되는 기본 구조는 유지한다. ALB→Web HTTPS를 별도로 선택하면 암호화 상태와 대상 인증서 신뢰 검증을 구분한다. ALB 대상 연결을 CA 미신뢰, 만료, 호스트 불일치 거부의 증거로 사용하지 않는다. 해당 실패는 실제 검증하는 Web→DB 클라이언트 경로에서 확인한다.

## 7. 실패 처리와 운영

| 실패 | 데이터와 서비스 동작 | 기록과 복구 |
|---|---|---|
| 키 접근 거부 또는 공급 장애 | 신규 보호 필드 저장 실패, 원문 fallback 금지 | 요청 ID와 실패 범주, 권한 및 연결 확인 |
| 암호문, tag, AAD 변조 | 복호화 실패, 부분 원문 응답 금지 | 가상 대상 식별자와 실패만 기록, 원본 보존 |
| 지원하지 않는 형식 또는 키 버전 | 일반 오류, 임의 기본 키 사용 금지 | 형식 호환과 키 목록 복구 |
| 재암호화 중단 또는 충돌 | 실패 행은 구 버전 유지, 최신 수정 보존 | 범위와 성공/실패 위치로 재시도 |
| 잘못된 인증서 | 연결 실패, 평문 자동 fallback 금지 | 체인, 호스트, 시간, 주체를 구분해 확인 |
| 갱신 후 정상 연결 실패 | 배포 중지, 이전 유효 설정 복구 | 설정과 인증서 참조 전후, 재시험 |
| 데이터 복원 후 키 불일치 | 복원 완료 처리 금지 | 필요한 키 버전 복구 또는 복구 불가 명시 |

실행 로그는 UTC 시각, 실행 ID, 단계, 대상의 가림 식별자, 결과, 오류 범주를 남긴다. 원문, 키, 비밀번호, 세션, 인증서 개인키, 전체 DB 연결 문자열은 기록하지 않는다. 공개 결과와 제한된 원본 자료를 분리한다.

## 8. 시험 목록

아래 `ENC`, `KEY`, `PKI`, `TLS`, `INT`는 이 심화의 내부 시험 ID다. 공식 과제 번호나 완료된 시험으로 해석하지 않는다. 결과 상태는 미착수, 통과, 실패, 미확정, 보류로 구분하고 실제 실행 근거가 있을 때만 통과로 기록한다.

### 8.1 필드 암호화

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| ENC-01 | 가상 필드 저장과 본인 조회 | 화면 결과와 원문 일치, DB에는 암호문 저장 |
| ENC-02 | DB 조회 및 덤프 대조 | 보호 필드 원문 없음, 기본 제목과 본문은 별도 범위임을 명시 |
| ENC-03 | 타인, 비로그인, 제한 관리자 직접 요청 | 기본 인가 정책에 따라 거부, 복호화와 데이터 변경 없음 |
| ENC-04 | 잘못된 키와 tag 및 암호문 변조 | 인증된 복호화 실패, 부분 원문 미노출 |
| ENC-05 | 다른 기록이나 소유자로 암호문 복사 | AAD 불일치로 실패 |
| ENC-06 | 빈 값, 형식 누락, 미지원 버전 | 빈 상태와 손상 구분, 손상을 정상 값으로 처리하지 않음 |
| ENC-07 | nonce 생성과 재시도 경로 | 고정값 없음, 같은 키의 nonce 재사용을 유발하는 코드 경로 없음 |
| ENC-08 | 한글과 기호, 요청 크기 경계 | encoding 유지, 전체 body 제한 초과 시 저장 없음 |
| ENC-09 | 키 공급 실패 중 저장 | 평문 및 반쪽 행 없음, 기존 데이터 유지 |
| ENC-10 | 로그, 오류 화면과 공개 증거 검사 | 원문과 키, 개인키, 세션 미노출 |

nonce 시험의 표본에서 중복이 없다는 사실만으로 영구 비충돌을 보장하지 않는다. 생성 방식과 키 사용량 기준의 검토를 함께 남긴다.

### 8.2 키 권한, 교체와 복원

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| KEY-01 | Web 실행 주체의 키 작업 | 승인한 범위만 성공, 정적 AWS 키 없음 |
| KEY-02 | DB Role, 점검 Role, 무관 주체의 키 접근 | 필요한 근거 없는 읽기와 복호화 거부 |
| KEY-03 | 새 키 활성화 후 새 저장과 구 행 조회 | 새 쓰기는 새 버전, 구 읽기는 구 버전 사용 |
| KEY-04 | 제한 묶음 재암호화와 중간 중단 | 성공 행만 갱신, 실패 행은 온전한 구 버전 유지 |
| KEY-05 | 중단 후 재시도와 이미 갱신된 행 | 중복 손상 없음, 수량 대조 가능 |
| KEY-06 | 재암호화와 사용자 동시 수정 | 최신 변경 미덮어쓰기, 충돌 명시 |
| KEY-07 | 코드 롤백 후보와 두 버전 데이터 | 읽기 호환 확인 또는 안전하게 배포 중지 |
| KEY-08 | 암호문 백업을 별도 DB에 복원 | 스키마와 데이터, 필요한 키 버전 일치, 앱 조회와 거부 재확인 |
| KEY-09 | 키 누락 또는 다른 버전으로 복원 | 실패를 복원 완료로 처리하지 않음 |
| KEY-10 | 구 키 폐기 사전 점검 | 잔존 행과 보존 백업 및 롤백 의존성이 있으면 폐기 보류 |

### 8.3 PKI와 내부 연결

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| PKI-01 | CA와 서버 및 클라이언트 발급 | 목적, SAN, 체인, 유효기간과 키 보관 위치 확인 |
| PKI-02 | 파일 접근과 배포 대상 점검 | CA 개인키가 Web/DB와 공개 자료에 없음 |
| TLS-01 | 신뢰 CA와 일치 호스트로 DB 연결 | 서버 검증 TLS 성공 및 CRUD 정상 |
| TLS-02 | 미신뢰 CA, 만료, 호스트 불일치 | 각각 실제 검증 클라이언트에서 실패 |
| TLS-03 | 평문 DB 접속 시도 | TLS를 요구하는 DB 접속 정책에서 거부 |
| TLS-04 | 승인한 클라이언트 인증서 | mTLS 연결과 허용 DB 작업 성공 |
| TLS-05 | 인증서 없음, 다른 CA, 만료, 주체 불일치 | 각 연결 거부, 앱 회원 인가와 별도 판정 |
| TLS-06 | 인증서 갱신과 서버 재시작 | 새 유효 인증서로 정상 연결, 필요한 실패 시험 유지 |
| TLS-07 | 잘못된 갱신과 설정 복구 | 이전 유효 설정 복원 후 정상 기능 확인 |
| TLS-08 | 앱 유효 설정과 fallback 경로 점검 | 검증 해제와 평문 fallback이 없고 TLS-02의 실패가 유지됨. 서버가 클라이언트 검증 모드를 판별한다고 해석하지 않음 |

### 8.4 통합과 성능

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| INT-01 | UI 저장에서 DB 암호문 및 본인 조회까지 | 하나의 실행 ID로 인가, 암호화, 연결과 DB 결과 대응 |
| INT-02 | AWS 주체와 앱 회원 및 DB 주체 교차 | 한 권한의 허용으로 다른 경계가 자동 허용되지 않음 |
| INT-03 | 교체 후 별도 복원과 정상 및 거부 요청 | 데이터와 키 버전 복원, 앱 인가와 TLS 경계 유지 |
| INT-04 | 기본 APP/DB/DEP/NET/WAF 관련 회귀 | 변경하지 않은 기본 기능과 보안 경계 유지 |
| INT-05 | 선택 성능 비교 | 동일 환경, 부하, 표본과 오류 조건 기록, 키 조회 영향 분리 |

INT-05는 선택 측정이며 통과 기준 수치를 미리 만들지 않는다. 평균만으로 결론 내리지 않고 표본 수, 지연 분포와 오류를 함께 기록한다. 서로 다른 서버나 다른 부하의 결과를 직접 개선율로 계산하지 않는다.

## 9. 증거와 완료 조건

기본 증거 구조에 심화 시험 결과를 추가한다. 예시는 향후 구현할 경로이며 이번 문서 작성으로 생성된 실행 결과가 아니다.

```text
evidence/<run-id>/
  manifest.json           환경, 코드와 설정 버전, 범위, 실행 시각
  config-redacted/        키 식별 참조와 TLS 설정의 가림본
  results/                ENC / KEY / PKI / TLS / INT 결과
  logs-redacted/          요청과 실패에 대응하는 최소 로그
  comparison/             키 버전 분포와 재암호화 전후, 선택 성능 비교
  restore/                백업 식별자, 필요 키 버전 참조, 별도 복원 결과
```

키 원문과 CA 및 서버 개인키는 증거 폴더에 두지 않는다. 인증서 공개 부분도 내부 호스트 등 공개 범위를 검토한다. 복원 메타데이터에는 키 버전 참조만 남기고 복구용 키의 실제 보관과 접근 경로는 제한된 운영 절차로 관리한다.

완료에는 구현 코드, 데이터 및 키 계약, 설정, 정상과 실패 시험, 키 교체와 별도 복원, 기본 회귀, 재현 절차가 필요하다. 보류한 항목은 이유와 재개 조건을 적는다. 인증서 파일 생성이나 암호화 함수 단독 성공만으로 심화를 완료 처리하지 않는다.
