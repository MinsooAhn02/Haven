# Haven 프로젝트 계획서 발표 대본

대상 자료: [Haven 프로젝트 계획서 최종 정리본](Haven_프로젝트_계획서_최종.pptx)

현재 상태는 구현 전 계획입니다. 아래 대본은 강사님께 구성과 수행 방법을 설명하고 의견을 받는 말투로 작성했습니다. 구현 완료나 검증 결과처럼 표현하지 않습니다.

## 1. Haven: AWS 기반 기록 공유 서비스와 보안 검증

저희 프로젝트는 Haven입니다. AWS에 기록과 파일을 공유하는 웹 서비스를 만들고, 사용자 권한과 클라우드 보안 설정이 제대로 적용되는지 검증하려고 합니다.

서비스 구축뿐 아니라 정상 접근과 거부 결과, 정책 개선 과정까지 설명할 수 있는 결과물을 만드는 것이 목표입니다.

## 2. 프로젝트 개요

사용자는 자신의 기록을 작성하고 파일을 첨부한 뒤 특정 회원에게 읽기 권한을 줄 수 있습니다. 공유받은 회원은 읽고 다운로드할 수 있지만, 수정하거나 다른 사람에게 재공유할 수는 없습니다.

이 기능을 이용해 누가 무엇을 할 수 있는지 구현하고, 허용되지 않은 접근이 실제로 거부되는지 확인하려고 합니다. 서비스 만들기, 접근 보호하기, 동작 확인하기를 하나의 프로젝트로 연결했습니다.

## 3. 전체 시스템 구성

전체 서비스 요청은 사용자에서 ALB라는 외부 입구를 거쳐 웹 서버와 DB 서버로 이어집니다. 웹 서버는 화면과 기능을 처리하고, DB는 기록과 권한 정보를 저장합니다. 실제 첨부 파일은 웹 서버의 비공개 저장 공간에 둡니다.

이 경로에 WAF 보안 정책을 연결하고 요청 로그를 확인하겠습니다. 도메인과 인증서, SSM 서버 관리, 시험 메일과 백업도 함께 준비할 계획입니다. 실선은 서비스 요청, 점선은 정책이나 관리 같은 보조 연결입니다.

## 4. AWS 안에 서비스를 어떻게 배치하는가

AWS 안에서도 공개 영역과 비공개 영역을 구분합니다. 외부 요청을 받는 ALB는 서로 다른 가용 영역의 공개 서브넷 두 개에 연결합니다. 웹 서버와 DB는 각각 별도의 비공개 서브넷에 배치하고 공인 IP를 주지 않습니다.

사용자가 웹 서버나 DB로 바로 들어오는 대신 정해진 입구를 거치도록 하는 구성입니다. 웹 서버와 DB는 각각 한 대로 시작하므로 전체 서비스가 이중화되거나 무중단으로 동작한다고 설명하지는 않겠습니다.

## 5. 허용할 연결과 막을 연결

서비스 요청에서 허용하는 연결은 세 구간입니다. 사용자는 HTTPS로 ALB에 접속하고, ALB는 허용된 규칙으로 웹 서버에, 웹 서버는 DB에 연결합니다.

웹 서버는 ALB 보안 그룹에서 오는 요청만, DB는 웹 서버 보안 그룹에서 오는 연결만 받도록 하겠습니다. 외부에서 서버로 바로 접속하거나 허가되지 않은 서버가 DB에 연결하는 경우도 거부되는지 시험하겠습니다. SSM 관리 접속과 앱 내부의 파일 권한 검사는 이 서비스 연결과 별도로 확인합니다.

## 6. 사용자가 이용할 기능과 화면

화면은 Django Templates로 구현할 계획입니다. 내 기록과 공유받은 기록을 구분하고, 작성과 수정, 공유 대상 지정과 해제, 첨부 기능을 제공합니다.

첨부는 우선 TXT와 PDF로 제한하고 파일당 2MiB, 기록당 3개, 계정당 10MiB를 제안 기준으로 잡았습니다. 파일은 공개 URL로 노출하지 않고 권한 확인 뒤 다운로드하도록 하겠습니다. 실패한 입력과 업로드에는 안내를 제공하고 실제 기능 시험도 화면에서 수행하겠습니다.

## 7. 구현 및 보안 검증 계획

이제부터는 세 가지 주제로 설명드리겠습니다.

먼저 화면에서 처리와 저장까지 서비스가 어떻게 동작하고, 데이터를 어떻게 복구할지 설명드리겠습니다. 다음으로 사용자 권한과 운영 권한, 웹 요청 보안 정책을 구분해서 설명하고, 마지막으로 직접 만들 점검 도구와 결과 비교 방법을 말씀드리겠습니다. 협업은 GitHub에서 작업과 검증 결과를 공유하는 방식으로 진행하려고 합니다.

## 8. 화면에서 저장까지의 동작

사용자가 보낸 요청은 ALB를 거쳐 웹 서버로 들어옵니다. 웹 서버 안에서는 Nginx가 요청을 전달하고 Gunicorn이 실행하는 Django 앱이 로그인 상태, 권한과 입력을 확인합니다.

검사를 통과하면 기록과 권한, 파일에 대한 정보는 DB에 저장하고 실제 첨부 파일은 웹 서버의 비공개 공간에 저장합니다. 조회는 소유자나 유효한 공유 대상에게, 수정과 첨부 변경은 소유자에게만 허용하겠습니다. 저장 실패와 임시 파일 정리도 기능의 일부로 다루겠습니다.

## 9. 저장한 내용을 유지하고 복구하는 방법

데이터 검증은 두 가지로 나눴습니다. 첫 번째는 기록과 첨부를 저장하고 서버를 재시작한 뒤 내용이 그대로 남아 있는지 확인하는 시험입니다.

두 번째는 백업으로 복구하는 시험입니다. DB와 파일, 파일 대응 목록을 같은 기준으로 보관하고 별도 환경에 복원하겠습니다. 복원 뒤 실제 내용을 조회하고 첨부를 다운로드하며, 공유 대상의 허용과 비인가 사용자의 거부도 다시 확인하겠습니다. 백업 파일이 생긴 것만으로 복구에 성공했다고 판단하지 않겠습니다.

## 10. 서비스 사용자 권한

서비스 권한은 소유자, 공유 대상, 그 외 회원으로 구분했습니다. 소유자는 자신의 기록과 첨부를 관리하고 읽기 권한을 부여하거나 해제합니다. 공유 대상은 읽기와 다운로드만 허용합니다.

예를 들어 A가 B에게 공유하면 B는 읽을 수 있지만 수정 요청은 거부됩니다. A가 공유를 해제하면 B의 다음 조회와 다운로드도 거부하겠습니다. 계정 관리자는 계정 상태와 이력을 관리할 뿐, 그 권한만으로 타인의 본문이나 파일을 볼 수 있게 하지는 않겠습니다.

## 11. AWS·서버·DB 권한

앞 장의 서비스 회원 권한과 별개로 운영 권한도 나누겠습니다. AWS에서는 필요한 설정을 변경하는 역할과 설정을 읽기만 하는 점검 역할을 분리합니다.

서버는 승인된 운영자가 SSM으로 관리하고 Web과 DB 각각에 필요한 권한과 연결을 준비하겠습니다. DB에서는 앱이 데이터를 사용하는 계정과 데이터 구조를 바꾸는 계정을 나눕니다. 역할 이름만 분리하는 데서 끝내지 않고 필요한 작업은 성공하고 맡지 않은 작업은 거부되는지 확인하겠습니다.

## 12. 잘못된 웹 요청을 어떻게 막는가

웹 요청 보안 정책인 WAF는 먼저 차단하지 않는 관찰 상태로 시작하려고 합니다. 정상 입력과 정해진 시험 요청이 어떤 규칙에 걸리는지 로그를 확인한 뒤 필요한 항목을 차단으로 전환하겠습니다.

변경 후에는 같은 요청으로 다시 시험하고 정상 사용도 유지되는지 확인하겠습니다. 응답 코드만 보고 WAF가 막았다고 판단하지는 않겠습니다. 특히 파일 요청은 전체 내용이 검사된다는 보장이 없으므로 앱의 권한, 형식과 크기 검증을 함께 유지하겠습니다.

## 13. 점검 도구로 무엇을 확인하는가

직접 만들 도구는 두 가지입니다. 설정 점검 도구는 AWS 보안 그룹을 읽어 실제 규칙과 기대한 규칙을 비교합니다. 정상, 위반, 판단 근거 부족과 실행 오류를 구분해 결과를 남기겠습니다.

요청 재현 도구는 허가된 대상에 정해진 사용자와 요청으로 시험하고 응답과 WAF, 앱 로그를 대조합니다. 점검 결과를 보고 필요한 정책을 운영자가 수정한 뒤 같은 조건으로 다시 시험하겠습니다. Prowler와 ZAP도 보조로 활용하되 자체 구현은 범위가 명확한 설정 비교와 요청 재현에 집중하겠습니다.

## 14. GitHub로 협업하며 구현하는 방법

기능과 시험 작업은 GitHub Issues에 완료 조건과 함께 나누고 담당을 정할 계획입니다. 각자 작업별 브랜치에서 구현한 뒤 PR로 변경 이유와 시험 결과를 공유하겠습니다.

다른 팀원의 검토와 준비된 자동 검사를 거쳐 main에 통합하고, 실제 AWS 동작과 보안 시험 결과도 작업에 연결하겠습니다. 자동 검사 통과를 실제 환경 확인으로 대신하지 않고 AWS 반영도 별도 절차로 수행하겠습니다.

전체는 설계, 로컬 서비스, AWS 통합, 점검과 개선, 증거와 시연 순서로 진행하려고 합니다. 이 범위와 구성으로 진행해도 과제의 의도에 맞는지, WAF 외에 별도 IPS가 필요한지, 공유와 첨부의 범위가 적절한지 의견을 듣고 싶습니다.
