# 조장 업무 절차

민수가 매일 하던 순서다. 기본 틀은 `docs/조장_운영기록/README.md`의 "조장 매일 점검 순서"와 같고, 여기에는 실제로 쓰던 명령을 적었다. Git Bash에서 레포 루트(`Haven/`) 기준이다.

## 1. 하루 흐름

| 언제 | 할 일 |
|---|---|
| 아침 | `morning.sh` 실행 (본인 담당), 열린 PR 확인 |
| PR 올라올 때마다 | 2번 "PR 처리" |
| 팀원이 판단을 물을 때 | 회의 없이 조장이 바로 정하고 운영기록 "결정과 이유"에 한 줄 |
| 저녁 | 3번 "저녁 정리"(개인 TODO 배포 → main 현황판 → 6개 동기화) → 4번 "팀 공지" |
| 21시 | `night.sh` (본인 담당) |

## 2. PR 처리

### 2-1. 확인

```bash
git fetch origin --prune
gh pr list                       # 열린 PR
gh pr view <번호>                 # 설명·시험 결과
gh pr diff <번호> | less          # 바뀐 내용
# GitHub Actions(CI)는 11/11부터 꺼져 있다(무료 사용량 소진). 대신 PR 본문의 로컬 시험 결과(명령·통과 수)를 본다.
# 앱 PR은 요찬이 main과 합쳐 PostgreSQL로 manage.py test 한 결과, 혁민 CLI는 pytest 결과.
```

확인할 것:
- PR에 **실제로 돌린 명령과 결과**, **일부러 실패시킨 거부 시험**이 있는지(팀 규칙)
- 짝 리뷰가 끝났는지: 요찬 PR은 혁민 보안 점검, 푸른 PR은 요찬이 context 대조, 민성 PR은 보람
- 비밀값(비밀번호, 키, 토큰)이 diff에 없는지
- 다른 사람 폴더를 건드리지 않았는지 (`gh pr diff <번호> --name-only`)

### 2-2. 앱 PR은 합쳐서 시험

앱 PR(요찬)과 화면 PR(푸른)이 서로 필요하면, main에 둘을 합친 상태로 시험한 뒤 병합한다. 요찬에게 맡겨도 된다.

```bash
git worktree add ../haven-test origin/main
cd ../haven-test
git merge --no-edit origin/<브랜치1> origin/<브랜치2>
cd 신요찬/app
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test -v 1       # 개발 DB는 dev-db-setup.ps1로 만든 로컬 PostgreSQL
cd ../../.. && git worktree remove ../haven-test --force
```

CI 통과는 "GitHub에서 시험이 돌았다"는 뜻일 뿐이다. 실제 서버에서 동작하는지는 배포 후 따로 확인한다.

### 2-3. 병합

```bash
gh pr merge <번호> --merge       # merge commit (squash·rebase 안 씀, 이력 보존)
```

## 3. 저녁 정리

> **저녁 정리 순서 (11/11 확정): ① 개인 TODO 배포(3-1) → ② main 현황판·기록 갱신(3-2) → ③ 6개 브랜치 동기화(3-3) → 공지.** 동기화를 마지막에 해야 6개가 한 번에 main 최신이 된다.

### 3-1. 개인 TODO 배포 (먼저)

사람별 할 일이 바뀌었으면 각자 `TODO.md` 끝에 `민성's comment · 날짜` 섹션을 덧붙인다(기존 내용은 수정·삭제하지 않는다).

- 다른 사람 폴더라 main에 직접 올리지 않고 **PR**로 보낸다(브랜치 `minsung-todo-<날짜>` 등). 추가만 있는지(`git diff --stat`에서 삭제 0) 확인한다.
- 병합하면 main에 들어간다. 팀원 개인 브랜치에는 3-3 동기화로 전달된다.
- 바뀐 것이 없으면 이 단계는 건너뛴다.

### 3-2. main 현황판·기록 갱신 (조장 기록만 main 직접 push 허용)

| 파일 | 고칠 곳 |
|---|---|
| `TASK_TODO.html` | 맨 아래 `<script>` 안의 `DATA`만. `updated`(시각), `mainSha`, 사람별 `main` 목록(끝난 건 `done: true`, 다 끝난 지난 항목은 지움, 내일 할 일 추가), `log`에 한 줄 |
| `TASK_TODO.md` | 사람별 상태 표의 해당 줄 |
| `docs/조장_운영기록/YYYY-MM-DD.md` | 그날 파일(없으면 새로). 점검 결과 / 결정과 이유 / 다음 조장 확인 사항 |

규칙:
- `done: true`는 **실제로 돌려 본 것만**. "PR 병합"과 "실제 서버에서 동작"은 따로 적는다.
- 팀원의 개인 `TODO.md`는 고치지 않는다. 바뀐 역할·할 일은 3-1처럼 끝에 `민성's comment · 날짜`로 덧붙인다.
- 현황판 JS가 깨지지 않았는지 확인:
  ```bash
  awk '/^const GH/{f=1} f&&/<\/script>/{exit} f' TASK_TODO.html > /tmp/tt.js && node --check /tmp/tt.js && echo OK
  ```
- 커밋·push:
  ```bash
  git switch Minsung && git pull
  git merge --ff-only origin/main
  # 파일 수정
  git add TASK_TODO.html TASK_TODO.md docs/조장_운영기록/
  git commit -m "docs: <무엇을 기록했는지>"
  git push origin HEAD:main && git push origin HEAD:Minsung
  ```
  main이 그 사이 바뀌어서 push가 거절되면 `git pull --rebase origin main` 후 다시 push. 이때도 force push는 쓰지 않는다.

### 3-3. 6개 브랜치 동기화 (마지막에 한다)

개인 TODO 코멘트 배포(3-1)와 main 현황판·기록 갱신(3-2)이 **모두 main에 들어간 뒤** 각자 브랜치에 main을 넣어 준다. 팀원은 다음 날 `git pull`만 하면 된다. 이 순서를 지키지 않으면 동기화한 뒤 main이 또 바뀌어 6개가 다시 뒤처진다(11/11 경험).

```bash
git fetch origin --prune
for b in Minsoo Minsung Boram Yochan Pureun Hyeokmin; do
  echo "$b: $(git rev-list --left-right --count origin/main...origin/$b)"   # 왼쪽=뒤처진 수, 오른쪽=앞선 수
done
```

- **오른쪽이 0**(앞선 커밋 없음)이면 그냥 앞으로 당긴다:
  `git push origin origin/main:refs/heads/<브랜치>`
- **오른쪽이 0보다 크면**(본인 작업이 있음) merge commit으로 합친다:
  ```bash
  git worktree add ../sync-<브랜치> origin/<브랜치>
  cd ../sync-<브랜치> && git merge --no-edit origin/main && git push origin HEAD:<브랜치>
  cd - && git worktree remove ../sync-<브랜치>
  ```
  충돌이 나면 멈추고 본인에게 맡긴다.
- **force push는 절대 하지 않는다.**
- 끝나면 위 for문을 다시 돌려 왼쪽이 전부 0인지 확인한다.

## 4. 팀 공지 (Discord)

기본은 한 줄이다:

```
6개 브랜치 main 최신으로 맞춰뒀습니다. pull 받고 TODO 이어서 하시면 됩니다.
```

- 할 일은 메시지에 쓰지 말고 현황판 사람별 `main`에 넣는다. 공지는 "pull 받고 TODO 보세요"만.
- todo에 없는 **새 문제나 안전 경고**가 있을 때만 `@이름`으로 한 줄 붙인다. 글은 하나로 쓰고 사람마다 따로 보내지 않는다.
- "확인했어요/잘했어요" 같은 줄은 넣지 않는다.
- 일정을 "앞당겼다/압축했다/두 배로 했다"는 식으로 쓰지 않는다.

## 5. 판단 기준

| 상황 | 기준 |
|---|---|
| AWS 작업 | `docs/AWS_운영결정.md` 범위 안이면 사전 승인된 것으로 진행. **되돌릴 수 없는 삭제**(EC2 terminate, DB, 백업, 버킷)만 그때 조장이 확인 |
| IAM 변경 | 보람이 적용, 민성은 실제 허용·거부 결과 확인 |
| 병합 보류 | 로컬 시험 결과 없음·실패, 거부 시험 없음, 짝 리뷰 안 끝남, 비밀값 포함 (Actions가 꺼져 GitGuardian 검사도 PR에 안 뜸 → diff에서 직접 확인) |
| 병합 후 고치기 | 이미 콘솔에 적용된 상태를 기록하는 PR 등, 위험이 작고 다음 PR로 충분할 때 (예: #42) |
| 막힘 | 담당자에게 바로 묻고, 답이 늦으면 조장이 정한다 |
