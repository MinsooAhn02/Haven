# 서버 배포 인계 (`안민수/server/`)

원본 절차는 `안민수/공통실행.md`의 "서버 설치·배포", "DB 백업·복원", "수요일 첫 배포 절차"다. 여기에는 민성이 혼자 할 때 필요한 것만 다시 정리했다.

## 1. 스크립트

| 파일 | 어디서 | 하는 일 |
|---|---|---|
| `common.sh` | 모두 | 공통 함수(로그, 실패 시 멈춤). 다른 스크립트가 같은 폴더에서 읽음 |
| `put-secrets.sh` | 조장 PC/CloudShell | SSM `/haven/*` 비밀값 3개 생성. **이미 생성됨, 다시 실행할 일 없음** |
| `db-setup.sh` | db-1 | PostgreSQL 16, DB `haven`, `haven_owner`(migrate)·`haven_app`(CRUD만), web-1에서만 접속 |
| `web-setup.sh` | web-1 | venv·Gunicorn(systemd)·Nginx·첨부 폴더, deploy key 생성 후 공개키 출력. GitHub SSH는 `~/.ssh/config`로 `ssh.github.com:443` 경유(sg-web outbound에 22 없음, #48). 여러 번 실행해도 결과가 같음 |
| `deploy.sh` | web-1 | `deploy.sh <40자리 commit>`: 받기 → 의존성 → migrate → 전환 → `/healthz`. 실패하면 이전 release로 복귀 (DB migration은 되돌리지 않음). 환경 파일에 `DJANGO_HTTPS`를 씀: CSRF origin이 `https://`면 1 (#52) |
| `backup.sh` / `restore.sh` | db-1 | DB 덤프 → `s3://haven-backup-${ACCOUNT_ID}/db-backups/<UTC시각>/`, 격리 DB `haven_restore_check`에 복원 후 행 수 비교 |
| `backup-uploads.sh` / `restore-uploads.sh` | web-1 | 첨부 파일 tar + sha256 목록 → DB 백업과 같은 `db-backups/<시각>/`에 한 묶음으로 (`haven` 서비스가 멈춰 있어야 실행됨), 복원은 격리 폴더 `/srv/haven/restore-check/uploads`에 풀고 비교 |
| `test-wsl.sh`, `test-backup-wsl.sh` | WSL Ubuntu-24.04 | 가짜 서버 시험. 스크립트를 고치면 다시 돌림 (47개 / 31개. 새로 설치한 WSL이어야 '새 머신' 확인 2개까지 통과) |

## 2. 첫 배포 (11/11 수) — 완료

**결과 (11/11):** 1~4번 완료(`f39e8e6`), 재배포 `b068ba5`(첨부 포함). 5번은 민성 연결확인표에 기록. 6번은 재부팅 대신 매일 `night.sh` → `morning.sh` 뒤 확인으로 바꿈(11/12 아침). **7번 백업 연습은 남음.** 서버에 실제 넣은 값: `ALLOWED_HOSTS=orchestration-haven.cloud`, `CSRF_TRUSTED_ORIGINS=https://orchestration-haven.cloud`(끝 슬래시 없음). 아래 표는 처음 계획 그대로 둔다(서버를 다시 만들 때 같은 순서).

**필요한 것:** web-1·db-1(인스턴스 ID·내부 IP는 기록에 적지 않음. EC2 콘솔 또는 `aws ec2 describe-instances`로 확인), 민성 Session Manager 권한(IAM 14번, 오전에 확인), main 최신 40자리 commit (`git rev-parse origin/main`).

**스크립트를 서버에 넣는 법 (첫 설치 때만):** 서버는 아직 코드를 받을 수 없어서 붙여넣기로 넣는다.
1. 내 PC Git Bash에서 `sha256sum 안민수/server/common.sh 안민수/server/db-setup.sh` (web-1은 `web-setup.sh deploy.sh`까지)
2. Session Manager에서 `sudo -i` → `mkdir -p /root/setup && cd /root/setup`
3. `cat > common.sh <<'EOF'` → 파일 내용 붙여넣기 → `EOF`
4. 서버에서 `sha256sum *.sh` → 1번 값과 같아야 실행. 다르면 붙여넣기가 깨진 것이니 다시 넣는다.

| # | 어디서 | 할 일 | 성공 확인 |
|---|---|---|---|
| 1 | db-1 | `WEB_IP=<web-1 내부 IP> bash db-setup.sh` | 마지막 줄 `OK  db-setup` |
| 2 | web-1 | `DB_HOST=<db-1 내부 IP> ALLOWED_HOSTS=orchestration-haven.cloud CSRF_TRUSTED_ORIGINS=https://orchestration-haven.cloud bash web-setup.sh` (11/11 실제 사용값) | 마지막에 공개키 출력 |
| 3 | GitHub | Settings > Deploy keys에 2번 공개키 등록, **Allow write 끔** — **admin만 가능 → 민수가 등록** | |
| 4 | web-1 | `bash deploy.sh <40자리 commit>` | `OK  deployed`, `curl -s -H 'Host: orchestration-haven.cloud' http://127.0.0.1/healthz` → ok |
| 5 | web-1·db-1 | 연결확인표: Web→DB 5432 성공, 다른 곳→DB 거부, postgres 원격 접속 거부 | 이민성 연결확인표에 결과 기록 |
| 6 | 둘 다 | `reboot` → 다시 접속 (11/11부터: 재부팅 대신 `night.sh` → `morning.sh` 뒤 확인) | healthz ok, `systemctl is-active haven nginx postgresql` 전부 active, DB 재접속은 아래 명령으로 `db ok` (healthz는 DB를 안 봄) |
| 7 | 백업 연습 | web-1 `systemctl stop haven` → db-1 `backup.sh`(시각 출력됨) → web-1 `backup-uploads.sh <그 시각>` → web-1 `systemctl start haven` → db-1 `restore.sh <시각>` → web-1 `restore-uploads.sh <시각>` | 각 단계 `OK`, 행 수·파일 sha 일치 |

7번의 버킷 지정 (11/18 정정): 계정 번호는 문서에 적지 않으므로 서버에서 STS로 조회해 넣는다. 예전 문구 `BACKUP_BUCKET=haven-backup-${ACCOUNT_ID} bash backup.sh`를 그대로 붙여 넣으면 `ACCOUNT_ID`가 비어 버킷 이름이 `haven-backup-`이 된다(스크립트의 `need BACKUP_BUCKET`은 빈 값만 막으므로 통과한 뒤 S3에서 실패).
```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text) && [ -n "$ACCOUNT_ID" ] && export BACKUP_BUCKET=haven-backup-$ACCOUNT_ID && echo "bucket ok"
bash backup.sh
```
- `bucket ok`가 안 나오면 멈춘다(STS는 NAT로 나가므로 21시 `night.sh` 뒤에는 실패한다).
- `restore.sh`·`backup-uploads.sh`·`restore-uploads.sh`도 같은 세션에서는 이 값을 그대로 쓴다. 다른 서버(db-1 ↔ web-1)나 새 세션이면 첫 줄을 다시 실행한다.
- `backup.sh`가 끝나면 `OK  backup <시각> -> …` 줄의 **시각을 바로 기록**한다. db-1 역할에는 `s3:ListBucket`이 없어 나중에 서버에서 목록으로 찾을 수 없다(11/18 확인).
7번 스크립트 위치: web-1은 배포된 코드 `/srv/haven/current/안민수/server/`에 있다. **db-1에는 코드가 없으므로** `backup.sh`·`restore.sh`를 위 붙여넣기 방법으로 `/root/setup/`에 넣는다(`common.sh`는 이미 있음, sha256 대조).

6번 DB 재접속 확인 (web-1, root):
```bash
(cd /srv/haven/current/신요찬/app && set -a && . /etc/haven/haven.env && set +a && runuser -u haven -- /srv/haven/venv/bin/python manage.py shell -c "from django.contrib.auth import get_user_model as U; U().objects.exists(); print('db ok')")
```

## 3. 두 번째 배포부터

코드와 같이 받은 스크립트를 쓴다. 붙여넣기는 필요 없다.

```bash
sudo -i
bash /srv/haven/current/안민수/server/deploy.sh <main 40자리 commit>
```

- 배포 전에 PR 병합과 PR 본문의 로컬 시험 결과 확인(Actions는 꺼져 있음), 배포한 commit을 운영기록에 남긴다.
- **배포는 매번 같은 커밋으로 2번 한다 (조장 결정 11/11).** `deploy.sh`는 받아 온 코드의 스크립트를 쓰는데 처음 한 번은 이전 버전 `deploy.sh`로 돌아 `deploy.sh`가 바뀐 커밋의 새 동작이 빠질 수 있다(11/11 `DJANGO_HTTPS` 누락). 같은 커밋으로 한 번 더 하면 코드가 같아 바뀌는 것은 없고 새 `deploy.sh`가 적용된다.
- 배포는 **09~21시**에만 한다. 21시 `night.sh` 이후에는 NAT가 없어 pip·apt·SSM 비밀값 읽기가 안 된다.
- 다음 날 EC2가 다시 시작되면 haven·nginx·postgresql은 자동으로 뜬다 (11/12 아침 `morning.sh` 뒤 6번 확인으로 검증).

### Nginx 접근 로그 요청 식별자 (11/18)

`web-setup.sh`가 Nginx 접근 로그(`/var/log/nginx/access.log`, CloudWatch `/haven/web` `…/nginx-access`)를 기본 combined 형식 뒤에 아래 값을 붙인 `haven` 형식으로 쓴다. WAF·ALB ↔ Nginx ↔ 앱 로그를 같은 요청으로 잇기 위해서다(조장 결정 11/13, 재검증 혁민).

| 값 | 뜻 | 없거나 형식이 틀리면 |
|---|---|---|
| `trace=` | `X-Amzn-Trace-Id`의 Root(ALB가 붙임). WAF 로그·앱 로그 `trace_id`와 같은 값 | `-` |
| `rid=` | 앱이 돌려준 `X-Request-ID`. 앱 로그 `request_id`와 같은 값 | `-`(Nginx가 직접 끊은 큰 413·static) |
| `cid=` / `run=` | `X-Haven-Request-ID` / `X-Haven-Run-ID`(혁민 CLI). 앱과 같은 형식(영숫자로 시작, `._:-`, 128자 이하)만 | `-`(원래 값은 쓰지 않음) |
| `client=` | `X-Forwarded-For`의 마지막 값 = ALB가 본 실제 접속 IP. 앞 값들은 클라이언트가 위조할 수 있어 쓰지 않음 | `-` |
| `rt=` | Nginx 처리 시간(초) | |

적용(PR 병합·배포 뒤 web-1 root, 09~21시): 서버의 `site.conf` 값을 그대로 읽어 다시 실행한다. 손으로 값을 적지 않는다.
```bash
(set -a && . /etc/haven/site.conf && set +a && bash /srv/haven/current/안민수/server/web-setup.sh)
tail -n 3 /var/log/nginx/access.log
```
- 새 Nginx 설정은 `nginx -t`를 통과할 때만 바뀐다. 실패하면 이전 설정으로 되돌리고 `FAIL: nginx config test failed (previous config restored…)`로 멈춘다(Nginx는 그대로 동작).
- 마지막 줄 끝에 공개키가 다시 출력되는데, 키는 이미 있어 바뀌지 않는다(GitHub 등록 다시 할 필요 없음).
- `client=`는 실제 접속 IP라 개인정보다. 로그 보존은 `/haven/web` 30일 그대로.

## 4. 도메인·HTTPS

서버의 도메인 값(`ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`)은 첫 web-setup 때 이미 넣었다. web-setup을 다시 돌릴 필요 없다.

- ALB 상태 검사: 경로 `/healthz`, 포트 80. Nginx가 `/healthz`만 Host를 첫 `ALLOWED_HOSTS`로 바꿔 넘기므로 ALB가 IP로 검사해도 통과한다.
- HTTPS 앱 설정은 요찬 #51(`DJANGO_HTTPS`, `신요찬/앱계약.md` 1.2.1). #51 병합 뒤 재배포하면 `deploy.sh`가 `DJANGO_HTTPS=1`을 쓴다(#52) → 세션·CSRF 쿠키에 Secure. 그 뒤에는 **HTTP로 로그인이 유지되지 않으므로 ALB 80 리스너를 443으로 리다이렉트**해 둔다. 앱에서 리다이렉트하지 않는다(ALB 상태 검사가 깨짐).
- HTTPS에서 CSRF 403이 나면: 환경 파일에 `DJANGO_HTTPS=1`이 있는지(`grep HTTPS /etc/haven/haven.env`), 브라우저 주소가 `https://orchestration-haven.cloud`인지(`CSRF_TRUSTED_ORIGINS`와 정확히 같아야 함).

## 5. 실패하면 볼 곳

| 증상 | 볼 곳 |
|---|---|
| deploy.sh 실패 | 스크립트가 이전 release로 되돌림. `journalctl -u haven -n 100`, `/srv/haven/releases/` |
| `github.com port 22: Connection timed out` | `/srv/haven/.ssh/config`가 없음(#48 전 web-setup). web-setup.sh를 다시 돌리거나 그 파일만 만든다. SG에 22를 열지 않는다 |
| healthz 실패 | `systemctl status haven nginx`, `journalctl -u haven -n 100`, `/var/log/nginx/error.log` |
| DB 연결 실패 | db-1 `systemctl status postgresql`, `/etc/postgresql/16/main/pg_hba.conf`, SG(Web→DB 5432) |
| SSM 비밀값 못 읽음 | NAT가 내려가 있는지(21시 이후?), EC2 Role `haven-ec2-ssm-role`에 `ssm:GetParameter` |
| pip/apt 실패 | NAT 상태 (`morning.sh` 했는지) |
| 백업 S3 거부 | 서버 Role의 `s3:PutObject`/`GetObject` (`db-backups/*`) → 보람 |
| 400 Bad Request | `ALLOWED_HOSTS`에 접속한 이름이 없음 → web-setup.sh 다시 |

**하면 안 되는 것:** 운영 DB `haven`에 restore (스크립트가 테이블이 있으면 거부하게 되어 있음), migration 되돌리기, 비밀값을 명령 인자나 로그에 넣기.
