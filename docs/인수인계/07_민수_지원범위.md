# 민수가 빠진 뒤 지원 범위

민수는 끝날 때까지 팀원으로 남는다. 개인 사정으로 코딩·배포·리뷰는 하지 않고, 레포(admin)만 지원한다. 민수의 폴더·기록·AWS 계정 `minsoo`는 그대로 둔다.

## 1. GitHub 레포 (`MinsooAhn02/Haven`)

- 레포는 민수 개인 계정에 그대로 둔다. 개인 계정 레포는 admin이 소유자 한 명뿐이다.
- 팀원 5명 + 조교님 2명은 write 권한이다. **PR 병합, 브랜치 push는 민성이 혼자 할 수 있다.**
- admin(민수)만 할 수 있는 것: 협업자 추가·삭제, Deploy keys 등록, 레포 설정·Actions 설정 변경, 레포 삭제·이름 변경.
  - 첫 배포의 Deploy key는 11/11에 민수가 등록한다.
  - 서버를 다시 만들어 deploy key가 바뀌면 민수에게 새 공개키를 보내 등록을 요청한다.
- 브랜치 보호는 무료 비공개 레포라 켤 수 없다. Actions는 이미 설정되어 있다.

## 2. 도메인

- **`orchestration-haven.cloud` — 이민성이 가비아에서 직접 구매 (11/11).** 등록 업체 계정과 DNS 모두 민성 관리라 민수 지원은 필요 없다.
- **DNS는 Route 53 호스팅 영역** (11/11 10:42 생성, 가비아 네임서버를 awsdns 4개로 변경). 도메인 등록·이전은 Route 53에서 하지 않는다(돈이 들고 계정에 묶임).

순서 (민성 권한은 보람 #50):
1. ACM 인증서 요청 (서울, `orchestration-haven.cloud`, DNS 검증, 태그 `Project=Haven`·`Owner=minsung`) → 검증 레코드를 Route 53에 추가. 네임서버 전파 뒤 Issued
2. ALB (public 서브넷 2개, sg-alb, 대상 그룹 web-1:80, 상태 검사 `/healthz`, 태그 `Project=Haven`) → 443 리스너에 인증서, 80은 443으로 리다이렉트만
3. Route 53에 `orchestration-haven.cloud` A 레코드 Alias → ALB
4. 서버 값은 이미 들어 있음(03 문서 4장). #51 병합 뒤 재배포하면 HTTPS 쿠키 설정이 켜진다
5. 확인: `https://orchestration-haven.cloud/healthz` → ok

## 3. 연락

- 레포 요청은 Discord로 민수에게. 바로 답하지 못할 수 있으니 하루 여유를 두고 요청한다.
- 민수 AWS 계정 `minsoo`는 그대로 둔다(MFA 등록됨). 민수는 팀원으로 남는다.
