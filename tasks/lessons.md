# Lessons

- Keep workflow docs focused on owner handoffs and time sequence; preserve the agreed architecture, roles, and four rounds instead of broadly rewriting them.
- 사용자가 구현과 마무리를 요청하면 로컬 수정에서 멈추지 않는다. 승인된 범위의 검증·커밋·푸시·병합까지 수행하고 실제 원격 상태로 완료를 확인한다.
- 병합·문서 정리 완료와 담당 구현 완료를 구분한다. 앱 인계가 없어도 독립적인 CLI CI·실행 검증처럼 진행할 수 있는 담당 작업은 먼저 수행한다.
- Discord 팀 공지는 보고서식 제목·강조·기계적인 담당별 목록을 줄이고, 실제 팀 대화처럼 짧고 자연스럽게 쓴다. 기존 작업 사실과 요청 범위는 유지한다.
- 팀원이 무엇을 답했는지 근거 없이 추측하지 않는다(11/09 '민성 답변은 Discord에 있을 것'이라고 단정했다가 틀림). git 커밋·PR·대화 아카이브에서 시각과 내용을 먼저 확인하고, 못 찾으면 못 찾았다고 말한다.
- 팀원에게 보내는 안내는 일어나는 순서대로 쓴다(예: PR 올리기 → 민수가 합치고 알림 → pull 후 이어서 작업). 조건·결과를 한 문장에 섞으면 순서를 헷갈린다.
- "main·내 거 최신화"는 상태 기록(TASK_TODO·현황판·운영기록·결정 문서) 갱신을 뜻할 수 있다(11/09: 브랜치 동기화만 하고 끝냈다가 정정받음). 병합 뒤에는 브랜치 동기화와 상태 기록 갱신을 둘 다 하고, 애매하면 둘 다 했다고 보고한다.
- 브랜치 동기화 루프는 매번 6개 전부 돌리고 끝에 behind 수를 출력해 빠진 브랜치가 없는지 확인한다(11/09 #31 병합 후 Yochan·Boram을 빠뜨림).
- 팀원이 보는 문서·공지에 "속도가 빨라서 기간을 줄인다/압축/2배" 같은 이유는 쓰지 않는다(11/09 정정). 일정은 날짜별 할 일만 적고, 이유가 필요하면 준비된 사실(무엇이 끝났는지)만 쓴다.
