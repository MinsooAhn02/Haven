# Haven 실제 공격 기반 보안 시험표 (확장안 SEC-01~SEC-60)

> **현황:** 60개 시험 설계 완료. **실제 공격/검증은 아직 수행하지 않음.**  
> **관계:** 기존 [Basic test plan.md](Basic%20test%20plan.md)의 APP/SH/UP/REP/WAF는 유지한다. 이 문서의 **SEC ID는 새로 제안한 번호**이며 공식 기본 구현 명세 ID가 아니다. 기존 명세와 연결하여 추적한다.

## 1. 왜 추가하는가

기본 시험표는 인증·인가·첨부 등의 요구사항 준수 확인이 중심이다. 본 확장안은 동일 기능에 **공격자가 조작한 요청**을 입력하여 인증 우회, SQL 주입, XSS, 파일 업로드·경로 조작, 비즈니스 로직 결함, 실제 WAF 판단을 검증한다. [OWASP WSTG v4.2](https://wstg.owasp.org/stable/4-Web_Application_Security_Testing/)와 [Django 보안 가이드](https://docs.djangoproject.com/en/6.0/topics/security/)를 참고했으나, 세부 ID는 **OWASP의 공식 시험 ID가 아니라 자체 ID**이다.

**중요:** 기능에 입력점이 없으면 `N/A (비적용)`로 표기한다. 예를 들어 Haven에는 공개 검색·익명 공유 링크·자체 API·파일 실행 기능이 기본 범위에 없다. SQLi 시험의 `id`는 Django의 숫자 라우팅에서 먼저 거부될 수 있으며, 그것만으로 모든 SQL 경로가 안전하다고 단정할 수 없다. **실제 원인**을 증거로 확인한다.

## 2. 실행 원칙

- **대상:** 승인된 Haven 로컬 개발 서버/가상 계정/허가된 AWS 시험 환경. 실제 개인정보, 운영 사용자, 무관한 호스트, 외부 반사·콜백 경로 사용 금지.
- **입력:** 고정된 무해한 fixture. 예시로 SQL 특수문자, 비실행 알림 수준의 XSS 확인 문자열, 웹쉘 *확장자만 흉내 낸 무해한 텍스트 파일*을 사용한다. 파일을 실행시키거나 시스템 명령을 수행하지 않는다.
- **요청 제한:** 기존 `request_verify.py`의 allowlist, 요청 수/속도/timeout/시간/응답 크기 제한을 그대로 따른다. WAF 기능 검증은 Count에서 먼저 수행하고, 정책 변경은 승인된 운영자가 수행한다.
- **판정:** 성공적인 공격 여부와 **WAF가 차단했는지**는 별개다. HTTP 코드만으로 PASS/FAIL을 결정하지 말고 DB·세션·로그·파일·브라우저 렌더링과 요청 ID를 함께 확인한다.
- **상태:** 각 행에 `미실행 → 진행 → PASS/FAIL/UNKNOWN/ERROR`를 별도 실행 기록으로 남긴다. `보류/N/A`는 테스트 누락이나 성공으로 세지 않는다.
- **분업:** Django 수정은 5번, 네트워크·SG는 6번, IAM·비용은 4번, 배포/DB·복원은 1번, WAF 시험과 CLI는 3번 담당.

## 4. 우선순위 및 단계별 적용

- **P0 (우선):** 핵심 공격면이자 직접적인 인증/인가·데이터 노출·파일 노출·WAF 평가에 중요한 테스트. 핵심 앱 기능이 준비되는 즉시 최소 요청으로 수행한다.
- **P1 (후속):** 범위 확대, 인코딩·예외·경합·운영 설정 확인. 준비된 기능부터 추가한다.
- **일정 해석:** `2회차` 등의 시점은 의존 기능의 구현과 승인 이후의 추천 시점이다. 1회차에는 **시험표 설계와 CLI fixture 개발**에 집중하고 실제 앱/WAF는 아직 준비되지 않았다면 미실행으로 둔다.

### 1회차에 바로 할 일

1. 이 문서의 범위와 `SEC-*` ID 사용을 팀에 공유하고, 기본 계획의 기능·테스트 범위 변경 승인을 받는다.
2. 변경이 없는 고정 입력 fixture, 예: SQL 문자열/HTML 문자열/더미 `.php` 확장자/잘못된 PDF/파일명 경계값을 설계한다.
3. `request_verify.py`에서 `suite_kind=regression`, `case_id=SEC-*`, `auth_role`, `input_reference`, `expected_app`, `expected_waf`를 지원하도록 기존 명세 계약을 따른다.
4. fixture만으로 기대 코드/오류/UNKNOWN/로그 가림과 URL allowlist를 검증한다. 실제 취약점 발견으로 기록하지 않는다.

## 6. 통합 시 유의사항

- 기존 시험표의 46개 ID는 삭제하지 않는다. `APP-06 ↔ SEC-09~15`, `SH-02 ↔ SEC-24~25`, `UP-02 ↔ SEC-32~36`, `WAF-02 ↔ SEC-56~58`처럼 **추적성을 유지**한다.
- 파일 업로드는 TXT/PDF가 허용된 현재 구현 계약에 맞춘다. 실물 웹쉘 실행 테스트는 현 기본 범위가 아니며, 별도 격리 환경과 팀 범위 승인 없이 추가하지 않는다.
- 추가 테스트 때문에 CLI를 무차별 공격 생성기나 부하 도구로 확장하지 않는다. `SEC-*` 케이스는 사전 승인된 고정 JSON/fixture 세트로 실행한다.
- 취약점 발견 시 **재현 조건 → 영향 범위 → WAF/앱 분리 → 수정 담당자 인계 → 수정 후 동일 조건 재시험** 순서로 기록한다.
