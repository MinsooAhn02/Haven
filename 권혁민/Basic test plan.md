# Haven 기본 보안 테스트

## 1. 목적과 시험 범위

Haven의 인증·인가·공유·첨부 처리에서 **정상 요청은 허용되고 비인가/잘못된 요청은 거부되는지** 확인한다. 로컬 Django 시험과 실제 AWS ALB/WAF 경유 시험을 분리하며, WAF 차단 여부는 HTTP 상태 코드만으로 단정하지 않고 WAF 및 앱 로그로 확인한다.

- 테스트는 **승인된 Haven 환경**에서만 진행하며 실제 개인정보·악성 파일·실제 계정 대신 가상 계정과 무해한 TXT/PDF fixture를 쓴다.
- 제한된 CLI는 미리 승인된 요청을 **순차 재현**한다. 임의 공격 생성, 무제한 부하, 자동 WAF 정책 변경은 범위가 아니다.
- 표의 **단계**는 권장 실행 시점이며, 어느 행도 현재 PASS로 간주하지 않는다. 준비되지 않은 기능은 `미실행` 또는 `보류`로 남긴다.

|---|---|---|

| 공유 | 기준선에서 B와 C 모두 미공유. 공유 시험에서만 A→B 관계 부여 | `PostShare` 행의 사전/사후 상태 |

| 경로 | 팀과 확정한 앱 URL·시험용 ID로 치환 | 대상 origin 승인, 실제 데이터가 아닌 가상 데이터 |

| 환경 | 로컬 앱(가능하면 CSRF 검사 강제) / HTTPS ALB·WAF 경유를 별도 실행 | 같은 케이스라도 계층별 거부 원인 구분 |

> **사전 조건 주의:** APP-03은 B/C가 *미공유*인 상태, SH-02는 B가 *공유받은* 상태, SH-03은 *공유 해제 직후* 상태에서 수행한다. 시나리오 간 상태 오염을 피하려면 시험 전용 데이터를 재생성하거나 기준 상태로 되돌린다.

### 공통 HTTP·보안 계약

- 비로그인 보호 **GET → 302** 로그인 이동. 비로그인 보호 **POST**는 **CSRF 오류 → 403**, 유효한 CSRF이나 비로그인 → **302** 로그인 이동하며 DB는 미변경.
- 로그인된 일반 사용자의 **미공유 글/권한 없는 객체 조회·변경 → 404**. 일반 회원의 **관리자 경로 → 403**. 지원하지 않는 HTTP 메서드 → **405**.
- 상태 변경의 정상 POST는 CSRF 검증과 인가·입력 검증을 모두 통과하면 **302(POST/Redirect/GET)**. 유효하지 않은 폼 입력은 **400**, 글 요청 전체 body 초과는 **413**.
- 응답 코드만 같아도 **로그인 이동 위치, 대상 정보 미노출, DB/파일 미변경, 차단 계층**까지 확인해야 PASS로 판정한다.
- Nginx/WAF가 먼저 응답했다면 그것을 Django의 CSRF/인가 검사 성공으로 기록하지 않는다.

## 6. 요청 재현 CLI 자체 시험 — REP-01~06

명세의 최종 예정 경로는 `scripts/request_verify.py`이나 **1회차 개발 파일은 본인 폴더에서 관리**하고, 공통 경로/실행 방식은 1번 담당자와 협의해 통합한다.

| 구분 | 기본값 / 요구 | 명령행 허용 상한 또는 비고 |

## 7. AWS WAF·로그·정책 비교 시험 — WAF-01~09

> **3회차:** Count로 관찰하고 AWS WAF·앱 로그를 대조. **4회차:** 승인된 규칙만 Block으로 전환하고 동일 조건 회귀·별도 confirmation으로 검증한다.

| 명세 ID | 대상 / 조건 | 시험 요청·행동 | 기대 결과·합격 조건 | 확인할 증거 | 단계 |
|---|---|---|---|---|---|
| WAF-01 | ALB + Regional web ACL | ACL 연결 확인·시험 요청과 로그 도착 대조 | 실제 rule/action·request ID에 맞는 로그 수집 | ACL/로그 설정·CloudWatch 로그 | 3회차 |
| WAF-02 | 후보 규칙 Count | 정상/시험 요청을 동일 조건으로 보내 일치 로그 확인 | Count 규칙의 탐지 기록은 있으나 **그 규칙만으로 차단되지 않음** | 규칙/버전/priority·로그·앱 도달 | 3회차 |
| WAF-03 | 검증된 Block 규칙 | 승인 후 Count→Block, 동일 시험 요청 재실행 | 규칙 일치 요청이 WAF에서 자동 차단됨을 실제 로그/앱 도달 여부로 확인 | 규칙 diff·WAF/앱 로그·HTTP | 4회차 |
| WAF-04 | 정상 업무 기능 | 로그인·글·공유·첨부 정상 요청 회귀 | 정책 전후 정상 기능 유지, 오탐 확인 | 정상 집합·로그·HTTP·DB | 4회차 |
| WAF-05 | 빈도 기반 규칙 | 승인된 한도 안에서 요청 간격·시각 변경 관찰 | 평가창·적용 지연·실제 action 기록; 한도로 불충분하면 미확정 기록 | 요청 타임라인·로그·설정 | 3~4회차 |

| WAF-07 | 로그 보존·가림 | WAF 로그의 가림 필드·보존 설정, 로그 미도착 상황 | 민감정보 미노출; 누락/충돌을 UNKNOWN으로 남김 | 로그 정책·가림 샘플·상관 상태 | 3~4회차 |
| WAF-08 | WAF 정책 rollback | 오탐/장애 시 직전 승인 정책으로 되돌리고 정상 요청 재시험 | 이전 정책 복구 및 정상 기능 회복 | 변경 이력·정책 버전·재시험 | 4회차 |
| WAF-09 | 글 body 크기·oversize | APP-11의 8,191/8,192/8,193바이트를 ALB/WAF 경유 재현 | WAF·프록시·앱 중 거부 주체 구분, 앱 body 제한 유지 | 직렬화 body·WAF/app 로그·HTTP | 3~4회차 |

### WAF 비교 보고 시 필요한 지표

- **정상 요청 오탐률:** WAF 판정 가능한 정상 요청 중 BLOCK된 수 / WAF 판정 가능한 정상 요청 수
- **시험 요청 차단률:** WAF 판정 가능한 시험 요청 중 BLOCK된 수 / WAF 판정 가능한 시험 요청 수
- Count 전·Block 후 동일한 대상, fixture, 인증 상태, 요청 속도, 앱 버전을 사용하며 **규칙/버전/예외 변경 내용**을 남긴다.
- WAF 분모 0은 `N/A`, 로그 미도착·충돌은 `UNKNOWN`, 실행/인증 오류는 `ERROR`로 따로 기록한다.
- Count에 사용한 회귀 집합 외에 **튜닝에 사용하지 않은 확인용 집합(confirmation)**을 분리한다.
- HTTP `403`만으로 WAF 차단 성공을 주장하지 않고 rule/action 로그 및 앱 수신 여부로 입증한다.

## 8. 시험 판정 기준과 기록 템플릿

### 8.1 공통 판정

| 상태 | 판정 기준 |
|---|---|
| `미실행` | 케이스만 설계했거나 대상 기능·환경이 준비되지 않음 |
| `PASS` | 기대 HTTP 동작과 함께 필요한 DB·파일·로그 증거를 확인 |
| `FAIL` | 증거가 충분하고 기대 동작과 실제 결과의 불일치가 확인됨 |
| `UNKNOWN` | 응답은 있으나 로그·차단 주체·필수 증거가 부족하거나 서로 충돌 |
| `ERROR` | 입력·인증 준비·연결·실행·출력 오류 또는 중단 |
| `보류` | 선행 구현·팀 결정·접근 권한·예산 승인 등 의존 조건 미충족 |

> `PASS/FAIL/UNKNOWN/ERROR`는 시험 판정용이며 프로젝트 TODO의 `미착수/진행/검증 대기/완료/보류`와 구분한다. **CLI 종료 코드**는 `0=전체 기대 결과 확인`, `1=확인된 불일치`, `2=ERROR·중단`, `3=UNKNOWN·로그 대기`이며 우선순위는 `2 > 3 > 1 > 0`.

각 시험 실행마다 다음 서식을 복사하여 기록한다(실제 시험 전에는 빈칸 유지).

|---|---|---|---|---|---|---|---|
| 미실행 | — | — | — | — | — | 미실행 | — |

로그/결과 기록 시 `run_id`, `request_id`, 요청 시각, HTTP 상태, redirect 대상, 응답 시간, 앱 도달 여부, WAF action·rule ID·verdict, `correlation_status`, 환경/정책 버전을 연결한다. 케이스 실행 결과 JSON의 세부 필드는 구현 명세 6.2절을 따른다.

- **Git 보안:** 실제 비밀번호·토큰·세션 쿠키·접근 키·민감한 원본 로그·파일 원문은 Git에 올리지 않는다. 공개용 증거는 식별자·필요 결과만 남긴다.
- **PR:** 본인 브랜치에서 commit/push → `main` 대상 PR → 검토 및 합의된 순서로 병합 → 최신 `main`을 `Hyeokmin`에 반영한다.
