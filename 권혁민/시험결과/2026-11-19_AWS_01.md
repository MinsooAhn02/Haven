## 2. 로컬 시험에서 바꾼 점

로컬 시험은 DB를 초기화한 뒤 게시글 1번이 있다는 전제로 만들어졌다. 운영 DB에서는 같은 번호가 다른 사용자의 게시글일 수 있으므로 다음과 같이 바꿨다.

| 로컬 | AWS 변환 |
|---|---|
| 미리 있는 게시글 1번 | 시작 시 A가 만드는 시험 게시글 `AWS-SEC-SETUP-A-POST` (ID는 응답에서 확인) |
| B가 이미 공유받은 상태 | 시험 중 `AWS-SEC-B-BEFORE-SHARE`(공유 전 B 조회 404) → `AWS-SEC-SHARE-B`(A가 B에게 공유) |
| SEC-28 고정 공유 번호 | B가 자기 공유를 해제 시도, 공유 번호는 A 화면에서 조회 |
| SEC-44 다른 출처로 새 글 작성 | 시험 게시글 수정으로 확인 (새 글이 거부되면 정리 대상이 없어지므로) |
| DB 초기화로 정리 | 시험이 만든 게시글 5개를 정리 단계에서 삭제하고 삭제 후 404 확인 |

코드 변경 (`request_verify.py`):

- 소유자가 아닌 계정의 수정·삭제·공유·해제 요청은 **기대 결과가 404일 때만** 허용
- 삭제 확인 화면 GET(`/posts/{post_id}/delete/`) 허용 (읽기 요청)
- AWS에서 비로그인 로그인 시도 허용 (데이터 변경 없음, 로그인 실패 기록만 남음)
- `share_lookup_role`: 공유 번호를 조회할 소유자 계정을 따로 지정
- AWS에서 시험 게시글을 수정할 때도 제목의 생성 표식 유지 (정리 단계가 게시글을 찾도록)
- 공유·해제 전에 관련 계정이 로그인했는지 실행 전에 검사 (1차 실행 중단 원인)
- 정리 요청 예약을 `정리 건수×4 + 공유 수×3 + 5`로 변경 (2차 실행 정리 오류 원인)

## 3. 실행 명령

작업 디렉터리: `권혁민/`

```cmd
python -m pytest -q

python request_verify.py run --target https://orchestration-haven.cloud --allowlist fixtures/allowlist_aws.json --cases fixtures/cases_aws_security_phase2.json --fixture-dir fixtures --output-dir output_aws_sec_phase2_02 --max-requests 150 --max-duration 400

python request_verify.py recover --run-json output_aws_sec_phase2_02/results.json --target https://orchestration-haven.cloud --allowlist fixtures/allowlist_aws.json --cases fixtures/cases_aws_security_phase2.json --fixture-dir fixtures --output-dir output_aws_sec_phase2_02_recover --apply

python request_verify.py collect-logs --run-json output_aws_sec_phase2_02/results.json --profile hyeokmin --region ap-northeast-2 --expected-account ${ACCOUNT_ID} --output-dir output_aws_sec_phase2_logs_02

python request_verify.py correlate-cloudwatch --run-json output_aws_sec_phase2_02/results.json --logs-dir output_aws_sec_phase2_logs_02 --expected-account ${ACCOUNT_ID} --output-dir output_aws_sec_phase2_corr_02
```

## 5. 실패 및 불일치 케이스

**시험 케이스:** HTTP 기대값 불일치 및 실행 오류 없음.

**1차 실행 (`output_aws_sec_phase2_01`):**

- `AWS-SEC-SHARE-B`에서 "공유 전 소유자와 수신자 로그인이 필요합니다"로 중단(17건 실행, 모두 기대값 일치).
- 원인: 시험 파일에서 B의 첫 요청이 공유보다 뒤에 있었음.
- 시험 게시글 5개는 자동 정리 완료(오류 0).
- 조치: 공유 전 B 조회 시험을 추가하고, 이런 순서 오류를 dry-run에서 잡는 검사를 추가함.

**2차 실행 정리 단계:**

- 마지막 정리(SEC-10 게시글, ID 41)가 "요청 수 한도 도달"로 실행되지 않음.
- 원인: 정리 예약 20건(`정리 건수×3+5`)보다 실제 필요 요청(23건: 게시글 5개 × 4 + 남은 B 공유 해제 3)이 많았음.
- 조치: 같은 실행 결과로 `recover` 실행 → 표식·ID 확인 후 삭제 302, 확인 조회 404, `cleanup_complete: true`. 예약 계산식을 수정함(`505a881`).
- 상관분석 종료 코드 2는 원 실행에 남은 이 정리 오류 기록 때문이며, 시험 케이스 문제는 아님.

## 7. 비고

- 공격형 문자열은 무해한 시험용이며, WAF는 Count 모드라 차단하지 않았다. 탐지 결과는 이번 시험 요청 기준의 관찰이며 방어율이 아니다.
- 템플릿 문자열(`{{ 7|add:7 }}`)만을 잡는 관리형 규칙은 없다. SEC-07 탐지는 같은 본문의 SQL·XSS 문자열 때문이다.
- XSS 문자열의 화면 이스케이프는 manual_required로 이번에 확인하지 않았다. 게시글이 정리 단계에서 삭제되므로 확인하려면 실행 중 브라우저로 봐야 한다.
- 로그인 SQLi 8종은 실행 IP에 로그인 실패 8회를 남긴다(IP 한도 15분 30회). 같은 시험을 15분 안에 반복하지 않는다.
- 원본 결과: `output_aws_sec_phase2_01/`, `output_aws_sec_phase2_02/`, `output_aws_sec_phase2_02_recover/`, `output_aws_sec_phase2_logs_02/`, `output_aws_sec_phase2_corr_02/` (로컬 보관, WAF 원본 로그에 접속 IP와 시험 문자열이 남아 커밋하지 않음)
- 비밀번호·세션 쿠키·CSRF 토큰·계정 번호는 보고서에서 제외.
