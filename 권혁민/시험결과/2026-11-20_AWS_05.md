# Haven AWS 보안 시험 결과 #05 (남은 SEC 자동 시험과 WAF 오탐·미탐 정리)

## 요약

공격 시험 계획서 SEC-01~60 중 **자동 CLI로 할 수 있는 항목을 모두 AWS 운영 사이트에서 실행**했다. 이번에 새로 실행한 것은 5회(2026-11-19~20)이고, 모든 요청이 기대한 HTTP 결과와 맞았으며, WAF·앱 로그에서 요청 하나하나를 찾아 대조했다. 시험이 만든 게시글·공유·첨부는 모두 정리했다.

| 묶음 | run_id | HTTP 기대값 | 로그 대조 | WAF에서 본 것 |
|---|---|---|---|---|
| 남은 SEC (26·47·49·52·58·60) | `10afc1de` | 26/26 | 30/30 MATCHED | 정상 로그인·가입 11종 오탐 0, 8KB 뒤 XSS 미탐 |
| 헤더 (08·55, 헤더 규칙) | `74d936ee` | 15/15 | 15/15 MATCHED | 정상 헤더 오탐 0, 헤더 공격 7/8 탐지 |
| 세션·첨부 (18·19·22·29·30·41) | `54020bc6` | 16/16 | 20/20 MATCHED | 일반 사용 흐름 전체 오탐 0 |
| 남은 SEC 재실행 (특수문자 비밀번호 1차) | `046d3e4b` | 31/31 | 35/35 MATCHED | `!`·`#`·`#$` 조합 5종 오탐 0 |
| 남은 SEC 재실행 (특수문자 비밀번호 2차) | `55441b52` | 31/31 | 35/35 MATCHED | **`!@#`가 든 비밀번호 2종이 `SQLi_BODY`에 걸림(오탐 재현)** |

**WAF 판단에 쓸 핵심 결과**

1. **오탐:** 정상 헤더와 글·공유·업로드·다운로드·로그아웃 흐름에서는 **규칙 매칭 0건**이었다. 그러나 **비밀번호에 `!@#`가 이어진 로그인·가입 요청은 `SQLi_BODY`에 걸린다**(재현 확인). 11/16·17 브라우저 로그인·가입 8건도 같은 원인이다(비밀번호 `qwer1234!@#$`, 시험용 더미값). SQLi 규칙을 그대로 Block하면 이런 비밀번호의 사용자는 로그인·가입이 막힌다.
2. **미탐:** KnownBadInputs 헤더 공격(Log4j, 난독화 Log4j, Java 실행 문자열, `Host: localhost`)은 **모두 탐지**했다. base64 직렬화 문자열만 규칙 범위 밖이었다. **본문 8KB 뒤의 공격 문자열은 탐지하지 못했다**(ALB WAF 검사 한도).
3. **앱 방어:** 세션 교체, 쿠키 속성, 로그아웃 후 세션 무효화, 첨부·공유 ID 조작, 소유자 필드 삽입, 프록시 헤더 조작에 대해 모두 기대대로 막았다.
4. **새로 발견:** WAF 로그의 `matchedData`에 **요청 본문 일부가 그대로 저장**된다(SEC-53). 로그인 요청이 규칙에 걸리면 비밀번호 일부가 로그에 남을 수 있다.

| 정상 요청 | 건수 | 규칙 매칭 |
|---|---|---|

| 어제 브라우저 수동 시험의 일반 요청 (화면 보기·공유·다운로드·삭제) | 30 | 0 |

**오탐 확인: 비밀번호의 `!@#` → `SQLi_BODY`**

11/16 11:16~11:35와 11/17 12:42에 한 IP(한국)의 브라우저 로그인 6건·가입 2건이 `SQLi_BODY`에 걸렸다. 비밀번호는 시험용 더미값 `qwer1234!@#$`였다(WAF 로그로 확인, 실사용 비밀번호 아님은 혁민 확인). 같은 모양의 가짜 비밀번호로 두 번 재현 시험을 했다.

| 비밀번호 (가짜) | 실행 | `SQLi_BODY` |
|---|---|---|
| `Haven2026!test#$`, `abcd1234!#$`, `Spring!2026#`, `test#1234`, `hello!world` | `046d3e4b` | 모두 안 걸림 |
| `qwer1234!@#$` | `55441b52` | **걸림** |
| `Haven2026!@#` | `55441b52` | **걸림** |
| `abcd1234!@` (`#` 없음) | `55441b52` | 안 걸림 |
| `abcd1234@#$` (`!` 없음) | `55441b52` | 안 걸림 |
| `abcd1234#$!@` (순서 다름) | `55441b52` | 안 걸림 |

- **`!` → `@` → `#`이 바로 이어질 때만** 걸렸다.
- WAF 매칭 조각은 본문을 MySQL 문법으로 나눈 모양이었다. `!`(NOT 연산자), `@`(이름 없는 변수), `#`부터 끝까지(주석)로 읽혀 SQL 주입 패턴처럼 보인 것으로 해석된다. 사용자가 `csrfmiddlewaretoken` 칸에 이상한 값을 넣은 것이 아니라, 매칭 조각이 본문 첫 칸 이름부터 표시된 것이다.
- `Shift+1·2·3(·4)`를 차례로 누른 비밀번호는 흔하므로, **실사용자 로그인·가입이 막힐 위험이 크다.**
- 앱은 이 요청을 정상 처리했다(없는 아이디라 400). 앱은 Django ORM을 쓰므로 로그인 폼에 SQL 주입 경로가 없고, 앱 시험(`admin' --` 등 400 거부)으로도 확인되어 있다.

## 5. 결과: WAF 미탐 (공격 요청을 놓쳤는가)

| 공격 | 규칙 | 결과 |
|---|---|---|
| User-Agent에 Log4j `${jndi:ldap://…}` | `Log4JRCE_HEADER` | 탐지 |
| 임의 헤더에 Log4j | `Log4JRCE_HEADER` | 탐지 |
| 난독화 Log4j `${${lower:j}ndi:…}` | `Log4JRCE_HEADER` | 탐지 |
| 헤더에 Java 실행 문자열 `(java.lang.Runtime).getRuntime().exec(…)` | `JavaDeserializationRCE_HEADER` | 탐지 |
| 헤더에 Java 직렬화 시작 문자열(base64)만 | — | 미탐(규칙 범위 밖) |
| `Host: localhost` | `Host_localhost_HEADER` | 탐지(앱도 400) |
| 스캐너 User-Agent (Nmap) | `UserAgent_BadBots_HEADER` | 탐지 |
| User-Agent 없음 | `NoUserAgent_HEADER` | 탐지 |
| 첨부 파일 내용 맨 앞의 XSS | `CrossSiteScripting_BODY` | 탐지 |
| 첨부 파일 내용 **8KB 뒤**의 XSS | `SizeRestrictions_BODY`만 | **XSS 미탐** |
| 쿼리·경로의 CRLF | — | 매칭 없음(앱이 무해하게 처리) |

공격 문자열 속 주소는 모두 `.invalid` 도메인이라 실제로 접속되지 않는다.

**8KB 경계:** ALB에 붙은 WAF는 요청 본문의 앞 8KB만 검사한다. 그보다 큰 본문은 `SizeRestrictions_BODY`가 표시하지만, 이 규칙은 2 MiB 정상 업로드도 잡는 오탐이 있어(`2026-11-19_AWS_02.md`) Block할 수 없다. 따라서 큰 업로드 안의 내용은 **WAF가 아니라 앱 검증**(TXT·PDF 형식 검사, 다운로드 전용 제공, `nosniff`)이 지킨다.

## 6. 수동 시험 로그 검토

**어제 브라우저 XSS 시험 (11/19 14:26~16:11)** — WAF 로그 37건, 앱 로그 29줄. 모두 시험자 PC 한 IP의 요청이었다.

| 요청 | WAF | 앱 |
|---|---|---|
| XSS 글 작성 2회 | 2/2 `CrossSiteScripting_BODY` | 1회 저장(나머지 1회는 저장 안 됨) |
| `x' onmouseover…` 업로드 | `CrossSiteScripting_BODY` | 302 성공 |
| `&lt;svg…` 업로드 2회 | 2/2 `CrossSiteScripting_BODY` | 400 거부 |
| 15:42 업로드 1회 | `CrossSiteScripting_BODY` | 로그인 세션 만료로 로그인 화면 이동(저장 안 됨) |
| DevTools `<img …>` 업로드 | `CrossSiteScripting_BODY` | 302 성공 |
| 일반 요청 30건 | 매칭 0 | 정상 |

- 공격 문자열이 든 요청 7건 모두 탐지했다(미탐 0). 오탐은 0이다.
- 첨부 파일명만으로도 XSS 규칙이 걸렸다. 파일명이 본문 앞부분에 들어가기 때문이다.
- 수동 요청도 ALB Trace ID가 WAF 로그와 앱 로그(앱 JSON·gunicorn·Nginx)에 똑같이 남아, CLI 없이 계층 간 대조가 가능했다.

## 7. 새로 발견한 점: WAF 로그의 본문 조각 (SEC-53)

규칙에 걸린 요청은 WAF 로그의 `ruleMatchDetails.matchedData`에 **요청 본문의 일부가 그대로 저장**된다. WAF 로그 가리기 설정은 헤더·URI·쿼리만 지원하고 **본문은 가릴 수 없다.** 실제로 11/16·17 로그인·가입 8건의 로그에 비밀번호가 평문으로 남아 있었다(이번에는 시험용 더미값). 실사용자 비밀번호가 위 오탐에 걸리면 같은 방식으로 `aws-waf-logs-haven`에 남는다. 이 문제는 로그인·가입 경로의 `SQLi_BODY` 오탐을 없애면 크게 줄어든다.

권고:
- `aws-waf-logs-haven` 조회 권한을 필요한 사람으로 제한한다.
- 보관 기간을 정해 둔다.
- 분석할 때는 `matchedData`를 화면이나 문서에 옮기지 않는다.

## 8. 정리와 한계

- **정리:** 실행마다 시험 게시글 2개(공유·첨부 포함)를 정리했고, 상세 주소 404로 확인했다. DB 행·첨부 파일의 물리 삭제는 확인하지 않았다.
- **로그 도착 지연:** `55441b52`는 실행 직후 로그를 모아 마지막 정리 확인 2건이 UNRESOLVED였다. 몇 분 뒤 다시 모아 35/35 MATCHED를 확인했다.
- **헤더 시험 1차 실행 오류:** 첫 실행에서 "User-Agent 없음" 요청에 urllib3가 기본 User-Agent를 붙여 시험이 성립하지 않았다. `SKIP_HEADER`로 고쳐 다시 실행했고, 위 결과는 2차 실행 기준이다.
- **판정 방식:** 모든 케이스가 `manual_required`라 CLI 판정은 UNKNOWN이다. PASS는 HTTP 결과와 로그를 보고 사람이 내렸다.
- **SEC-52:** CLI는 응답 본문을 저장하지 않는다. DEBUG 화면이 없다는 판단은 응답 크기와 헤더에 근거한다.
- **출력 파일:** 원본 결과와 로그(`output/`)는 계정 번호와 IP가 들어 있어 저장소에 넣지 않았다.
