## 2. 시험 방법: Block 기대값 프로필

같은 시험 묶음을 그대로 쓰고, **기대값만 Block 단계 기준으로 바꿔 끼운다.**

- `fixtures/block_expectations.json`은 묶음별로 "몇 단계부터 WAF에서 막혀야 하는 요청"의 목록이다. 각 요청이 **Count 실행에서 실제로 걸린 규칙**(`count_rule_ids`)에 판단안의 단계와 예외를 적용해 만들었다. 요청마다 근거 Count 실행의 run_id와 규칙 이름을 함께 적어 두었다.
- `--expect-profile fixtures/block_expectations.json --block-stage N`으로 실행하면:
  - 목록에서 N단계까지 막히는 요청은 **WAF BLOCK + HTTP 403 + 앱 미도달**을 기대한다.
  - 나머지 요청은 **원래 앱 기대값 + WAF ALLOW**를 기대한다. 정상 요청이 막히면 FAIL이 된다.
  - 판정은 `http_only`로 바꿔, 로그 대조 뒤 CLI가 PASS/FAIL을 낸다(기존 묶음 파일은 그대로).
- 글을 만드는 요청이 막히는 단계에서는 글이 생기지 않는 것이 정상이므로, 정리 단계에서 그 표식의 글이 **없는지만** 확인한다. 막히지 않아 글이 생기면 정리는 하되 실패로 남긴다.

### 정상 요청 (막히면 안 되는 것)

- 글 작성·수정·읽기, 공유·해제, TXT·PDF 업로드(2 MiB 포함), 다운로드, 로그인·가입·로그아웃, 권한 거부(404)가 **모두 WAF ALLOW이고 Count 실행 때와 같은 응답**이었다.
- 2·3단계에서 다룰 요청(SQLi·XSS 문자열, 스캐너 User-Agent, User-Agent 없음, 8KB 넘는 본문)도 아직 Count라 **ALLOW, 원래 앱 응답 그대로**였다.
- 3단계 예외로 남길 요청(로그인 `!@#` 비밀번호, XMP 메타데이터 PDF, 파일명 XSS 업로드)도 ALLOW였다.
