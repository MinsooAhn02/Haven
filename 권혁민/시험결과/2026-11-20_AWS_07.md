# Haven AWS 보안 시험 결과 #07 (WAF Block 2단계 전후 비교: SQLi + 로그인·가입 예외)

## 요약

2026-11-20 14:28:22 KST에 **SQLi 규칙 그룹을 Block으로 바꾸고, 로그인·가입 주소에서만 `SQLi_BODY`를 Block하지 않는 예외 규칙(`haven-sqli-body-except-auth`)을 추가했다**(WAF Block 판단안 5-2의 2단계). KnownBadInputs는 1단계(11:46:57)부터 Block이다. 그 뒤 AWS 시험 묶음 8개를 **Block 2단계 기준 기대값**으로 다시 실행하고 WAF·앱 로그를 대조했다.

### 2단계에서 새로 막힌 요청 (19건)

| 요청 | 막은 규칙 | 레이블 |
|---|---|---|
| 로그인 username SQLi 6종, password SQLi 3종 | `SQLiExtendedPatterns_BODY` | `SQLi_Body`도 붙음(로그인이라 Count) |
| SQL이 든 글 작성 3건(SEC-06·07·10), 글 수정 1건(SEC-11 준비) | `SQLiExtendedPatterns_BODY` | `SQLi_Body`, `CrossSiteScripting_Body`(Count)도 붙음 |
| 공유 대상 SQLi (SEC-04) | `SQLiExtendedPatterns_BODY` | `SQLi_Body` |
| 경로 SQLi (`/posts/1 OR 1=1/`) | `SQLi_URIPATH` | — |
| 쿼리 SQLi (글 목록·로그인 화면 쿼리, `SLEEP`, 주석 끼운 `UNION`) 4건 | `SQLi_QUERYARGUMENTS` 등 | — |

로그인 SQLi 공격은 `SQLi_BODY`가 예외로 Count인데도 `SQLiExtendedPatterns_BODY`가 막았다. **로그인·가입 예외를 둬도 일반적인 로그인 SQL 공격은 막힌다**는 판단안 3-2의 예상이 맞았다.

### 그대로여야 하는 요청

- 1단계 6건(KnownBadInputs)은 그대로 403이었다.
- 글·공유·업로드(2 MiB, XMP PDF 포함)·다운로드·로그인·가입·로그아웃은 모두 WAF ALLOW, 원래 응답 그대로였다.
- 3단계 대상(XSS, 스캐너 User-Agent, `../` 파일명 등)은 아직 Count라 ALLOW, 원래 앱 응답 그대로였다.

## 4. 예외 규칙 확인

**로그인·가입 예외가 동작하는가**

| 요청 (남은 SEC, 2회 실행) | `SQLi_Body` 레이블 | WAF | 앱 |
|---|---|---|---|
| 로그인 비밀번호 `qwer1234!@#$` | 있음 | ALLOW | 400 |
| 로그인 비밀번호 `Haven2026!@#` | 있음 | ALLOW | 400 |
| 나머지 특수문자 비밀번호 3종, 정상 로그인 8종, 가입 3종 | 없음 | ALLOW | 400 |

**예외 규칙이 로그인·가입 밖에서 막는가**

글 본문에 같은 문자열을 넣는 시험을 추가했다(P04 `qwer1234!@#$`, P05 `새 비밀번호는 Haven2026!@#`). 두 요청 모두 **302(저장)**, WAF ALLOW이고 `SQLi_Body` 레이블이 **붙지 않았다.** 글 본문에서는 이 문자열이 `SQLi_BODY`에 걸리지 않는다. 그래서 예외 규칙이 막을 대상이 없었다.

예외 규칙의 Block 동작을 직접 확인하려고, **로그인 요청과 같은 모양의 본문**(`…&username=…&password=qwer1234!@#$`, 가짜 CSRF 값)을 비로그인 curl로 두 주소에 보냈다(15:09). WAF는 앱보다 먼저 검사하므로 로그인하지 않아도 확인된다.

| 시각 | 요청 | 응답 | WAF 로그 |
|---|---|---|---|
| 15:09:47 | `POST /posts/new/` | 403, `Server: awselb/2.0` | **BLOCK, `haven-sqli-body-except-auth`** |
| 15:09:51 | `POST /accounts/login/` | 403, `Server: nginx`(앱의 CSRF 거부) | ALLOW, `Default_Action` |

같은 본문이 주소에 따라 갈렸다. **예외 규칙이 로그인·가입 밖에서는 막고, 로그인·가입에서는 통과시킨다.** 계정·글은 만들어지지 않았다.

**판단안의 남는 위험 갱신:** 판단안 3-2는 "글 본문에 `abc123!@#`처럼 쓰면 걸릴 수 있다(시험하지 않음)"고 남겼다. 이번에 글 본문 5종(P01~P05)으로 확인한 결과 **걸리지 않았다.** `!@#` 오탐은 로그인 본문의 구조(`…&password=…!@#` 끝부분)에서 생기는 것으로 보이며, 그 위치는 예외로 처리되어 있다.

## 6. 다음 단계

- **3단계:** Common 그룹 Block + 업로드 `CrossSiteScripting_BODY` 예외 규칙(판단안 5-2, 우선순위는 Common보다 뒤). `SizeRestrictions_BODY`·`NoUserAgent_HEADER`는 Count 유지. 적용 뒤 같은 8개 묶음을 `--block-stage 3`으로 실행한다. 기대: XSS·LFI·SSRF·스캐너 UA 등 19건이 새로 403, **파일명 XSS 업로드·XMP PDF·2 MiB 업로드는 302 유지**(예외 확인), User-Agent 없음은 200 유지.
- 3단계 예외 규칙도 이번과 같이 **설정 대조 + curl로 직접 Block 확인**을 한다.
