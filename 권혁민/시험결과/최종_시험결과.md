**결론**

1. **앱 방어:** 실행한 SEC 시험과 기본 시험에서 인증·인가·공유·첨부·CSRF·입력 검증 결함은 나오지 않았다. 모든 요청이 기대한 HTTP 결과와 같았고, 요청마다 WAF·앱 로그에서 같은 요청을 찾아 대조했다.
2. **WAF:** Count 관찰로 정상 요청 오탐 3가지를 찾았다. 예외 규칙으로 처리한 뒤 3단계로 Block 전환을 마쳤다(11/20). 단계마다 막혀야 할 요청만 막혔고, **정상 요청이 403이 된 것은 0건**이다.
3. **남은 위험:** WAF 로그 `matchedData`에 요청 본문 조각이 남는다(SEC-53, 가릴 수 없음). 본문 8KB 뒤 내용은 WAF가 검사하지 않는다. 둘 다 앱 검증과 로그 접근 제한으로 대응한다(5절).

## 4. WAF 결과

### 4-1. Count 관찰에서 찾은 오탐과 처리

| 오탐 | 규칙 | 처리 | 근거 |
|---|---|---|---|
| 8KB 넘는 정상 첨부 업로드 | `SizeRestrictions_BODY` | Count 유지(앱이 2 MiB 제한) | `TODO.md` 누적 분석, `2026-11-20_AWS_05.md` |
| 비밀번호에 `!@#`가 이어진 로그인·가입 | `SQLi_BODY` | 그룹은 Block, 로그인·가입 주소에서만 예외(`haven-sqli-body-except-auth`) | `2026-11-20_AWS_05.md`, `_07.md` |
| XMP 메타데이터가 든 정상 PDF 업로드 | `CrossSiteScripting_BODY` | 그룹은 Block, 첨부 업로드 주소에서만 예외(`haven-xss-body-except-upload`) | `2026-11-20_AWS_05.md`, `_08.md` |

- `NoUserAgent_HEADER`는 **Count 유지(조장 결정 11/20, 이유: 점검 스크립트 미확인)**.
- 예외 주소에서도 SQLi 공격은 `SQLiExtendedPatterns_BODY`가 막는다. 업로드의 XSS는 앱이 화면에서 이스케이프한다(SEC-14).

**결과 해석의 한계**

- **정리 확인은 HTTP 수준이다.** 시험이 만든 글·공유·첨부는 상세 주소 404로 확인했고, DB 행·저장 파일의 물리 삭제는 확인하지 않았다.
- **WAF가 막지 못하는 것:** 본문 8KB 뒤 내용(ALB WAF 검사 한도), 주석형 `admin'--`, base64 직렬화 문자열, 업로드 파일 안의 XSS. 시험에서 모두 앱 검증(400·413·화면 이스케이프)이 막았다.
- **`NoUserAgent_HEADER` Count의 비용:** User-Agent 없이 온 해외 `.php`·`/.git/config` 탐색은 WAF를 통과한다. 앱 응답은 확인하지 않았다.
- **SEC-52:** CLI는 응답 본문을 저장하지 않는다. DEBUG 화면이 없다는 판단은 응답 크기와 헤더에 근거한다.
- **SEC-21:** `?user_id=` 같은 쿼리 문자열은 보내지 않았고, 본문 필드로만 확인했다.
- **UP-12:** 문자열 검색이라 목록에 없는 형태의 정보는 찾지 못한다. 오류 상황은 그 구간의 거부 응답까지만 포함한다.
- **AWS에서 뺀 업로드 시험:** 운영 관리자 업로드 거부(관리자 계정 미준비 당시), 계정 용량 시험(운영 계정 기존 사용량을 알 수 없음). 로컬 결과만 있다(`2026-11-19_AWS_02.md` 2절).
- **SEC-53:** WAF 로그 `matchedData`에 본문 조각(로그인이면 비밀번호 일부)이 남는다. WAF 로그 가리기는 헤더·URI·쿼리만 지원한다. 그래서 보관 30일, 조회 권한을 필요한 담당자로 제한, 분석 때 `matchedData`를 옮기지 않는 것으로 대응한다(판단안 7절).

## 7. 시험 설계 변경과 가림

**로컬 → AWS 변환에서 바꾼 것** (`2026-11-19_AWS_01·02.md` 2절)
