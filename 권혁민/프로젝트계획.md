# PROJECT 3 — 클라우드 보안 및 암호화 통합 프로젝트 구축 계획

## 1. 프로젝트 개요

### 1.1 목표

AWS에 웹 애플리케이션과 데이터 저장 환경을 구축하고, IAM·네트워크 접근 통제·WAF/침입 탐지·데이터 암호화·PKI/TLS를 적용한다. 마지막으로 정상 사용자와 비인가 사용자의 접근 결과, 공격 탐지, 보안 정책 개선 전후의 결과를 검증한다.

### 1.2 전제 및 범위

- **웹 서비스 주제와 업무별 세부 기능은 추후 결정한다.** 현재는 공통 모듈과 인프라만 정한다.
- 프론트엔드, 백엔드, 데이터베이스를 갖춘 **실제 동작하는 최소 웹 서비스**는 필요하다. 단, 어떤 도메인(문서·쇼핑몰·그룹웨어 등)을 택할지는 보류한다.
- 운영 자격 증명·개인정보는 테스트용으로 취급하고, 실제 비밀키와 비밀번호를 저장소에 올리지 않는다.
- AWS 관리형 서비스는 **AWS가 제공**하지만 구성, 정책, 연동, 검증은 **팀이 수행**한다.
- 30일 내 완성을 위해 **필수(Must)** / **권장(Should)** / **추가(Could)** 로 우선순위를 구분한다.

### 1.3 기본 아키텍처(논리 구조)

```text
인터넷 사용자 / 테스트 클라이언트
                │ HTTPS
                ▼
        [ALB + AWS WAF]
                │
                ▼
       [EC2: 웹 / 백엔드]
           │          │
           ▼          ▼
 [RDS MySQL]      [S3: 파일/객체]    ← 업무 기능에 따라 선택
 [Private DB]          │
                       └── [AWS KMS: 키 관리]

[EC2 IAM Role] → AWS API 접근 권한 제어
[CloudTrail]   → AWS API 활동 감사
[CloudWatch]  → 앱/인프라/WAF 로그·지표
[Suricata IDS] → 별도 실습 트래픽 관측 환경(권장)
[OpenSSL CA]   → 실습용 PKI/인증서 검증 환경
```

- ALB, DB, 애플리케이션을 적절한 서브넷 및 보안 그룹으로 분리한다.
- S3, KMS, CloudWatch는 VPC 내 서버가 아니라 **AWS 관리형 서비스**다.
- **AWS WAF는 EC2에 직접 부착할 수 없으며** ALB 또는 CloudFront 등 지원 리소스와 연결해야 한다.
- RDS의 프라이빗 연결, EC2에서 AWS 서비스 호출을 위한 아웃바운드 경로(필요시 VPC Endpoint 또는 NAT)까지 설계한다.
- 실제 서비스 종류에 따라 S3는 필수가 아닐 수 있다. 다만 S3 접근 통제·암호화 실습용 객체 저장소로 활용할 수 있다.

## 2. AWS 제공 영역과 직접 수행 영역

### 2.1 AWS 서비스 기반 구성

| 구분 | AWS가 제공하는 것 | 팀이 직접 수행할 작업 | 우선순위 |
|---|---|---|---|
| 서버 | EC2 가상 서버 | OS 초기 설정, 보안 설정, 웹/백엔드 배포 | Must |
| 네트워크 | VPC, Subnet, Route Table, IGW | 네트워크 분리 및 라우팅 설계 | Must |
| 트래픽 제어 | Security Group, NACL | 최소 개방 포트와 허용 출발지 정책 | Must |
| 데이터베이스 | RDS MySQL(관리형) | 스키마, 테이블, 계정 권한, 연결 테스트 | Must (RDS 또는 EC2 DB) |
| AWS 권한 | IAM User/Group/Role/Policy | 최소 권한 정책, 역할 분리, 허용·거부 실험 | Must |
| 웹 공격 방어 | AWS WAF | Web ACL 연결, 규칙 선택, 탐지·차단 검증 | Must (또는 직접 WAF 구축) |
| TLS 인증서 | ACM | 도메인 검증, HTTPS 리스너 연결 | Should (공개 HTTPS 경로) |
| 키 관리 | KMS | 키 생성·정책 설정, 앱 암호화 연동 | Should (키 분리는 Must) |
| 로그·감사 | CloudTrail, CloudWatch | 로그 수집/보존, 검색·알림·분석 | Must (필요 범위) |
| 객체 저장소 | S3 | 버킷 정책, 비공개 설정, 앱/실습 연동 | Should |
| 로드 밸런서 | ALB | EC2 Target Group, 리스너, WAF 연결 | Should (AWS WAF 사용 시 권장 경로) |
| 설정 검사 | Config, Security Hub 등 | 점검 항목 선정, 정책 해석, 검증 | Could |

> **선택:** RDS 대신 EC2 직접 MySQL 설치 가능. AWS WAF 대신 Nginx/ModSecurity+CRS로 직접 WAF를 구성하는 선택도 가능하지만, 선택한 방식의 탐지·차단 결과는 필수로 검증한다.

| 기능 영역 | 팀 구현 내용 | 우선순위 |

| 애플리케이션 인증 | 로그인, 로그아웃, 비밀번호 안전 저장, 세션 관리 | Must |

| 데이터 암호화 | 검증된 라이브러리로 민감 데이터 AES-GCM 등 암·복호화 | Must |
| 키 분리 | 키를 코드·Git에서 분리, 생성·사용·저장·접근 절차 명시 | Must |
| 자체 PKI 실습 | OpenSSL CA 생성, 서버 인증서 발급·검증 | Must |
| HTTPS | 웹 접속 TLS 적용, 인증서 유효성 검사 | Must |
| 네트워크 자동점검 | Boto3로 개방 포트·과도한 SG 규칙 검사 및 결과 출력 | Should (기본 도전 과업) |
| 보안 이벤트 화면 | 탐지 결과·접근 거부·감사 로그 요약 표시 | Should |
| 침입 탐지 | Suricata/동등 IDS 설치, 실제 보이는 트래픽의 탐지 확인 | Should |

| IaC/CI | Terraform, GitHub Actions 등 자동화 | Could |

### 2.3 오해하기 쉬운 경계

1. **IAM vs 웹 로그인:** IAM은 AWS 리소스/API 접근 제어, 앱 로그인/RBAC는 웹 사용자와 업무 데이터 접근 제어다. 서로 대체되지 않는다.
2. **WAF vs 안전한 코드:** WAF가 SQLi/XSS 패턴을 차단하더라도 서버의 파라미터 바인딩·출력 인코딩·권한 검사는 반드시 구현한다.
3. **암호화 vs 비밀번호 저장:** 복호화할 필요가 없는 비밀번호는 Argon2id 등으로 *해시*하고, 복호화가 필요한 민감 데이터만 대칭 암호화한다.
4. **ACM vs 자체 CA:** 공개 서비스는 ACM 등의 공인 인증서, PKI 과제에서는 별도의 OpenSSL 실습용 CA를 사용한다. 자체 CA 인증서는 기본적으로 일반 브라우저가 신뢰하지 않는다.
5. **IDS 관측 범위:** EC2에 설치한 Suricata가 AWS VPC 전체 트래픽을 자동으로 보는 것은 아니다. 패킷을 실제 관측할 수 있는 실습 경로에서 시험한다.

## 3. 필수 개발 기능 명세(서비스 불문)

### 3.1 공통 사용자·인증·인가

- [ ] 사용자 계정 생성 또는 관리자가 발급하는 계정 등록
- [ ] 로그인/로그아웃 및 안전한 세션 처리
- [ ] 비밀번호 해시 저장 및 로그인 실패 처리
- [ ] 일반 사용자/관리자 역할 정의
- [ ] API마다 인증 여부 및 접근 권한 검증
- [ ] 권한 없는 사용자에 대한 401/403 응답 검증
- [ ] 중요 작업·로그인 실패·권한 거부에 대한 감사 로그
- [ ] 관리자 화면(사용자/역할/감사 로그 조회의 최소 기능)

### 3.2 애플리케이션 기반 기능(주제 결정 후)

- [ ] 사용자에게 보여줄 핵심 업무 화면 2~4개 정의
- [ ] 핵심 업무 엔터티 2~4개 및 CRUD API 정의
- [ ] 사용자별 소유권/공유 범위 등 자원별 인가 규칙 정의
- [ ] 데이터 입력 검증, 에러 처리, 검색/조회/수정 흐름 구현
- [ ] 민감 데이터 선정 및 암호화 적용 지점 명시

> 문서 관리, 쇼핑몰, 그룹웨어 등 **구체적 업무 로직은 추후 결정**. 공통 보안 기능부터 구현 가능하도록 인터페이스를 분리한다.

### 3.3 공통 데이터베이스 초안

| 테이블 | 핵심 필드(예시) | 역할 |
|---|---|---|
| `users` | id, email, password_hash, status, created_at | 로그인 계정 |
| `roles` | id, name | 앱 역할 |
| `user_roles` | user_id, role_id | 사용자-역할 연결(다중 역할일 때) |
| `sessions` | id, user_id, expires_at, revoked_at | 서버 측 세션 관리(선택 구현) |
| `audit_logs` | id, actor_id, action, resource_type, resource_id, result, created_at | 앱 감사 기록 |
| `security_events` | id, event_type, severity, source, metadata, created_at | 탐지·차단 이벤트 정규화 |
| `protected_records` | id, owner_id, ciphertext, nonce, key_ref | 암호화 검증용 데이터(실습 또는 업무 엔터티) |

- 업무별 테이블은 주제 결정 후 추가한다.
- 로그와 데이터 레코드에는 최소한의 정보만 저장하고, 비밀번호·토큰·원본 암호키는 기록하지 않는다.
- 개인 데이터 접근 통제는 앱 서버에서 구현한다. AWS IAM 정책만으로 웹 사용자별 데이터를 분리하지 않는다.

| GET | `/api/security/events` | 보안 이벤트 조회 |
| POST | `/api/protected-records` | 암호화 저장 실습 |
| GET | `/api/protected-records/{id}` | 권한 검사 후 복호화 실습 |
| ... | `/api/<업무리소스>` | 주제 확정 후 추가 |

## 4. 가이드 단계별 구성·검증·산출물

### 기본 1 — AWS 환경 구축 및 서비스 확장

- **구성:** EC2, Web/API, MySQL(RDS 또는 EC2), 필요시 S3/ALB.
- **검증:** 외부 HTTPS 접속, 앱 API/DB 연동, 서버 재시작 후 기능 정상 동작.
- **도전:** 도메인 연결, DNS 및 외부 서비스 연동.
- **산출물:** AWS 인프라 구성도, 구축 내역, 웹/DB 연동 화면, 접속 테스트.

### 기본 2 — IAM 사용자 및 권한 관리

- **구성:** 관리자·개발자·보안 담당·감사 담당 IAM 권한 구분, EC2 Role 사용.
- **검증:** 허용 API 성공, 거부 API `AccessDenied`, 불필요한 `*` 권한 점검.
- **도전:** IAM Access Analyzer 등을 이용해 과도한 권한 개선.
- **산출물:** 역할별 권한표, IAM 정책 JSON, 허용/거부 테스트, 개선 보고서.

### 기본 3 — 네트워크 보안 및 접근 통제

- **구성:** VPC, 퍼블릭·프라이빗 서브넷, SG, 라우팅, DB 외부 접근 차단.
- **검증:** HTTPS 허용, 비인가 SSH/DB 접근 차단, 앱→DB 연결 허용.
- **도전:** Boto3로 `0.0.0.0/0`, `::/0` 및 과도한 개방 규칙 자동점검.
- **산출물:** 네트워크 구성도, SG 규칙표, 접속 테스트, 자동점검 코드·결과.

### 기본 4 — 보안 장비 및 정책 고도화

- **구성:** AWS WAF 또는 직접 WAF; Suricata IDS(권장), 로그 수집.
- **검증:** SQLi/XSS 테스트 입력, 요청 제한, 정상 요청 오탐, 탐지·차단 로그 대조.
- **도전:** 정책 변경 전후 탐지율·차단율·오탐률 비교.
- **산출물:** 보안 장비 설정, 탐지 로그, 정책 및 개선 결과.

### 심화 1 — 데이터 암호화 및 키 관리

- **구성:** 보호 데이터 선정, AES-256-GCM 등 검증된 라이브러리, 키 분리 및 KMS 연동(권장).
- **검증:** 암호화→저장→복호화 동일성, 위변조 검증 실패, 권한 없는 복호화 거부.
- **도전:** 데이터 크기별 암호화·복호화 성능 비교.
- **산출물:** 암호화 코드, 키 관리 구조, 정상/오류 검증 결과.

### 심화 2 — PKI 및 TLS

- **구성:** OpenSSL 자체 CA 및 서버 인증서 발급, 웹 서비스 HTTPS.
- **검증:** 인증서 체인·호스트명·유효기간 검사, HTTPS 연결 및 HTTP 전환 확인.
- **도전:** 만료 예정 인증서 점검·알림.
- **산출물:** PKI 구성도, 발급 인증서(개인키 제외), HTTPS 설정 및 검증 기록.

### 심화 3 — 인증·인가와 데이터 보호 통합 검증

- **구성:** 앱 인증·인가, AWS IAM, WAF, 암호화, HTTPS 통합.
- **검증:** 정상·비정상 권한 접근, 파일/레코드별 접근 거부, DB 암호문 확인, 보안 로그 상관 분석.
- **도전:** 내부 API 간 mTLS.
- **산출물:** 최종 시스템 구성도, 테스트 매트릭스, 로그/시연 화면, 개선 전후 보고서.

## 8. 개발·운영 공통 원칙

1. **인증·인가:** 모든 보호 API에서 서버 측 검증. UI에서 메뉴를 숨기는 것만으로 권한 통제하지 않는다.
2. **비밀정보:** AWS Access Key, DB 비밀번호, 암호화 키를 소스·로그·Git에 저장하지 않는다. EC2는 IAM Role을 사용한다.
3. **로그:** 민감한 원문·비밀번호·토큰을 기록하지 않는다. 테스트마다 식별 가능한 요청 ID를 사용한다.
4. **DB:** 외부 공개 금지, 최소 권한 DB 계정, 백업/복구 절차 확인.
5. **암호화:** 자체 알고리즘 구현 금지, 검증된 라이브러리와 AEAD 방식 사용, 키와 암호문 분리.
6. **서비스 간 통신:** 외부 접속 HTTPS, 내부 통신의 암호화 필요성도 평가.
7. **보안 점검:** 취약 설정은 격리된 테스트 리소스에서 의도적으로 만들고 테스트 후 즉시 되돌린다.
8. **변경 관리:** Git 브랜치 및 리뷰, 인프라 변경 이력, 재현 가능한 실행 절차 기록.
9. **비용 관리:** 초기부터 AWS Budgets 알림, 리소스 태그, 종료/정리 체크리스트 관리. ALB·RDS·NAT·WAF·공인 IPv4 등 과금 확인.

## 10. 추후 결정할 사항

웹 서비스 주제를 정하기 전까지 아래 항목만 미정으로 둔다.

- [ ] 웹 서비스 유형 및 핵심 사용자 업무 시나리오
- [ ] 업무 데이터 엔터티 및 추가 DB 테이블
- [ ] 업무 API와 화면 목록
- [ ] 저장 대상 데이터의 민감도 및 구체적 암호화 필드
- [ ] S3 파일 저장 필요 여부
- [ ] AWS WAF vs ModSecurity, RDS vs EC2 MySQL 선택
- [ ] 예산 상한 및 도메인/인증서 확보 방식
- [ ] 팀원 기술 숙련도에 맞는 프론트/백엔드 스택 확정

**우선 구현할 공통 골격:** AWS 네트워크/서버 + 웹/API/DB 기본 연결 + 인증/인가 + IAM 최소 권한 + WAF 탐지 + 감사 로그 + 데이터 암호화 + PKI/TLS + 통합 검증.

이 공통 골격을 먼저 구축하면 이후 어떤 웹 서비스 주제를 선택하더라도 업무 기능만 추가하면서 보안 프로젝트 목표를 유지할 수 있다.
