
# Haven 프로젝트 IAM 권한 설계 (1차 초안)

## 1. 작업 목적
AWS 팀 프로젝트에서 담당자별 필요한 권한만 부여하고, 승인되지 않은 작업은 제한하여 안전하게 운영한다.

## 2. 팀원별 IAM 권한

| 담당자 | 필요한 권한 |
|---|---|
| 이민성 | VPC, EC2, 보안그룹, NAT, ALB 구축 및 관리 |
| 안민수 | Web·DB 서버 SSM 접속, 배포 및 승인된 백업·복원 |
| 권혁민 | 보안그룹·로그·WAF 조회 및 승인된 보안 시험 |
| 김보람 | IAM 사용자·Role 관리 및 예산·비용 조회 |
| 신요찬 | 현재 AWS 콘솔 권한 불필요 |
| 노푸른 | 현재 AWS 콘솔 권한 불필요 |

모든 권한은 담당 업무에 필요한 최소 범위로 제한하며, MFA 사용을 원칙으로 한다.

## 3. EC2 서버 Role 설계 및 현재 적용 상태 (2026-11-09)

| 대상 | 확정 이름 | 권한 및 상태 |
|---|---|---|
| Web·DB 공통 EC2 역할 | `haven-ec2-ssm-role` | AWS에 생성 완료. `AmazonSSMManagedInstanceCore`, `/haven/*` SSM 읽기, S3 백업·복원 인라인 정책 연결 |
| EC2 인스턴스 프로파일 | `haven-ec2-ssm-profile` | AWS에 생성하고 위 공통 역할 연결 확인 |
| Web 로그 정책 초안 | `04_Web_Logs_Policy.json` | **예전 초안(실제 적용본 아님).** 11/11 `haven-ec2-ssm-role`에 적용한 웹 로그 쓰기 정책 기록은 `22_EC2_Web_CloudWatch_Write_Policy.json`. 실제 로그 전송 시험은 민성 담당 |
| DB 로그 정책 초안 | `05_DB_Logs_Policy.json` | GitHub JSON 초안. AWS 실제 적용/시험 미확인 |

- Web·DB는 현재 **같은 역할**을 사용할 예정이므로 S3 백업 권한도 두 서버에 공통으로 부여된다. 보안상 분리 필요 여부는 검토 사항이다.
- S3 백업·복원 권한을 역할에 연결했지만 **버킷 생성과 실제 백업·복원 성공은 아직 미검증**이다.
- SSM 비밀값 및 액세스 키 원문은 GitHub에 올리지 않는다.

## 4. 이민성 담당자 권한

- 승인된 네트워크 및 EC2 자원 생성·관리
- `iam:PassRole`은 `haven-ec2-ssm-role` **하나에만**, `iam:PassedToService=ec2.amazonaws.com` 조건으로 허용(민성 IAM 사용자에 AWS 실제 연결 완료)
- 승인되지 않은 IAM Role 전달 및 IAM 관리자 권한 부여 제한

## 5. 허용·거부 시험 계획

- 승인된 운영자 → 지정 서버 SSM 접속 성공
- 일반 계정 → SSM 접속 거부
- EC2 → 필요한 로그 전송 성공
- DB 서버 → 지정된 S3 백업 경로 쓰기 성공
- DB 서버 → 다른 S3 버킷 및 허가되지 않은 작업 거부
- 이민성 → 승인되지 않은 Role 전달 거부


## 6. IAM 작업 계획 및 완료 기준

**완료 목표: 2026년 11월 11일(수) 서버 구축 전까지**

- 팀원별 담당 업무에 맞는 IAM 정책 JSON 작성
- Web·DB 서버용 IAM Role 및 정책 JSON 작성
- 이민성 담당자의 `iam:PassRole` 권한 범위 설정
- SSM 접속 허용·거부 대상 구분
- CloudWatch 로그 전송 및 S3 백업 권한 설정
- 이민성 담당자와 Role 이름 및 권한 범위 확인
- 확정된 IAM 권한을 AWS에 적용하고 가능한 허용·거부 시험 진행
- 적용 결과와 미검증 항목을 기록하여 이민성 담당자에게 전달

**완료 기준:** 서버 구축에 필요한 IAM 권한을 적용하고, 서버 생성 전에 검증 가능한 항목을 확인한다. 실제 서버가 필요한 SSM 접속 및 로그·백업 시험은 서버 구축 후 진행한다.

**현재 상태(2026-11-10):** `Haven-Minsung-Infra-Policy`를 `minsung` 사용자에게 실제 연결 확인. EC2 시작·중지 권한 기존 포함 및 SSM 인스턴스 조회 권한 추가. IAM 시뮬레이터의 EC2 조회·PassRole 허용/거부 총 4개 결과 확인. `minsoo`의 Session Manager 인라인 정책 추가 연결, S3 백업 버킷 생성 확인. **실제 CLI/서버/백업 시험은 각 담당자 확인 대기**. 상세 기록은 [2회차](../1~4회차/2회차.md) 참조.

계정 ID와 자원 ARN은 추후 계정 이전이 가능하도록 변수로 관리한다.


## 7. 11/10 설정 추가 및 보안 검증 유의사항

- `minsung`의 `ec2:StartInstances`, `ec2:StopInstances`는 서울 리전 `Project=Haven` 및 `Owner=minsung` 조건이 모두 일치해야 허용되도록 기존 정책에 포함. `ssm:DescribeInstanceInformation`도 추가함.
- `minsoo`는 `Haven-Minsoo-SessionManager-Policy` 생성·연결. 서버 접속은 Project=Haven 태그로 제한하고, 세션 종료/재개는 자기 세션만 대상으로 하는 설계. 기존 파라미터 읽기·쓰기 정책과는 별개.
- IAM 정책이 저장되어도 실제 서비스 동작 성공을 뜻하지 않으므로 민성·민수의 IAM 사용자 로그인 및 서버별 허용/거부 결과를 받아 확인할 것. 특히 SSM Session Manager의 세션 문서 ARN, 조건 키, 세션 ID 평가 여부 확인 필요.
- S3 버킷 `haven-backup-${ACCOUNT_ID}` (서울, 퍼블릭 차단, SSE-S3) 생성 완료. 공통 Role은 `db-backups/*`에 PutObject/GetObject; 실제 업로드·복원은 미검증.
- **GitHub의 `${ACCOUNT_ID}` 자리 표시자 정책은 실제 AWS 연결 정책과 구별**하여 사용. 계정 이식 시 치환 필요. AWS 액세스 키·비밀번호·비밀 파라미터 값은 기록하지 않음.

## 8. GitHub IAM JSON 사용 방법

- `김보람/JSON/` 폴더의 IAM 정책 JSON은 **공유·검토용 템플릿**이며, 그대로 AWS에 붙여넣는 적용본이 아니다.
- `${ACCOUNT_ID}`는 실제 AWS 계정 번호가 아닌 자리 표시자다. AWS에 적용하기 전에 **해당 AWS 계정의 12자리 번호로 치환**해야 한다.
- `<default SG ID>`처럼 표시된 자원 ID도 실제 적용 대상 ID로 바꿔야 한다.
- 치환 후 JSON 형식과 ARN·권한 범위를 확인하고 AWS에 적용한다. 실제 AWS에 저장된 정책은 GitHub 템플릿과 구분해 관리한다.
