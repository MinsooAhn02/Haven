## 7. UP-13 업로드 도중 끊김 (11/10 오후 보강)

명세 UP-13: "비로그인/CSRF 실패/중단 multipart와 임시 디스크 — 영구/ACTIVE 파일 없음, 프레임워크 임시 파일이 정리되거나 만료 정리 대상".

**찾은 결함:** 실제 서버(`runserver`, `haven_app`)에 2 MiB 가까이 보내다가 TCP RST로 강제로 끊으면 `.incoming/upload-*.tmp`가 남았다. 이후 정상 요청을 해도 지워지지 않았다. Django는 파싱 중 오류가 나면 다 받은 파일만 닫고 **받는 중이던 임시 파일은 열린 채로** 둔다. 실제 서버에서는 오류 기록이 요청 객체를 붙잡고 있어 메모리 정리 때까지 파일이 남는다. 행·영구 파일은 없었고 `cleanup_attachments`가 만료 후 지우므로 명세 기준은 통과였지만, 바로 지우도록 고쳤다.

**수정:** 업로드 경로에만 쓰는 파서 래퍼(`_strict_parse_file_upload`)에서 파싱이 실패하면 처리기의 `upload_interrupted()`를 불러 임시 파일을 닫고 지운 뒤 오류를 다시 낸다.

**시험 도구 함정:** Django 시험 도구는 본문 인자를 비우면 `Content-Type`을 붙이지 않는다. 처음 쓴 끊김 시험은 이 때문에 업로드로 인식되지 않아 **아무것도 확인하지 않고 통과**했다. 수정을 뺀 코드로 돌려 보고 알아냈으며, `CONTENT_TYPE`을 직접 넣고 요청 객체를 붙잡은 상태에서 확인하는 시험을 더해 수정을 빼면 4건 모두 실패하는 것을 확인했다(A31).

실제 서버 (`haven_app`, `DJANGO_DEBUG=0`, 빈 업로드 폴더, 소켓으로 일부만 보내고 끊음):

| 경우 | 기대 | 결과 |
|---|---|---|
| 로그인+토큰, 1 MiB 선언 중 600 KiB 보내고 정상 종료 | 행·저장 파일·임시 파일 없음 | 일치 |
| 로그인+토큰, 2,100,000 선언 중 2,097,000 보내고 **RST** | 같음 | 수정 전 **임시 파일 1개 남음** → 수정 후 일치 |
| 로그인, 토큰 없음, 절반에서 끊음 | 같음 | 일치 |
| 비로그인, 절반에서 끊음 | 같음 | 일치 |
| 헤더만 보내고 끊음 | 같음 | 일치 |
| 끊긴 요청들 뒤 정상 업로드 | 302, 첨부 1개, 임시 파일 없음 | 일치 |
