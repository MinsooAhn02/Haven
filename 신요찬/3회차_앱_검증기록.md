## 7. UP-13 업로드 도중 끊김 (11/10 오후 보강)

명세 UP-13: "비로그인/CSRF 실패/중단 multipart와 임시 디스크 — 영구/ACTIVE 파일 없음, 프레임워크 임시 파일이 정리되거나 만료 정리 대상".

**찾은 결함:** 실제 서버(`runserver`, `haven_app`)에 2 MiB 가까이 보내다가 TCP RST로 강제로 끊으면 `.incoming/upload-*.tmp`가 남았다. 이후 정상 요청을 해도 지워지지 않았다. Django는 파싱 중 오류가 나면 다 받은 파일만 닫고 **받는 중이던 임시 파일은 열린 채로** 둔다. 실제 서버에서는 오류 기록이 요청 객체를 붙잡고 있어 메모리 정리 때까지 파일이 남는다. 행·영구 파일은 없었고 `cleanup_attachments`가 만료 후 지우므로 명세 기준은 통과였지만, 바로 지우도록 고쳤다.

**수정:** 업로드 경로에만 쓰는 파서 래퍼(`_strict_parse_file_upload`)에서 파싱이 실패하면 처리기의 `upload_interrupted()`를 불러 임시 파일을 닫고 지운 뒤 오류를 다시 낸다.

**시험 도구 함정:** Django 시험 도구는 본문 인자를 비우면 `Content-Type`을 붙이지 않는다. 처음 쓴 끊김 시험은 이 때문에 업로드로 인식되지 않아 **아무것도 확인하지 않고 통과**했다. 수정을 뺀 코드로 돌려 보고 알아냈으며, `CONTENT_TYPE`을 직접 넣고 요청 객체를 붙잡은 상태에서 확인하는 시험을 더해 수정을 빼면 4건 모두 실패하는 것을 확인했다(A31).

실제 서버 (`haven_app`, `DJANGO_DEBUG=0`, 빈 업로드 폴더, 소켓으로 일부만 보내고 끊음):

| 경우 | 기대 | 결과 |
|---|---|---|
| 로그인+토큰, 1 MiB 선언 중 600 KiB 보내고 정상 종료 | 행·저장 파일·임시 파일 없음 | 일치 |
| 로그인+토큰, 2,100,000 선언 중 2,097,000 보내고 **RST** | 같음 | 수정 전 **임시 파일 1개 남음** → 수정 후 일치 |
| 로그인, 토큰 없음, 절반에서 끊음 | 같음 | 일치 |
| 비로그인, 절반에서 끊음 | 같음 | 일치 |
| 헤더만 보내고 끊음 | 같음 | 일치 |
| 끊긴 요청들 뒤 정상 업로드 | 302, 첨부 1개, 임시 파일 없음 | 일치 |

## 10. 권혁민 리뷰 반영: 정리 명령 동시성 (11/11 오전)

권혁민 #38 리뷰(11/11 09:52)의 "파일 정리 동시성" 두 가지를 반영했다. 둘 다 코드에서 실제로 확인되는 빈틈이었다.

| 지적 | 확인한 원인 | 고친 것 |
|---|---|---|
| 오래된 PENDING 정리가 삭제 직전 상태를 다시 보지 않음 | `cleanup_attachments`가 목록을 읽은 뒤 `purge()`가 `pk`만으로 파일·행을 지웠다. 목록을 읽은 뒤 업로드가 ACTIVE가 되면 "업로드 성공" 응답을 받은 파일이 지워질 수 있었다. 업로드가 기준 시간(60분)보다 오래 멈춰 있어야 생기는 상황이라 가능성은 낮다 | `purge()`가 행을 `select_for_update`로 잠그고 상태(와 PENDING이면 생성 시각)를 다시 확인한다. 맞지 않으면 건너뛴다(`skipped`). 잠금을 잡은 동안 업로드의 `activate()`는 같은 행에서 기다렸다가, 행이 지워졌으면 실패(404)로 끝난다 |
| `--delete-orphans`가 막 올라온 파일을 고아로 볼 수 있음 | 행 목록을 먼저 읽고 폴더를 훑어서, 그 사이에 생긴 업로드 파일은 목록에 없었다 | 기준 시간보다 오래된 파일만 지우고, 지우기 직전에 같은 저장키의 행이 생겼는지 다시 확인한다. 업로드는 행을 먼저(reserve) 만들고 파일을 나중에(store) 만들어서, 지우기 직전에 확인하면 업로드 중인 파일을 잘못 보지 않는다 |

| 명령 성공 | `SES 접수 message_id=…`, 받는 주소는 `v***@…`로만, "실제 도착은 받은 편지함에서 확인", 출력·로그에 주소 원문 없음 |
| 명령 실패 (EXT-04) | `MessageRejected`(문구에 주소 포함) → 종료 코드 1, "접수" 출력 없음, 오류 원문·주소 없음 |
| 접수 ID 없음 | SES 응답에 MessageId 없음 → 실패 / 다른 백엔드가 "1통"이라고만 함 → 실패 |
| 잘못된 주소 | 형식 오류, `@` 두 개, 줄바꿈 넣은 헤더 주입, 빈 값 → 보내기 전에 실패 |

### 12-7. 남은 것

- **실제 발송·수신(EXT-03)과 실패 표시(EXT-04)는 미실행**이다. 서버에서 확인한다(11/12 신요찬·김보람). 필요한 것: 발신 주소 확정(E6), 김보람 Web Role `ses:SendEmail`(SES 도메인 `orchestration-haven.cloud` 인증은 11/11 완료, #58), 이민성 서버 `boto3`(E5)·환경 파일.
- 확인할 것(`공통실행.md`): `send_test_mail --to <승인된 가상 수신처>`로 ① API 성공 ② 메시지 식별자 ③ 수신함 실제 도착을 따로 기록. 인증 안 된 주소로 보내 실패가 성공으로 표시되지 않는지 확인. 반복 발송·실사용자 주소는 쓰지 않는다.
