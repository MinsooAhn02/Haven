### 1-1. EXT-04 오류 코드가 `MessageRejected`가 아닌 이유

- 재시험 때 28번 정책의 Resource는 발신 도메인 identity와 **등록한 받는 주소 identity**뿐이다(민성 기록). 위 첫 시도에서 본 것처럼 sandbox에서는 받는 주소 identity 권한도 검사하는 것으로 보이므로, 등록 안 한 주소(`nobody@example.invalid`)는 sandbox 규칙(`MessageRejected`)까지 가기 전에 SES의 **권한 검사에서** `AccessDeniedException`으로 거부됐다.
- 명세의 핵심인 "실패를 성공으로 표시하지 않음"은 확인됐다(안내서 기준: 실패로 표시되면 통과, 코드만 기록).
- 등록 안 한 주소로의 발송을 권한 정책이 막는다는 것도 확인됐다(최소 권한 동작).
- **실환경에서 시험하지 못한 것:** SES의 `MessageRejected` 경로. 앱에서는 `accounts/tests/test_mail.py`가 `MessageRejected`를 흉내 내 실패 표시·주소 미노출을 시험한다(90·174행). 지금 권한 구성으로는 실환경에서 이 경로가 나오기 어렵다.

## 2. 운영 사이트 권한 대조: 공유받은 사용자의 업로드 직접 요청 (구민철)

조장이 "시험 계정(test1·test2)과 시험 글에만, 작은 TXT 한 번, 거부되는지만, 성공하면 즉시 보고·삭제" 조건으로 허용한 시험. 결과는 구민철 2회차 첨부·공유 보고서 6장(#101 `10e66c1`, 보강 #105 `f79f15d`).

| 항목 | 내용 |
|---|---|
| 시각·배포 | 11/13 15:24 KST(공유 15:19), 운영 `a7bfcd6` |
| 상황 | test1 글 `/posts/10/`(첨부 시험2)을 test2에게 읽기 공유. test2 화면에는 업로드 칸 없음 |
| 요청 | test2 로그인 상태, 브라우저 Console `fetch`로 `/posts/10/attachments/`에 POST 1회(13바이트 TXT, 화면의 CSRF 토큰 포함) |
| 기대(앱계약) | 404(소유자 아님), 첨부 저장 안 됨 |
| 실제 | **404**, 요청 뒤에도 첨부 없음 |

- **판정: 결함 없음.** 403이 아니라 404이므로 CSRF 검사는 통과했고, 서버가 "소유자 아님"으로 거부했다. 화면에서 버튼을 숨긴 것만이 아니라 서버가 권한을 직접 검사한다.
- 앱 자동 시험과도 일치: `posts/tests/test_attachments.py` `test_up06_recipient_and_others_cannot_change`가 공유받은 사람·다른 회원·운영자의 업로드 POST와 첨부 삭제를 모두 404로, 첨부 상태·저장 파일이 그대로인지 확인한다.
- 참고: 허용 조건에는 대상 글이 `/posts/7/`로 적혀 있었으나 실제 시험은 같은 시험 계정의 `/posts/10/`에서 했다(용량·업로드 권한 시험용 글). 시험 계정·1회·TXT·거부 확인이라는 조건은 지켰다.
