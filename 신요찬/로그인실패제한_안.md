# 로그인 실패 제한 안 (앱계약 8장 13번)

작성: 신요찬 · 2026-11-12 · 상태: **확정** (#75, 2026-11-12 이민성. 계정 기준만 10번 → 5번으로 변경)
근거: 기본프로젝트_구현명세 1장("계정과 출발지의 두 축을 시험하고 영구 잠금은 사용하지 않는다. WAF IP 빈도 제한만으로 계정별 로그인 방어를 완료하지 않는다"), 같은 문서 APP-10, 기본프로젝트_계획 "로그인 방어: 공개 전에 수치 확정(횟수/관찰창/회복/계정 열거/분산 실패 시험)", 조장 운영기록 11/12.

## 1. 한 줄 요약

**15분 안에 같은 아이디로 5번, 또는 같은 IP에서 30번 틀리면, 그 아이디나 IP의 로그인을 잠시 막는다.** 막힌 동안은 비밀번호를 확인하지 않고 같은 안내만 보여 준다. 시간이 지나면 저절로 풀리고, 영구 잠금은 없다.

## 2. 수치 (제안값과 조장 결정, 11/12 #75)

| # | 항목 | 제안값 | 조장 결정 | 이유 |
|---|---|---|---|---|
| 1 | 관찰 시간 | 최근 15분 | **최근 15분** (제안 그대로) | 사람이 오타를 내고 다시 시도하는 시간보다 충분히 길고, 막혀도 15분이면 풀린다 |
| 2 | 계정 축 (같은 아이디, IP 상관없이) | 실패 10번 | **실패 5번** → 그 아이디 로그인 거부 (10번에서 변경) | 정상 사용자가 15분에 5번 틀리는 일은 드물다. 공격자는 아이디 하나에 15분당 5번(하루 약 480번)만 시도할 수 있고, 비밀번호 정책(8자 이상, 흔한 비밀번호·숫자만 거부) 아래서 맞히기 어렵다 |
| 3 | 출발지 축 (같은 IP, 아이디 상관없이) | 실패 30번 | **실패 30번** → 그 IP 로그인 거부 (제안 그대로) | 여러 아이디에 흔한 비밀번호를 돌려 보는 공격(password spraying)을 막는다. 학교처럼 여러 명이 IP 하나를 같이 쓰는 곳에서 팀원들의 오타가 겹쳐도 막히지 않게 계정 축보다 크게 잡는다 |
| 4 | 회복 | 자동 | **자동** (제안 그대로). 최근 15분 실패 수가 기준 아래로 내려가면 다시 시도 가능(가장 오래된 실패가 15분을 넘길 때마다 한 번씩 풀리므로, 늦어도 마지막 실패 15분 뒤에는 모두 풀림) | 영구 잠금 금지(명세). 관리자가 풀어 줄 필요가 없다 |
| 5 | 막힌 동안의 시도 | 세지 않고, 비밀번호도 확인하지 않음 | **세지 않고, 비밀번호도 확인하지 않음** (제안 그대로) | 막힌 상태에서 맞는 비밀번호를 넣었을 때 결과가 달라지면, 공격자가 "맞았다"는 것을 알 수 있다. 세지 않으니 잠금이 끝없이 늘어나지도 않는다 |
| 6 | 로그인 성공 | 계정 축 기록만 지움 | **그 아이디의 계정 축 실패 기록만 지움. IP 축은 그대로** (제안 그대로) | 한 IP에서 여러 아이디를 시도하다 하나가 맞아도 IP 축이 리셋되지 않게 |

정리하면, 공격자는 아이디 하나당 15분에 최대 5번, IP 하나당 15분에 최대 30번까지만 시도할 수 있다.

## 3. 사용자에게 보이는 것 (계정 존재 여부를 드러내지 않음)

| 상황 | 응답 | 문구 |
|---|---|---|
| 아이디·비밀번호 틀림, 없는 아이디, 비활성 계정 | **400** (지금과 같음) | "로그인할 수 없습니다. 아이디와 비밀번호를 확인해 주세요." |
| 제한에 걸림 (어느 축이든) | **429** (Too Many Requests), 같은 로그인 화면 | "로그인 시도가 너무 많습니다. 잠시 후 다시 시도해 주세요." |

- **없는 아이디도 똑같이 센다.** 그래서 없는 아이디와 있는 아이디의 반응(횟수, 응답 코드, 문구)이 같다. 제한 문구로는 아이디가 있는지 알 수 없다.
- 어느 축에 걸렸는지, 몇 분 남았는지는 알려 주지 않는다.
- 로그인 화면(`registration/login.html`)은 지금 쓰는 `form.non_field_errors`로 문구를 보여 준다. **화면 수정은 필요 없다.**
- 요청 로그 `action`에 `login_limited`(429)를 새로 남긴다. 기존 거부 표시 방식(`haven_log_action`)을 그대로 쓰고, `result`는 기존 규칙대로 `denied`가 된다. 로그 필드는 늘리지 않는다. 지금처럼 아이디·비밀번호·IP는 로그에 남기지 않는다.

## 4. 구현 방식 (앱, 요찬)

| 항목 | 방식 | 이유 |
|---|---|---|
| 실패 기록 위치 | **DB 테이블 `accounts.LoginFailure`**(축, 키, 시각) + migration 1개 | 서버의 Gunicorn worker가 3개라 메모리에 세면 worker마다 따로 센다. DB는 셋이 같이 본다 |
| 세는 실패 | 아이디·비밀번호를 둘 다 넣었고 인증이 실패한 경우만. 빈 칸 오류는 세지 않음 | 비밀번호를 확인하지 않은 요청은 추측 시도가 아니다 |
| 키 | 아이디는 **로그인 폼과 같은 방식으로 정리**(앞뒤 공백 제거, NFKC)한 뒤 대소문자를 무시하고, IP와 함께 **`SECRET_KEY`로 HMAC해서** 저장 | 로그인 폼은 `alice `, 전각 `ａｌｉｃｅ`를 `alice`로 바꿔 인증한다. 입력 원문으로 세면 이런 변형으로 계정 축을 피할 수 있다. HMAC은 아이디 칸에 비밀번호를 잘못 넣는 일이 있어 원문을 DB에 남기지 않기 위함 |
| 오래된 기록 | 기록할 때마다 15분 지난 행을 지움 | 테이블이 커지지 않게. 따로 정리 작업이 필요 없다 |
| 사용자 IP | 서버(`DJANGO_HTTPS=1`, ALB → Nginx 뒤)에서는 `X-Forwarded-For`의 **끝에서 두 번째** 값. 로컬은 `REMOTE_ADDR` | ALB가 실제 IP를 붙이고 Nginx가 ALB 주소를 붙이므로 끝 두 개만 믿을 수 있다. 공격자가 앞에 넣은 값은 무시된다. Web 80은 ALB 보안 그룹에서만 열려 있다(#51과 같은 전제). 값이 이상하면 `REMOTE_ADDR`를 쓴다. **전제: ALB의 X-Forwarded-For 처리 방식이 기본값(append)** — 콘솔 설정이라 repo에 없으므로 보람·민성 확인 필요. WSL 서버 시뮬레이션(`DJANGO_HTTPS=0`)에서는 모두 Nginx 주소 하나로 묶인다(알려진 한계) |
| 서버 설정 변경 | **없음** (`DJANGO_HTTPS`를 그대로 씀) | `deploy.sh`를 바꾸지 않아도 된다. migration은 배포 때 `haven_owner`로 자동 적용 |
| 동시 요청 | 같은 순간에 들어온 요청 몇 개(최대 worker 수 정도)는 기준을 넘어 처리될 수 있음 | 행 잠금까지 넣지 않는다. 5번이 7번이 되는 정도라 방어 효과는 같다. 따로 시험하지 않고 알려진 한계로 적는다 |

예상 작업량: 모델·migration, 판정 모듈, 로그인 view 수정, 시험 약 20개. 구현과 시험에 반나절~하루.

## 5. 시험 계획 (APP-10)

**로컬 (자동 시험, 시간은 가짜 시계로 당김)**

| 시험 | 기대 |
|---|---|
| 같은 아이디 4번 실패 → 5번째 실패 → 6번째는 **맞는 비밀번호여도** | 1~5번 400, 6번째 **429**, 로그인 안 됨 |
| 15분 지난 뒤 | 맞는 비밀번호로 로그인 302 |
| 막힌 동안 시도 50번 | 모두 429, 실패 수는 늘지 않음(15분 뒤 바로 회복) |
| 서로 다른 IP 5개에서 같은 아이디 1번씩 | 계정 축 걸림(분산 공격) |
| 한 IP에서 서로 다른 아이디 30개 | 31번째부터 그 IP 429, 다른 IP의 같은 아이디는 영향 없음 |
| 없는 아이디 vs 있는 아이디, 같은 횟수 | 응답 코드·문구·화면이 똑같음 |
| 아이디 변형(`alice `, `ALICE`, 전각 `ａｌｉｃｅ`)으로 섞어서 실패 | 모두 같은 아이디로 세져 5번에서 걸림 |
| 빈 아이디·빈 비밀번호 제출 | 400 폼 오류, 실패 수는 늘지 않음 |
| 성공 로그인 | 그 아이디 계정 축 기록만 지워짐 |
| `X-Forwarded-For` 앞에 가짜 IP를 넣음 | 무시하고 실제(끝에서 두 번째) IP로 셈 |
| 요청 로그 | `login_limited` 429가 남고, 아이디·비밀번호 원문은 어디에도 없음 |
| DB | 원문 아이디·IP 없음, 15분 지난 행 지워짐 |
| 일부러 실패시킨 거부 시험 | 축 하나 빼기, 막힌 동안 비밀번호 확인, 없는 아이디 안 세기, XFF 맨 앞 값 믿기 등 결함을 넣으면 시험이 잡는지 |

**실제 AWS (배포 뒤, 혁민 점검)**

팀원이 각자 다른 곳(다른 IP)에서 접속하므로 두 축 모두 실제 환경에서 시험할 수 있다. 시험 전용 계정만 쓴다.

| 시험 | 누가 | 방법 | 기대 |
|---|---|---|---|
| 계정 축 | 시험자 1명 | 시험 계정으로 일부러 5번 틀린 뒤 맞는 비밀번호 | 6번째 429, 15분 뒤 로그인 성공 |
| **분산 공격 (계정 축)** | **팀원 3명이 각자 집에서** | 같은 시험 계정에 한 사람당 2번씩 차례로 틀림(합계 6번 시도) | 합계 5번 실패 뒤 6번째 시도부터 **모든 사람에게** 429. 각자의 IP는 30번에 못 미쳐 IP 축은 안 걸림 → 계정 축이 IP와 상관없이 동작함을 확인 |
| IP 축 | 시험자 1명 | 서로 다른 없는 아이디 30개로 실패(요청 CLI로 천천히) | 31번째부터 그 시험자 IP만 429, **다른 팀원은 그 시간에도 정상 로그인** |
| 계정 열거 | 시험자 1명 | 없는 아이디와 있는 시험 계정에 같은 횟수 실패 | 응답 코드·문구 같음 |
| 실제 IP 판별 | 조장 | 분산 공격 시험 직후 DB의 IP 축 키 수를 셈(요청 로그에는 IP가 없고, DB에는 HMAC 키만 있음) | **IP 키 수 = 참여자 수.** ALB 노드가 AZ마다 있어서, IP 판별이 틀리면 키가 1~2개로 나온다. "다른 팀원은 정상 로그인"(IP 축 시험)과 함께 봐야 확실하다 |

주의:
- IP 축에 걸린 시험자는 **15분 동안 그 IP에서 로그인만** 막힌다(이미 로그인된 화면은 그대로). 그 사이 같은 IP로 다른 로그인 시험(혁민 요청 CLI 등)을 하지 않는다.
- 휴대폰 데이터·회사망처럼 여러 사람이 같은 공인 IP를 쓰는 곳이면 그 사람들도 같이 막힐 수 있다. 집 인터넷에서 한다.
- 시험 시각과 참여자 IP 대역(앞 두 자리 정도)은 운영기록에 적어 두고, 전체 IP는 적지 않는다.

## 6. WAF와의 관계

이 안에서 WAF 규칙은 만들지 않는다. 앱 제한이 본 방어이고(명세: WAF만으로는 완료 아님), WAF 빈도 규칙을 더할지는 4회차 WAF 작업(혁민·민성)에서 따로 정한다.

## 7. 다른 작업에 주는 영향

| 대상 | 영향 | 할 일 |
|---|---|---|
| 앱계약 3장 응답표, 1장 구조(`accounts/` 모델 없음) | 로그인에 **429**가 새로 생기고, `accounts`에 첫 migration `0001`(LoginFailure)이 생긴다 | 구현 PR에서 요찬이 앱계약 갱신 |

| 화면(푸른)·서버 설정(민성) | 없음 | 없음 |

## 8. 받아들이는 위험

- **남의 계정 막기:** 공격자가 어떤 사람의 아이디로 일부러 5번 틀리면 그 사람이 최대 15분 로그인하지 못한다. 시간이 지나면 풀리고 영구 잠금은 없다. 시험용 서비스라 이 정도는 받아들이는 것을 제안하고, 실제 사용자가 생기면 다시 본다.
- 동시 요청 몇 개만큼 기준을 넘을 수 있다(4장). 따로 막지 않는다.
