### 1.2.1 HTTPS 뒤 동작 [제안, 11/11]

명세 3.2 "DEBUG, ALLOWED_HOSTS, CSRF origin, cookie Secure/HttpOnly/SameSite와 프록시 신뢰를 명시"와 DEP-03을 앱 쪽에서 맞춘 것이다.

| 설정 | `DJANGO_HTTPS=0` (로컬·CI) | `DJANGO_HTTPS=1` (AWS HTTPS) |
|---|---|---|
| `SECURE_PROXY_SSL_HEADER` | 없음. `X-Forwarded-Proto`를 보내도 HTTPS로 보지 않음 | `("HTTP_X_FORWARDED_PROTO", "https")` |
| 세션·CSRF 쿠키 `Secure` | 없음 | 있음 |
| 세션·CSRF 쿠키 `HttpOnly` | 있음 | 있음 |
| 세션·CSRF 쿠키 `SameSite` | `Lax` | `Lax` |
| `SECURE_SSL_REDIRECT` | 끔 | 끔 (HTTP→HTTPS 전환은 ALB. 앱이 하면 ALB 상태 검사 `/healthz`가 301로 실패) |
| HSTS | 끔 | 끔 (도메인 운영이 안정된 뒤 결정. 한 번 보내면 브라우저가 기간 동안 되돌리지 못함) |

켠 상태의 CSRF 동작 (Django 기본, 시험으로 확인):
- `Origin: https://<도메인>` → 통과. `Origin: http://<도메인>`(scheme이 다름) → 403
- Origin이 없으면 같은 출처의 `Referer`가 있어야 통과. 둘 다 없거나 다른 사이트 Referer → 403
- 브라우저는 POST에 Origin을 붙이므로 사용자 흐름에는 영향이 없다. 권혁민 CLI는 기본 `origin_mode: same`이라 그대로 통과하고, `origin_mode: absent`를 쓰는 케이스는 HTTPS에서 Referer 없이 보내면 403이 된다(지금은 CSRF 토큰 없는 `post_without_csrf`뿐이라 기대값 403 그대로)

서버 쪽 조건 (이민성, `안민수/server/`):
- `deploy.sh`가 환경 파일(`/etc/haven/haven.env`)에 `DJANGO_HTTPS`를 항상 쓴다(#52). `CSRF_TRUSTED_ORIGINS`가 `https://`로 시작하면 `1`, 아니면 `0`이다(`HTTPS_ON` 변수). 확인: `grep HTTPS /etc/haven/haven.env`
- Nginx가 `X-Forwarded-Proto`를 ALB 값 그대로(`$http_x_forwarded_proto`), `Host`를 `$host`(포트 없음)로 넘긴다 → 지금 `web-setup.sh` 그대로 맞음
- Web 80은 ALB SG에서만 허용 (헤더 신뢰 범위). ALB 80 리스너는 443으로 리다이렉트
- 켠 뒤 HTTP로 접속하면 브라우저가 Secure 쿠키를 보내지 않아 로그인이 유지되지 않는다(의도된 동작)

### 1.2.2 시험 메일 [제안, 11/11]

명세 6.5 "메일은 가상 수신자 대상 최소 알림 한 가지", "발송 API 성공과 실제 도착, 실패 표시를 각각 검증", EXT-03(가상 수신자 실제 수신), EXT-04(실패를 사용자·운영자에게 성공으로 표시하지 않음), AWS 운영결정 6번(SES API 443)을 따른다.

| 항목 | 내용 |
|---|---|
| 보내는 곳 | 운영 명령 `python manage.py send_test_mail --to <가상 수신 주소>` 하나(회원 화면에서 보내는 기능 없음) |
| 보내는 방식 | `config.mail.SesEmailBackend` → SES v2 `SendEmail`(Simple, UTF-8 텍스트). AWS 키 없이 Web EC2 Role 임시 자격 증명 |
| 내용 | 고정 제목 `[Haven] 시험 메일`, 고정 문구 + 보낸 시각(UTC) + 실행 ID. 회원 정보·비밀값 없음 |
| 성공 표시 | SES가 MessageId를 돌려줄 때만 `SES 접수 message_id=… to=v***@… run_id=…`. "도착"이라고 쓰지 않는다. 실제 도착은 받은 편지함(스팸함 포함)에서 확인 |
| 실패 표시 | 종료 코드 1, `메일을 보내지 못했습니다 (오류: <SES 오류 코드>, 실행 ID: …)`. 오류 원문은 쓰지 않는다(SES 문구에 주소가 들어 있음). `HAVEN_MAIL_BACKEND`가 `ses`가 아니면 보내지 않고 실패 |
| 받지 않는 것 | 참조·숨은 참조·회신 주소·추가 헤더·첨부·HTML은 조용히 버리지 않고 오류. 받는 주소는 Django 이메일 검사(줄바꿈 등 헤더 주입 거부) |
| 시도 횟수·시간 | 한 번만 시도한다(자동 재시도 없음). 연결 5초·응답 10초 제한. 밤에 NAT가 내려가 있어도 오래 멈추지 않고, 같은 메일이 두 번 나가지 않는다. 실패하면 사람이 보고 다시 실행한다 |
| 로그 | 로거 `haven.mail`(표준 출력 → journald). `run_id`, `message_id` 또는 오류 코드만. 받는 주소 원문 없음 |

실패했을 때 보이는 오류 코드 (명령 출력과 `haven.mail` 로그):

| 오류 코드 | 뜻 | 볼 곳 |
|---|---|---|
| `ModuleNotFoundError` | 서버에 `boto3`가 없다 | 서버 requirements (E5) |
| `NoCredentialsError` | Web EC2 Role 자격 증명을 못 얻었다 | 인스턴스 프로파일 |
| `AccessDeniedException` | `ses:SendEmail` 권한이 없거나 발신 주소 조건과 다르다 | 김보람 IAM |
| `MessageRejected` | SES가 거부했다(발신 주소 미인증, sandbox에서 받는 주소 미인증 등) | 김보람 SES |
| `ConnectTimeoutError`·`EndpointConnectionError`·`ReadTimeoutError` | SES에 닿지 못했다(NAT가 내려간 밤 시간 등) | 이민성 네트워크 |

서버 쪽 조건:
- **의존성(E5):** `boto3==1.43.120`, `botocore==1.43.120`(2026-10-27 배포). 앱 코드는 보낼 때만 boto3를 불러서 로컬·CI 시험은 boto3 없이 돈다. 서버 requirements(`안민수/server/requirements.txt`)에만 넣으면 된다.
- **환경 파일(`/etc/haven/haven.env`, `deploy.sh`):** `HAVEN_MAIL_BACKEND=ses`, `HAVEN_MAIL_FROM=<인증한 발신 주소>`(선택 `HAVEN_SES_REGION`). **두 값은 같이 넣는다.** `ses`만 있고 발신 주소가 없으면 앱이 시작하지 않아 배포의 `/healthz` 확인이 실패하고 이전 release로 돌아간다. 둘 다 없으면 지금처럼 보내지 않는다. `deploy.sh`가 바뀌는 커밋은 같은 커밋으로 2번 배포해야 반영된다(11/11 조장 결정, `docs/인수인계/03_서버배포_인계.md`).
- **IAM(김보람):** Web EC2 Role에 `ses:SendEmail`. Resource는 발신 identity ARN, 조건 `ses:FromAddress`로 발신 주소 하나만. sandbox에서는 받는 주소도 SES에서 인증해야 하고, 거부되면 `AccessDeniedException`이나 `MessageRejected`가 오류 코드로 보인다.
- **출구:** SES API는 443(NAT 경유). 새 SG 규칙 없음(운영결정 6번).
- **발신 주소 [확정, 11/11 이민성]:** `noreply@orchestration-haven.cloud`. SES 도메인 `orchestration-haven.cloud`는 11/11 인증이 끝났다(김보람 #58 병합 `b54d77b`, 이민성 확인: Route 53 DKIM CNAME 3개, `VerifiedForSendingStatus=True`, DKIM `SUCCESS`). 서버 환경 파일의 `HAVEN_MAIL_FROM`에 이 값을 넣는다. 앱 코드는 주소가 바뀌어도 그대로다.
- **받는 주소 [확정, 11/11 이민성]:** 지금 SES가 받을 수 있는 주소는 김보람이 SES에 등록한 주소 1개뿐이다(SES sandbox로 보임). 시험은 그 주소로만 보낸다. 다른 주소가 필요하면 김보람에게 SES 등록을 요청한다. 개인 메일 주소라 이 문서와 Git에는 적지 않는다.

### 1.5 migration 순서

- `posts.0001_initial`은 `auth`(Django 기본 User)에 의존한다. `migrate` 한 번으로 순서대로 적용된다.
- 2회차: `django.contrib.admin`의 `admin.0001`~`0003`(감사 기록 테이블 `django_admin_log`)이 추가된다. [확정] D2
- 2회차: `adminpanel.0001_initial`은 운영 권한 두 개를 등록하기 위한 것으로 표를 만들지 않는다(`managed=False`). 권한 행은 `migrate` 뒤 Django가 만든다.
- 3회차: `posts.0002_attachment` (Attachment 표). [확정, 결정 5]
- 역 migration(되돌리기)은 승인 없이 실행하지 않는다.

`python manage.py seed_demo`는 권혁민 fixture의 사전 조건에 맞춰 아래를 만든다.

| 이름 | 역할 | fixture `auth_role` |
|---|---|---|
| `member_a` | 글 소유자 | `member_a` |
| `member_b` | 공유 대상 | `member_b` |
| `member_c` | 비대상 | `member_c` |
| `operator` | 제한된 운영 관리자. 권한 `adminpanel.manage_account_status`·`adminpanel.view_account_status_events`, is_staff·superuser 아님 [확정] D3 | `operator` |
| P1 (id=1) | A 소유, ACTIVE | `APP-02`, `APP-03` |

- 빈 DB가 아니거나 P1·P2의 id가 1·2가 아니면 실패로 종료한다. 다른 id로 조용히 만들지 않는다.

- Django 기본 관리자 사이트(`admin.site.urls`)는 연결하지 않는다. `/admin/login/`, `/admin/auth/user/` 등은 404다.
- 운영 관리자 = 활성 + superuser 아님 + **전용 권한**. 계정 목록과 상태 변경에는 `adminpanel.manage_account_status`, 이력에는 `adminpanel.view_account_status_events`가 필요하다. 권한은 개인 또는 그룹으로 부여할 수 있다. **is_staff만으로는 허용하지 않는다.** [확정, 명세 3.2] superuser(복구용)는 운영 흐름에 포함하지 않는다(명세 2.2).
- 관리자 계정 = 운영 권한이 있거나 is_staff 또는 superuser인 계정. 계정 목록, 상태 변경 대상, 공유 대상에서 빠진다.

### 3.1 응답 공통 규칙 (명세 2.1절)

| 상황 | 응답 | DB |
|---|---|---|
| 성공한 POST | 302 (POST/Redirect/GET) | 변경 |
| 입력 검증 실패 (로그인 실패 포함) | 400 + 같은 폼, 비밀번호는 다시 채우지 않음 | 변경 없음 |
| CSRF 누락·오류, 다른 출처 Origin | 403, 로그인 여부와 무관 | 변경 없음 |
| CSRF는 유효하지만 비로그인 | 302 → `/accounts/login/?next=<원래 경로>` | 변경 없음 |
| 없는 글, 다른 사람 글, 숫자가 아닌 id | 404, 모두 같은 화면 | 변경 없음 |
| 로그인한 일반 회원이 관리자 화면 | 403 (`403.html`) | 변경 없음 |
| 허용하지 않는 메서드 | 405 (`errors/405.html`) | 변경 없음 |
| 글 작성·수정 body 8,192바이트 초과 | 413 (`errors/413.html`) | 변경 없음 |
| 글 작성·수정의 숫자가 아니거나 음수인 Content-Length | 400 | 변경 없음 |
| 처리되지 않은 오류 | 500 + 일반 오류 화면 | |

- 로그인 실패는 Django 기본(200)을 바꿔 **400**으로 응답한다. 문구는 하나다: "로그인할 수 없습니다. 아이디와 비밀번호를 확인해 주세요."
- 비로그인 이동의 실제 `Location`에는 `?next=`가 붙는다. fixture의 `redirect_path`는 같은 Origin을 확인한 뒤 쿼리를 뺀 경로로 비교한다. [확정, 결정 11]
- **413이 CSRF·로그인 검사보다 먼저다.** 8,193바이트 이상이면 토큰이 없거나 비로그인이어도 413이다(Nginx와 같은 순서). body는 CSRF 토큰·폼 인코딩을 포함한 실제 직렬화 바이트로 센다. 글 작성·수정 경로에만 적용하고 로그인·가입·공유 폼에는 적용하지 않는다. [확정, 결정 9]
- 로그인 사용자 화면에는 `Cache-Control: private, no-store`를 붙인다.
- **첨부 업로드**(명세 3.4): 전체 multipart body 2,162,688바이트 초과는 413이 CSRF·로그인보다 먼저. 파일 크기는 실제 받은 bytes로 다시 세어 2 MiB 초과면 413. 형식·이름·개수·계정 용량 위반 400(상세 화면을 같은 상태 코드로 다시 보여 줌, 오류는 `attachment_form`). 저장·DB 실패는 500.
- **첨부 다운로드**: `Content-Disposition: attachment`(파일 이름은 Django가 RFC 6266 형식으로 인코딩), 검증된 `Content-Type`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`. 저장 위치(UUID)는 화면·주소 어디에도 나오지 않는다.

- 모든 POST 폼에 `{% csrf_token %}`을 넣는다.
- 입력 칸 id는 Django 기본값(`id_title`, `id_body`, `id_username`, `id_password` …)이다. 오류 안내 id는 `<필드>-error`(예: `title-error`)로 맞추면 `aria-describedby` 연결이 쉽다.
- 실패 후 다시 채우는 값: `username`, `title`, `body`. 비밀번호는 채우지 않는다.
- 서버가 받지 않는 값: `owner`, `author_id`, `status`. 보내도 무시하고 소유자는 로그인 사용자로 정한다.
- 비밀번호 안내 `form.password1.help_text`는 Django가 만든 HTML 목록이다. 그대로 출력하면 된다.
- 중복 아이디 안내는 가입 화면에서만 허용하고, 로그인 오류는 하나로 일반화한다. [확정, 결정 10]

## 6. 모델 계약

| 모델 | 필드 | 규칙 |
|---|---|---|
| User | Django 기본 `auth.User` | [확정, 결정 4] 별도 모델·인증 테이블 없음 |
| Post | `owner`(FK User, PROTECT), `title`(max 200), `body`, `status`(ACTIVE/DELETING), `created_at`, `updated_at` | `-created_at, -id` 순서, `(owner, -created_at)` 인덱스, ACTIVE만 조회·변경 |
| PostShare | `post`(FK, CASCADE), `recipient`(FK User, PROTECT), `created_at` | `(post, recipient)` unique. 해제는 행 삭제. 읽기는 매 요청 현재 관계·상태로 다시 확인 |
| 운영 권한 | `adminpanel.AccountStatusAdministration` (`managed=False`, 표 없음) | 권한 `manage_account_status`, `view_account_status_events`만 등록 (`default_permissions=()`) |
| 감사 기록 | Django `admin.LogEntry` (`user`=운영 관리자, `object_id`=대상, `change_message`=`{"account_status": {"before": …, "after": …}}`) | 상태 변경과 같은 transaction. 이력 화면에서 수정·삭제 불가. [확정] D2 |
| Attachment | `post`(FK, PROTECT), `storage_key`(UUID unique), `original_name`, `content_type`, `size_bytes`(≤ 2 MiB), `sha256`, `status`(PENDING/ACTIVE/DELETE_PENDING), `created_at` | 소유자는 `post.owner`. ACTIVE면 `content_type`·`sha256` 필수(DB 제약). 세 상태 모두 글당 3개·계정 10 MiB에 포함. 파일은 `HAVEN_UPLOAD_DIR/<storage_key>`(권한 600) |

글 삭제: 한 DB transaction에서 DELETING 전환 → 공유 관계 삭제 → 첨부를 DELETE_PENDING으로. 그다음 첨부 파일을 정리하고 끝나면 글을 최종 삭제한다. 파일 정리가 실패하면 글은 DELETING(누구도 볼 수 없음)으로 남고 `cleanup_attachments`가 마무리한다. 바깥 결과는 같다(302 → 목록, 이후 상세 404).

첨부 업로드: 이름·크기·내용 검사(DB 변경 전) → 소유자 행 → 글 행 순서로 잠그고 개수·용량 검사 후 PENDING 예약 → `.incoming`에 쓰고 fsync → UUID 경로로 link(기존 키 덮어쓰기 불가) → 글이 여전히 ACTIVE·소유인지 다시 확인하고 ACTIVE. 실패하면 파일·예약을 지우고, 그마저 실패하면 PENDING이 남아 `cleanup_attachments`가 지운다.

첨부 삭제: DELETE_PENDING(즉시 다운로드 차단) → 파일 삭제 → 메타데이터 삭제. 파일 삭제가 실패하면 행이 남아 용량을 돌려주지 않는다.

## 7. 로그 계약 [확정 형식, 3회차 PR에서 구현]

계정 상태 변경 감사는 6장 LogEntry(2회차). 요청 단위 로그는 `config/request_log.py`(D5). 형식은 권혁민 요청 재현 CLI(`request_verify.py correlate`)가 읽는 필드에 맞췄다.

| 항목 | 내용 |
|---|---|

| 필드 | `ts`(UTC ISO, 밀리초, `Z`), `request_id`(서버 UUID, 응답 헤더 `X-Request-ID`), `trace_id`(`X-Amzn-Trace-Id`의 Root), `client_request_id`(`X-Haven-Request-ID`), `run_id`(`X-Haven-Run-ID`), `method`, `path`(쿼리 문자열 제외), `view`(URL 이름), `action`, `actor_id`, `resource_id`(`post:1`, `post:1/attachment:3`, `post:1/share:2`, `user:5`), `status`, `result`, `elapsed_ms` |

| 대조 기준 | CLI는 요청마다 `X-Amzn-Trace-Id: Root=1-…`를 새로 만들어 보내고, AWS에서는 ALB가 붙인다. correlate는 `trace_id`의 Root, `run_id`, `ts` ±120초로 연결한다. 같은 Trace에 두 줄이 있으면 판정 불가이므로 한 줄만 남긴다 |

| 시험 실행 중 | 출력을 끈다(시험은 `assertLogs`로 직접 확인) |
