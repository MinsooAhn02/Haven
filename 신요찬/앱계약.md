### 1.2 환경변수 [제안, 이름과 공급 방식은 안민수와 확정]

| 이름 | 필수 | 기본값 | 용도 |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | 필수 | 없음 (없으면 시작 실패) | 세션·CSRF 서명 |
| `DJANGO_DEBUG` | 선택 | `0` | 로컬 개발에서만 `1` |
| `DJANGO_ALLOWED_HOSTS` | 필수 | 없음 | 쉼표 구분. 로컬 예: `127.0.0.1,localhost` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | HTTPS 배포 때 | 없음 | 쉼표 구분. 예: `https://<도메인>` |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | 필수 | 없음 | 개발 PostgreSQL 접속 |
| `DB_HOST`, `DB_PORT` | 선택 | `localhost`, `5432` | |
| `HAVEN_TEMPLATES_DIR` | 선택 | 저장소의 `노푸른/templates` | 통합 때 경로를 옮겨도 코드 수정 없이 연결 |
| `HAVEN_STATIC_DIR` | 선택 | 저장소의 `노푸른/static` | 위와 같음 |
| `HAVEN_SEED_PASSWORD` | `seed_demo` 실행 때만 | 없음 | 가상 계정 비밀번호. Git·문서·로그에 쓰지 않음 |

- **필수값이 없으면 시작 실패.** DB 설정이 없거나 틀려도 SQLite로 대체하지 않고, 운영 인증정보를 기본값으로 두지 않는다.
- `.env` 파일 자동 로딩은 넣지 않는다(추가 의존성 필요). `.env.example`을 만든다면 위 이름에 placeholder만 넣는다. 공급 방식과 파일 위치는 [결정 필요] → 안민수.
- migration과 상시 실행은 같은 변수 이름을 쓰고 값(계정)만 다르게 공급한다. 운영에서 migration 계정을 상시 실행 환경에 두지 않는 것은 배포 절차(안민수)에서 정한다.
- 메일: 1회차에는 메일 기능이 없다. 로컬·CI에서는 실제 전송하지 않는 backend를 쓰고, 메일 설정 이름은 3회차에 안민수와 정한다.
- 3회차에 `HAVEN_UPLOAD_DIR`(기본 `/srv/haven/uploads`), 2회차 배포 때 static 수집 경로를 추가한다.

### 1.3 개발 DB 조건 [결정 필요] → 안민수

- 개발용 DB 1개와 개발용 계정 1개가 필요하다.
- `python manage.py test`는 시험용 DB(`test_<DB_NAME>`)를 새로 만들므로 이 계정에 **CREATEDB 권한**이 필요하다.
- 이 계정은 로컬·CI 전용이다. 운영 runtime 계정(DDL 권한 없음)과 다르다.
- CI도 시험용 DB를 만들고 지울 수 있는 임시 PostgreSQL이 필요하다. 이 권한을 운영 runtime 권한에 복사하지 않는다.
- 준비 방식은 안민수가 정한다. 앱은 PostgreSQL 접속 정보만 요구하며 특정 설치 방식에 의존하지 않는다.

### 1.5 migration 순서

- `posts.0001_initial`은 `auth`(Django 기본 User)에 의존한다. `migrate` 한 번으로 순서대로 적용된다.

## 2. 시험용 가상 데이터와 초기화

`python manage.py seed_demo`(구현 예정)는 권혁민 fixture의 사전 조건에 맞춰 아래를 만든다.

| 이름 | 역할 | fixture `auth_role` |
|---|---|---|
| `member_a` | 글 소유자 | `member_a` |
| `member_b` | 2회차 공유 대상 | `member_b` |
| `member_c` | 비대상 | `member_c` |
| P1 (id=1) | A 소유, ACTIVE | `APP-02`, `APP-03` |
| P2 (id=2) | A 소유, ACTIVE, 삭제 시험 전용 | `APP-02-OWNER-DELETE` |

- 비밀번호는 `HAVEN_SEED_PASSWORD`에서 읽고 출력하지 않는다.
- `DJANGO_DEBUG=1`에서만 실행된다.
- 빈 DB가 아니거나 P1·P2의 id가 1·2가 아니면 실패로 종료한다. 다른 id로 조용히 만들지 않는다.
- **초기화:** 로컬 개발 DB에서만 `python manage.py flush --noinput` 후 `python manage.py seed_demo`. 공유 DB와 운영 DB에서는 실행하지 않는다.

## 3. URL 계약

템플릿에서는 이름으로 부른다. 예: `{% url 'posts:edit' post.pk %}`

| 경로 | 이름 | 메서드 | 성공 | 실패 | 회차 |
|---|---|---|---|---|---|
| `/` | `home` | GET | 302 → 로그인 상태면 `/posts/`, 아니면 `/accounts/login/` | | 1 |
| `/accounts/signup/` | `accounts:signup` | GET/POST | 302 → `/accounts/login/` [결정 필요] | 400 + 같은 폼 | 1 |
| `/accounts/login/` | `accounts:login` | GET/POST | 302 → 같은 호스트의 `next` 또는 `/posts/` | 400 + 일반화된 오류 | 1 |
| `/accounts/logout/` | `accounts:logout` | POST | 302 → `/accounts/login/` | GET 405 | 1 |
| `/posts/` | `posts:list` | GET | 200, 내 글 최신순 20건, `?page=N` | 비로그인 302 | 1 |
| `/posts/new/` | `posts:create` | GET/POST | 302 → 새 글 상세 | 400 | 1 |
| `/posts/<id>/` | `posts:detail` | GET | 200 | 404 | 1 |
| `/posts/<id>/edit/` | `posts:edit` | GET/POST | 302 → 상세 | 400 / 404 | 1 |
| `/posts/<id>/delete/` | `posts:delete` | GET/POST | GET 200 확인 화면, POST 302 → 목록 | 404 | 1 |
| `/posts/shared/` | `posts:shared` | GET | 200 | 비로그인 302 | 1에서 이름만 등록(빈 목록), 2에서 구현 |
| `/posts/<id>/shares/` | `posts:shares` | GET/POST | | | 2 |
| `/posts/<id>/shares/<share_id>/revoke/` | `posts:share_revoke` | POST | | | 2 |
| `/posts/<id>/attachments/…` | `posts:attachment_*` | | | | 3 (그 전에는 404) |
| `/admin/accounts/…` | `adminpanel:*` | | | | 2 |
| `/healthz` | `healthz` | GET | 200 `ok` (DB 미확인, 버전 미노출) | | 1 |

`posts:shared`를 1회차에 등록하는 이유: 공통 탐색의 "공유받은 기록" 링크를 `{% url %}`로 걸면, 이름이 없을 때 모든 화면이 500이 된다.

### 3.1 응답 공통 규칙 (명세 2.1절)

| 상황 | 응답 | DB |
|---|---|---|
| 성공한 POST | 302 (POST/Redirect/GET) | 변경 |
| 입력 검증 실패 (로그인 실패 포함) | 400 + 같은 폼, 비밀번호는 다시 채우지 않음 | 변경 없음 |
| CSRF 누락·오류, 다른 출처 Origin | 403, 로그인 여부와 무관 | 변경 없음 |
| CSRF는 유효하지만 비로그인 | 302 → `/accounts/login/?next=<원래 경로>` | 변경 없음 |
| 없는 글, 다른 사람 글, 숫자가 아닌 id | 404, 모두 같은 화면 | 변경 없음 |
| 허용하지 않는 메서드 | 405 | 변경 없음 |
| 글 작성·수정 body 8,192바이트 초과 | 413 | 변경 없음 |
| 처리되지 않은 오류 | 500 + 일반 오류 화면 | |

- 로그인 실패는 Django 기본(200)을 바꿔 **400**으로 응답한다. 명세와 fixture `APP-01-LOGIN-INVALID`에 맞춘다.
- 비로그인 이동의 실제 `Location`에는 `?next=`가 붙는다. fixture의 `redirect_path`는 쿼리를 뺀 경로로 비교해야 한다. [결정 필요] → 권혁민
- 413과 CSRF 실패가 동시에 해당할 때의 우선순위는 [결정 필요] → 권혁민·안민수. fixture `APP-11-A/B/C`는 유효한 CSRF 요청이라 지금은 충돌하지 않는다.
- 로그인 사용자 화면에는 `Cache-Control: private, no-store`를 붙인다.

## 4. 폼 계약

| 폼 | 필드 (`name`) | 검증 | 오류 위치 |
|---|---|---|---|
| 가입 (`UserCreationForm`) | `username`, `password1`, `password2` | Django 기본 username 규칙, 비밀번호 검사기, 두 값 일치 | 중복 아이디 `username`, 불일치 `password2` |
| 로그인 (`AuthenticationForm`) | `username`, `password` | 없는 계정·틀린 비밀번호·비활성 계정에 같은 문구 | `form.non_field_errors` |
| 글 (`PostForm`) | `title`, `body` | 제목 1~200자, 제목·본문 공백만 있으면 거부 | 각 필드 |
| 삭제·로그아웃 | 없음 (`csrfmiddlewaretoken`만) | | |

- 모든 POST 폼에 `{% csrf_token %}`을 넣는다.
- 입력 칸 id는 Django 기본값(`id_title`, `id_body`, `id_username`, `id_password` …)이다. 오류 안내 id는 `<필드>-error`(예: `title-error`)로 맞추면 `aria-describedby` 연결이 쉽다.
- 실패 후 다시 채우는 값: `username`, `title`, `body`. 비밀번호는 채우지 않는다.
- 서버가 받지 않는 값: `owner`, `author_id`, `status`. 보내도 무시하고 소유자는 로그인 사용자로 정한다.
- 비밀번호 안내 `form.password1.help_text`는 Django가 만든 HTML 목록이다. 그대로 출력하면 된다.
- 가입 화면의 중복 아이디 안내는 아이디 존재 여부를 알려 준다. 허용 범위는 [결정 필요] → 안민수·권혁민.

## 5. 템플릿과 context 계약

- 템플릿 위치: `노푸른/templates/` (`HAVEN_TEMPLATES_DIR`로 변경 가능). static: `노푸른/static/`. [결정 필요] → 노푸른
- 앱 폴더에 템플릿 복사본을 두지 않는다.
- 모든 화면 공통: `user`, `request`, `messages`, `csrf_token`

| 템플릿 | 화면 | context |
|---|---|---|
| `base.html` | 공통 레이아웃 | `user.is_authenticated`, `user.username` |
| `registration/login.html` | 로그인 | `form`, `next` |
| `accounts/signup.html` | 가입 | `form` |
| `posts/list.html` | 내 기록 목록 | `posts`(현재 페이지 글 목록), `page_obj`(`has_previous`, `has_next`, `previous_page_number`, `next_page_number`, `number`, `paginator.num_pages`) |
| `posts/detail.html` | 상세 | `post`(`pk`, `title`, `body`, `created_at`, `updated_at`, `owner.username`), `is_owner` |
| `posts/form.html` | 작성·수정 공용 | `form`, `mode`(`"create"`/`"edit"`), `post`(수정 때만, 작성 때 `None`) |
| `posts/confirm_delete.html` | 삭제 확인 | `post`. 삭제 POST 대상 `posts:delete`, 취소 링크 `posts:detail` |
| `posts/shared_list.html` | 공유받은 기록 | `posts`, `page_obj` (1회차는 항상 빈 목록) |
| `400.html`, `404.html`, `403_csrf.html` | 오류 | 공통 값(`user` 등)만 사용. 404에는 Django가 `exception`도 넘기지만 화면에 표시하지 않음 |
| `403.html` | 권한 거부 (2회차 관리자 화면) | 공통 값만 사용. Django가 `exception`을 넘기지만 표시하지 않음 |
| `500.html` | 서버 오류 | context 없음(`user`도 없음). `base.html`을 상속하면 `user` 없이도 깨지지 않아야 함 |
| `errors/413.html` | 본문 초과 | 공통 값만 사용 |
| `errors/405.html` | 메서드 오류 | [결정 필요] Django 기본 405는 빈 본문. 화면을 보여 주려면 처리기를 추가함 |

화면 규칙 (명세 2.3절):

- `|safe`를 쓰지 않는다. 본문은 `{{ post.body|linebreaksbr }}`처럼 이스케이프를 유지해 출력한다.
- 1회차에서 `is_owner`는 항상 `True`다. 2회차 공유 대상 화면에서 `False`가 되며, 이때 수정·삭제·공유·업로드 버튼을 숨긴다(서버도 같은 권한을 따로 검사).
- 저장·삭제 성공 안내는 `messages`로 전달한다.
- 빈 목록이면 `posts`가 비어 있다. 작성 안내는 템플릿에서 표시한다.

## 6. 모델 계약 (첫 migration 전 확인)

| 모델 | 필드 | 규칙 |
|---|---|---|
| User | Django 기본 `auth.User` (명세 1절 그대로) | 별도 모델·인증 테이블 없음. 첫 migration 전 안민수 확인만 받음. 이후에는 바꾸기 어려움 |
| Post | `owner`(FK User, PROTECT), `title`(max 200), `body`, `status`(ACTIVE/DELETING), `created_at`, `updated_at` | `-created_at, -id` 순서, `(owner, -created_at)` 인덱스, ACTIVE만 조회·변경 |
| PostShare | `post`(FK, CASCADE), `recipient`(FK User, PROTECT), `created_at` | `(post, recipient)` unique. 해제는 행 삭제 |
| Attachment (설계만) | `post`(FK, PROTECT), `storage_key`(UUID unique), `original_name`, `content_type`, `size_bytes`, `sha256`, `status`(PENDING/ACTIVE/DELETE_PENDING), `created_at` | 검사 전 `content_type`·`sha256`는 비어 있을 수 있고 ACTIVE면 값 필수. 생성 시점 [결정 필요] |

1회차 글 삭제: 한 DB transaction에서 DELETING 전환 → 공유 관계 삭제 → 최종 삭제. 3회차에는 첨부 파일 정리가 끝난 뒤 최종 삭제로 바뀐다. 바깥 결과는 같다(302 → 목록, 이후 상세 404).
