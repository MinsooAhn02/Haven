## 4. 2회차 · 3~4일차 — PostgreSQL과 AWS 첫 배포

공통 환경의 현재 확인값·미결정 계약은 [공통 실행 안내](공통실행.md)에 기록한다. 이 회차는 아래 인계 순서가 갖춰진 뒤 실제 변경을 진행한다.

**인계/실행 순서:** 보람의 운영 접근·Role 승인 → 민성의 승인 범위 EC2/SSM 및 Web→DB 연결·직접 접근 거부 증거 → 요찬의 배포 commit·의존성·settings/WSGI·migration/시험 절차 → 민수의 DB·역할 분리·migration → 앱 배포와 재시작 확인 → 실패 시 앱 버전 복귀/설정 복구 → 푸른·혁민 재시험. 각 단계에서 결과와 다음 담당자에게 필요한 값을 넘긴다. 승인·연결·앱 인계가 없으면 준비와 문서화까지만 하고 다음 단계의 완료로 표시하지 않는다.

### 먼저 받을 것

- [ ] 김보람: 승인된 운영 접근·서버 Role·권한 범위.
- [ ] 이민성: 서버 식별 정보·OS·SSM·디스크/마운트·Web→DB·필요 출구의 실제 시험 결과.
- [ ] 신요찬: 배포 commit·의존성·settings/WSGI·migration 순서·가상 데이터 준비·호환성 주의사항.

### 3일차: DB 준비 후 앱 연결

- [ ] 대상·중단 영향·복구 방법을 확인하고 PostgreSQL을 설치한다. listener와 pg_hba를 허용 Web 주소·DB·사용자에 맞춘다. SG 변경은 이민성이 한다.
- [ ] 앱 DB·migration/runtime 계정을 분리한다. runtime에 superuser·역할 관리·불필요한 DDL을 주지 않고 필요한 테이블·sequence 권한만 부여한다.
- [ ] migration 객체 소유자·권한 부여 방식을 정하고 새 migration 후에도 runtime CRUD가 가능한지 확인한다.
- [ ] 승인된 migration을 migration 계정으로 실행하고 runtime 인증으로 전환해 저장/조회를 확인한다. 앱에 migration 비밀값을 상시 제공하지 않는다.
- [ ] 올바른 Web/runtime 연결 성공·잘못된 계정 인증 실패·runtime DDL 거부를 확인한다. 무허가 출발지 시험은 이민성과 수행해 인증 오류와 네트워크 거부를 구분한다.

### 4일차: 앱 서비스와 재시작

- [ ] 비root 실행 계정·venv·고정 의존성을 준비하고 Nginx→loopback Gunicorn→Django로 연결한다. 환경파일 읽기 권한을 제한한다.
- [ ] systemd의 실행 사용자·경로·환경파일·자동 기동을 확인한다. static 수집/제공 경로를 노푸른·신요찬과 맞춘다.
- [ ] DEBUG·허용 host·Secret 공급·로그를 점검한다. HTTPS 쿠키/프록시 검증은 ALB HTTPS 연결 후 완료하고 준비 전 공개 여부를 이민성과 확인한다.
- [ ] 배포 commit·설정 변경·migration 내역을 기록한다. `/healthz`와 실제 로그인·저장/조회를 별도로 확인한다.
- [ ] 승인된 점검 시간에 앱 서비스·Web 서버·DB를 재시작하고 자동 기동·SSM·기존 기록 유지·새 CRUD를 확인한다.
- [ ] 이전 앱 복귀 조건을 기록하고 호환되는 변경으로 복귀·재배포를 시험한다. DB를 무조건 역 migration하거나 덮어쓰지 않는다.

**완료 조건:** DB-01~03/05, DEP-01~02/04~05의 실제 결과 확보. DB-04 복원·DEP-03 HTTPS가 남아 있으면 미완료로 구분한다.

**인계:** 노푸른·권혁민에게 배포 commit·시험 경로·계정 준비 방법·알려진 실패를, 이민성에게 Web 포트·health 경로·응답 결과 전달. 자격증명은 별도 보안 경로로 전달한다.

**main 순서:** `4 → 6 → 5 → 2 → 1 → 3`. 서버 연결과 앱/migration 인계 후 실제 배포한다.

## 5. 3회차 · 5~6일차 — 첨부·HTTPS·메일·정합 백업

### 5일차: 첨부와 HTTPS 운영 설정

- [ ] 신요찬에게 첨부 migration·저장/임시 경로·정리 작업·실패 처리 계약을 받아 재배포한다.
- [ ] 비공개 첨부/임시 디렉터리의 실행 계정·접근 권한·용량·재시작 후 유지를 확인한다. Nginx 공개 static 경로에서 첨부를 직접 제공하지 않는다.
- [ ] Nginx와 앱의 요청 제한을 맞춘다. 명세 제안값은 일반 글 body 8,192바이트·업로드 body 2,162,688바이트다. 변경은 신요찬·권혁민과 대조하며 파일당 제한과 전체 multipart 제한을 구분한다.
- [ ] 이민성의 ALB/DNS/ACM 인계 후 실제 HTTPS 로그인·POST·CSRF·Secure/HttpOnly/SameSite·허용 origin을 확인한다. settings 수정은 신요찬에게 요청한다.
- [ ] 원래 scheme을 신뢰할 조건과 위조 프록시 헤더 처리를 확인한다. ALB→Web은 기본 HTTP임을 기록한다.
- [ ] A 첨부 작성→B 공유/다운로드→C 거부→B 변경 거부→해제 후 B 거부를 함께 확인한다. 앱/프록시/WAF 원인을 구분해 담당자에게 전달한다.

### 6일차: 시험 메일과 백업 준비

- [ ] 김보람과 메일 제공자·리전·발신/수신 허가·예산을 확정하고 이민성에게 출구/DNS 작업을 요청한다. SES는 sandbox·발신/수신 인증 조건을 확인한다.
- [ ] 가상 시험 계정의 승인된 수신처로 최소 알림 한 가지를 보낸다. API 성공·메시지 식별 정보·실제 도착을 구분하고 실패를 성공으로 표시하지 않는지 확인한다.
- [ ] 백업 위치·접근 권한·보존·가상 데이터 범위·쓰기 중지/재개 조건을 정한다. 저장소/IAM 신규 변경은 담당자 확인을 받는다.
- [ ] 쓰기 중지 후 진행 중 업로드·삭제/정리를 확인해 기준 시점을 맞춘다. DB dump와 ACTIVE 첨부를 같은 묶음으로 수집하고 실패 시 상태를 남기고 재개 여부를 확인한다.
- [ ] 파일 manifest에 `post_id, attachment_id, storage_key, size_bytes, sha256`, 백업 묶음에 시각·배포 commit·schema 상태·도구 버전을 남긴다.
- [ ] 누락/고아 파일·hash 불일치를 구분하고 4회차 격리 복원 대상과 절차를 준비한다.

**완료 조건:** DEP-03, EXT-03~04와 첨부 운영 결과, 정합 백업 확보. DNS/인증서 EXT-01~02는 이민성 결과에 연결한다. 백업 생성만으로 복원 완료 처리하지 않는다.

**인계:** 권혁민에게 HTTPS origin·commit·정상 요청 기준·로그 시각/위치·요청 한도, 신요찬에게 저장/정리 오류, 전원에게 시험 가능한 배포 시간 전달.

**main 순서:** `4 → 5 → 1 → 6 → 2 → 3`. 실제 HTTPS 시험은 배포와 ALB 연결 확인 후 진행한다.
