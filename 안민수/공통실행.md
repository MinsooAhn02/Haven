## 실행 순서

앱 인계와 위 계약 확정 후에만 Django 실행 명령을 채운다. 현재 실행 가능한 앱 명령은 확인되지 않았다.

1. 확정한 Python으로 가상환경을 만든다.
2. 앱 담당자가 지정한 의존성 파일을 설치한다.
3. 운영 비밀값을 사용하지 않고 개발용 설정·인증정보를 공급해 개발 전용 PostgreSQL 연결을 확인한다. 실제 비밀값은 Git에 기록하지 않는다.
4. 인계된 migration을 새 개발 DB에 적용하고 가상 시험 계정을 준비한다.
5. 인계된 실행 명령으로 서버를 시작해 로그인·기록 저장·조회·인가 시험을 한다.
6. 앱 시험은 앱 인계 후 CI에 추가한다. 현재 CI는 아래 SG fixture CLI만 실행한다.

## 현재 실행 가능한 독립 CLI 시험

Windows 저장소 루트에서 `py -3.13 -B -m unittest discover -s 이민성/sg_audit -p test_network_audit.py -v`를 실행한다. 격리 설치 재현은 `.venv`의 Python 3.13으로도 완료했다. CI는 Python 3.13에서 동일한 테스트 모듈을 실행하며, 시험 0건도 실패 처리한다.

앱·의존성·시험 명령 인계가 없어 앱 실행, migration, 앱 CI는 미확인이다. SG CLI 5개는 기본 Python 3.13 및 깨끗한 `.venv` Python 3.13.15에서 통과했고, `pip check`도 깨끗했다. GitHub CI는 [실행 42211003282](https://github.com/MinsooAhn02/Haven/actions/runs/42211003282)에서 성공했다. 로컬 고의 실패는 exit 1이었다. 별도 임시 디렉터리에 추적 CLI 소스만 내보내고 CI와 같은 runner를 적용해 5건 통과를 재현했으며, mock 0건은 exit 1·성공 fixture는 exit 0·고의 실패 fixture는 exit 1임을 확인했다. 이는 격리 재현이지 팀원/새 PC 재현은 아니다. 이는 SG CLI 범위만 증명한다.

## 개발 PostgreSQL 준비 (앱 구조와 무관한 부분 · 2026-11-08 초안, 미실행)

앱 경로·settings·모델이 어떻게 정해져도 바뀌지 않는 DB 쪽 준비만 적는다. (변경됨 2026-11-09: 처음엔 설치 방식 미정·미실행이었음)

**설치 (요찬·푸른·혁민은 화요일까지):** 저장소 루트에서 `powershell -ExecutionPolicy Bypass -File 안민수\dev-db-setup.ps1`. 관리자 확인 창이 뜨면 허용한다. 하는 일:
1. PostgreSQL 16이 없으면 winget으로 설치(서버·명령줄 도구만)
2. 비밀번호를 무작위로 만들어 `%APPDATA%\postgresql\pgpass.conf`에만 저장(psql·Django가 자동으로 읽음). Git·Discord에 올리지 않는다
3. 서버를 localhost에서만 받게 제한(설치 기본값은 모든 주소에서 대기)
4. 아래 SQL과 같은 `haven_owner`·`haven_app`·`haven_dev` 생성
5. `haven_app`의 CRUD 성공과 CREATE TABLE 거부를 확인하고, 하나라도 틀리면 실패로 멈춤

**왜 Docker가 아니라 winget인가:** 민수 PC에 Docker가 없고(팀원 PC는 미확인), 개발 DB 하나 때문에 Docker Desktop을 새로 까는 부담이 더 크다. 서버(Ubuntu 24.04)도 같은 PostgreSQL 16이다.

**민수 PC 실행 기록 (2026-11-09):** PostgreSQL 16.15 설치·서비스 자동 시작, `listen_addresses=localhost`(127.0.0.1·::1만 대기), 스크립트 두 번 연속 실행 통과(중복 없음). `haven_app`에 CREATE 권한을 일부러 준 상태에서는 스크립트가 exit 1로 실패함을 확인한 뒤 권한을 되돌렸다. 다른 팀원 PC에서는 아직 실행 전.

**이미 PostgreSQL을 다른 방법으로 설치한 경우:** 스크립트가 pgpass에 `postgres` 비밀번호가 없다며 멈춘다. 안내대로 pgpass에 한 줄을 넣고 다시 실행한다.

**역할을 처음부터 나누는 이유:** 운영(2회차)에서 migration 주체와 runtime 주체를 분리하기로 했다(명세 DB 절). 개발 때부터 같은 구조로 쓰면 "개발에선 됐는데 운영 권한에서 안 되는" 문제를 미리 잡는다.

| 역할 | 용도 | 권한 |
|---|---|---|
| `haven_owner` | migration 실행·테이블 소유 | 개발 DB 소유자. 개발 PC에서만 `CREATEDB`(Django 시험 runner가 `test_<DB명>`을 만들고 지우기 때문) |
| `haven_app` | 앱 runtime 연결 | 접속 + 테이블/sequence CRUD만. DDL·superuser 없음 |

```sql
-- psql에서 관리자(postgres)로 실행. 비밀번호는 각자 개발용 값으로 정하고 Git·문서에 쓰지 않는다.
CREATE ROLE haven_owner LOGIN CREATEDB PASSWORD :'owner_pw';
CREATE ROLE haven_app   LOGIN PASSWORD :'app_pw';
CREATE DATABASE haven_dev OWNER haven_owner;
\c haven_dev
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO haven_app;
-- haven_owner가 앞으로 만드는 테이블·sequence에 runtime 권한 자동 부여
ALTER DEFAULT PRIVILEGES FOR ROLE haven_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO haven_app;
ALTER DEFAULT PRIVILEGES FOR ROLE haven_owner IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO haven_app;
```

실행 예: `psql -U postgres -v owner_pw=... -v app_pw=... -f <위 내용 파일>` (값은 대화형 입력이나 로컬 전용 파일로 공급).

**확인할 것 (설치 후):**
- `haven_owner`로 테이블 생성 → `haven_app`으로 같은 테이블 CRUD 성공
- `haven_app`으로 `CREATE TABLE` 시도 → 거부되어야 함
- Django 시험은 `haven_owner`로 실행(시험 DB 생성 권한 필요). 앱 실행은 `haven_app`
- 앱이 정해지면 위 이름을 그대로 쓰고, settings가 읽을 환경변수 이름만 요찬과 맞춘다

**한계:** 운영에서는 `CREATEDB`를 주지 않는다. Django가 `public` 스키마 외 다른 스키마를 쓰도록 정해지면 위 GRANT 대상만 바꾼다.

## 차회 운영 준비 절차 (계획; 아직 실행하지 않음)

### 입력 먼저 받기

실제 OS/호스트 식별자·접속 경로·운영 Role·DB/data 경로·앱 commit와 settings/WSGI·migration 명령·중단 허용 시간·복구 대상이 확정되기 전에는 적용할 설치 명령이나 환경파일을 만들지 않는다. DB 연결 포트는 명세의 TCP 5432, Nginx ingress는 HTTP 80 기준이며 보안그룹 변경은 민성 담당이다. DB 인바운드는 Web SG만 허용하는 명세를 따르고 앱은 DB 전용 runtime 인증으로 연결한다.

### DB 역할과 배포/복귀 순서

1. 변경 전 승인된 대상, 현재 앱 commit/schema, 백업 시각, 중단 영향, 되돌릴 앱 버전과 복구 담당을 기록한다. 이 중 하나라도 미정이면 작업을 보류한다.
2. DB 담당 입력에 맞춰 앱 데이터베이스, migration 주체, runtime 주체를 분리한다. runtime에는 CRUD에 필요한 최소 테이블/sequence 권한만 주고 superuser·역할 생성·DDL은 주지 않는다. migration 뒤 runtime CRUD와 DDL 거부를 각각 확인한다.
3. 비root 실행 계정·venv·환경파일 접근 권한과 Nginx → loopback Gunicorn → Django 연결을 확인한다. systemd 실행 사용자·작업 경로·WSGI·자동 기동 및 static 원본 경로는 인계값과 맞춘다. 승인한 migration과 앱 commit을 기록하고 runtime 인증으로 전환한 뒤 서비스를 시작한다. health 응답만으로 완료하지 말고 로그인·생성·조회와 기존 데이터 유지도 확인한다. 승인된 점검 시간에 서비스/서버 재시작 후 자동 기동·SSM·데이터 영속성을 검증한다.
4. 실패하면 우선 트래픽/재시작을 멈추고 로그·현재 버전·오류를 보존한다. 호환되는 앱 버전과 이전 설정으로 복귀해 로그인·기존 데이터 조회를 확인한다. DB를 무조건 역 migration하거나 덮어쓰지 않는다. 데이터/schema 손상이 의심되면 별도 승인된 복원 계획으로 전환한다.

**합격:** 지정 Web에서 DB 연결 성공, 다른 출발지 차단 증거, runtime 인증 성공 및 DDL 거부, 앱 재시작 후 로그인·CRUD·기존 기록 유지, 실패 시 앱 설정 복귀 결과가 기록됨.

### 정합 백업과 격리 복원

1. 승인된 백업 위치·접근 주체·보존 기간·복원 전용 격리 대상·쓰기 중지 시간을 확정한다. 백업 생성 권한과 복원/삭제 권한은 분리해 확인한다.
2. 쓰기를 멈추고 업로드/삭제 작업 완료를 확인한 동일 시점에 PostgreSQL dump와 ACTIVE 첨부를 수집한다. manifest에는 `post_id, attachment_id, storage_key, size_bytes, sha256`와 백업 시각·앱 commit·schema 상태를 기록한다. 부분 실패면 묶음을 유효 백업으로 표시하지 않는다.
3. 운영과 분리된 DB와 비공개 파일 경로로 함께 복원한다. 스키마·행 수·샘플 조회, 각 파일 크기/hash, A/B/C 권한·공유 해제 후 거부를 확인한다. 운영 메일/API 호출을 차단한다.
4. 누락·고아 파일·hash mismatch·권한 오류가 하나라도 있으면 복원 실패로 남기고 원인을 정리한다. 운영으로 덮어쓰지 않는다. 실패한 격리 복원 환경은 증거를 보존하고 승인된 방식으로 폐기한다.

**합격:** 같은 시점의 DB/첨부/manifest 세트 복구, 구조·기록·hash·권한 검사 통과, 실제 조회 확인 및 격리 분리 증거. dump 파일 생성만으로 복원 성공이라 하지 않는다.

### 시험 메일

메일 제공자, 리전, 발신 도메인/주소, 수신 허가, 비용 및 네트워크 egress를 보람·민성과 먼저 확정한다. SES를 선택한다고 가정하지 않는다. 비운영 시험 설정으로 승인된 가상 수신처 하나에 최소 알림을 보낸다. API 성공, 메시지 식별자, 수신함 실제 도착을 각각 기록하고 실패 시 사용자에게 성공 표시가 없는지 확인한다. 반복 발송·실사용자 주소·운영 Secret은 시험에 쓰지 않는다.

## 서버 설치·배포 (2026-11-09, `안민수/server/`)

결정: 코드는 **읽기 전용 deploy key**로 web-1이 GitHub에서 직접 받는다(AWS 변경 없음, 개인키는 서버 밖으로 안 나감). 비밀값(DB 비밀번호 2개, `DJANGO_SECRET_KEY`)은 **SSM Parameter Store SecureString `/haven/*`**(Git·명령 인자·로그에 안 남고, 계정 이전 때도 같은 방식). 버린 대안: S3 경유(버킷·권한 추가 필요), 서버에서 손으로 복사(계정 이전마다 반복).

| 순서 | 어디서 | 명령 | 하는 일 |
|---|---|---|---|
| 1 | 조장 PC | `bash put-secrets.sh` | SSM에 비밀값 3개 생성. 이미 있으면 유지, 값 출력 안 함 |
| 2 | db-1 (SSM) | `WEB_IP=<web-1 사설 IP> bash db-setup.sh` | PostgreSQL 16, DB `haven`, `haven_owner`(소유·migrate)/`haven_app`(CRUD만), web-1에서 두 계정만 접속 허용 |
| 3 | web-1 (SSM) | `DB_HOST=<db-1 IP> ALLOWED_HOSTS=<도메인 또는 ALB 이름> bash web-setup.sh` | venv·Gunicorn(systemd)·Nginx. 마지막에 deploy key 공개키 출력 |
| 4 | GitHub | Settings > Deploy keys에 3의 공개키 등록(**Allow write 끄기**) | |
| 5 | web-1 | `bash deploy.sh <40자리 commit>` | 받기 → 의존성 → migrate(haven_owner) → 전환 → `/healthz`. 실패 시 이전 release로 복귀(DB migration은 되돌리지 않음) |

- 필요한 IAM(보람): EC2 Role `haven-ec2-ssm-role`에 `ssm:GetParameter` (`arn:aws:ssm:ap-northeast-2:<계정>:parameter/haven/*`만). 조장에게 같은 경로의 `ssm:PutParameter`·`ssm:GetParameter`. 기본 키(aws/ssm) 사용이라 KMS 정책 추가 없음.
- ALB 상태 검사: 경로 `/healthz`, 포트 80. ALB는 Host에 서버 IP를 넣어 Django가 400을 내므로 Nginx가 `/healthz`만 Host를 첫 `ALLOWED_HOSTS` 값으로 바꿔 넘긴다.
- static: Nginx가 release 안 `노푸른/static/`을 직접 제공(collectstatic 없음). 관리자 사이트를 쓰지 않아 지금은 충분하다.
- 한계: 3회차 첨부 업로드는 `ProtectSystem=strict`라 `ReadWritePaths`를 추가해야 한다. HTTPS 뒤 `SECURE_PROXY_SSL_HEADER`는 3회차에 요찬과 맞춘다.

시험: `test-wsl.sh`를 서버와 같은 WSL Ubuntu-24.04(Python 3.12.3)에서 root로 실행. 가짜 aws로 SSM 읽기 실패도 시험한다. 실제 AWS 실행은 수요일 구축 후.

### DB 백업·복원 (2026-11-09)

| 명령 (db-1, root) | 하는 일 |
|---|---|
| `BACKUP_BUCKET=haven-backup-<계정ID> bash backup.sh` | `pg_dump` + 표별 행 수 + manifest(sha256) → `s3://<버킷>/db-backups/<UTC시각>/`. manifest를 마지막에 올려 manifest 있는 것만 완전한 백업. 백업 중 행 수가 바뀌면 실패(다시 실행) |
| `BACKUP_BUCKET=... bash restore.sh <UTC시각>` | sha256 확인 → 격리 DB `haven_restore_check`에 복원 → 행 수 비교. 운영 DB는 건드리지 않음 |
| `TARGET_DB=haven BACKUP_BUCKET=... bash restore.sh <UTC시각>` | 새 계정 이전: `db-setup.sh`로 만든 빈 `haven`에 복원. 테이블이 하나라도 있으면 거부 |

- 버킷 이름 `haven-backup-<계정ID>`(S3 이름은 전 세계 유일이라 계정 ID를 붙임, 계정 이전 때 같은 규칙). 버킷 생성은 구축 때.
- IAM(보람): 서버 Role에 `s3:PutObject`·`s3:GetObject` (`<버킷>/db-backups/*`만). 복원은 시각을 직접 지정하므로 `s3:ListBucket` 불필요.
- 한계: 첨부 파일 백업은 3회차(업로드 생긴 뒤). 자동 실행 타이머는 첫 배포 직후 연습 뒤에 정한다. 쓰기 감지는 덤프 전후 행 수 비교라 행 수가 같은 수정은 못 잡는다.
- 시험: `test-backup-wsl.sh` (test-wsl.sh 다음에 실행) 19개 통과. 버킷 없음·S3 거부·없는 백업·손상된 dump·행 수 불일치·운영 DB 덮어쓰기는 모두 멈춘다.

### 수요일 첫 배포 절차 (2026-11-09 작성, 실행 전)

**받아야 할 것:** 민성 → web-1·db-1 인스턴스 ID와 사설 IP · 보람 → `minsoo` Session Manager 접속 권한, 백업 버킷 `haven-backup-<계정ID>`(퍼블릭 차단·암호화) · 도메인(없으면 ALB 이름, ALB 전이면 임시 `haven.local`).

| # | 어디서 | 할 일 | 확인 |
|---|---|---|---|
| 1 | 콘솔 EC2 → db-1 → 연결 → Session Manager, `sudo -i` | `common.sh`·`db-setup.sh`를 붙여넣기(`cat > 파일 <<'EOF'`)로 넣고 `sha256sum`을 저장소 파일과 대조 → `WEB_IP=<web-1 IP> bash db-setup.sh` | 마지막 줄 `OK  db-setup`, 두 번 실행해도 OK |
| 2 | web-1 Session Manager | `common.sh`·`web-setup.sh`·`deploy.sh` 붙여넣기·대조 → `DB_HOST=<db-1 IP> ALLOWED_HOSTS=<도메인 또는 ALB 이름> bash web-setup.sh` | 마지막에 공개키 출력 |
| 3 | GitHub Settings > Deploy keys | 2의 공개키 등록, **Allow write 끔** | |
| 4 | web-1 | `bash deploy.sh <main 40자리 commit>` | `OK  deployed`, `curl -s -H 'Host: <첫 허용 Host>' http://127.0.0.1/healthz` → ok |
| 5 | web-1·db-1 | 연결확인표: Web→DB 5432 성공, 다른 곳→DB 거부, postgres 원격 거부(pg_hba) | 민성 연결확인표에 결과 |
| 6 | 둘 다 | `reboot` → 다시 접속 | healthz 200, `systemctl is-active haven nginx postgresql` |
| 7 | 백업 연습 | web-1 `systemctl stop haven` → db-1 `backup.sh`(시각 출력) → web-1 `backup-uploads.sh <시각>` → web-1 `systemctl start haven` → db-1 `restore.sh <시각>` → web-1 `restore-uploads.sh <시각>` | 각 `OK`, 행 수·파일 sha 일치 |

- 2번째 배포부터는 web-1에서 `bash /srv/haven/current/안민수/server/deploy.sh <commit>`(코드와 같이 받은 스크립트). 1·2의 붙여넣기는 첫 설치 때만.
- 붙여넣기 파일과 sha256 값은 그날 Claude가 저장소 기준으로 만들어 준다(CloudShell 때와 같은 방식).
- 매일 21시 민성 `nat-down` + EC2 중지 → 다음 날 시작하면 haven·nginx·postgresql이 자동으로 뜬다(6번 재부팅으로 확인). NAT가 없는 동안은 pip·apt·SSM 비밀값 읽기가 안 되므로 배포는 09~21시에.
- 도메인 확정(11/11): `orchestration-haven.cloud`. ALB·ACM 연결 후 `ALLOWED_HOSTS=orchestration-haven.cloud`·`CSRF_TRUSTED_ORIGINS=https://orchestration-haven.cloud`으로 web-setup.sh 다시 실행(여러 번 실행해도 같은 결과) → 같은 commit으로 deploy.sh.
