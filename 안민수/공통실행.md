# 공통 실행 안내

이 문서는 확인된 환경과 앱 담당자에게 받을 실행 계약의 기준이다. TODO 작성은 설치·실행·AWS 변경 승인이 아니며, 미확정 항목은 실제 앱 인계 후 갱신한다.

## 확인된 환경

| 항목 | 확인값 | 범위 |
|---|---|---|
| 기본 `python` | Python 3.9.13 | 이 작업 환경에서 확인 |
| Python Launcher | 3.13 및 3.14 설치 확인 | 마지막 조회 시점; 사용할 버전은 앱 요구와 합의 필요 |
| PostgreSQL CLI | `psql` 명령 조회에서 찾지 못함 | 설치 여부의 확정 판정 아님 |
| Docker CLI | `docker` 명령 조회에서 찾지 못함 | 설치 여부의 확정 판정 아님 |
| Django 앱·의존성 | 저장소에서 확인되지 않음 | 앱 인계 후 재확인 |
| 로컬 전용 venv | `.venv` Python 3.13.15, pip 26.2.1; `pip check` 통과 | 이 저장소 작업 환경에서 재현; 앱 의존성은 미설치 |
| PostgreSQL/컨테이너/AWS CLI | `psql`, `pg_dump`, `pg_restore`, `docker`, `aws`가 PATH에서 조회되지 않았고 PostgreSQL 서비스 조회 결과 없음 | 이 PC의 현재 탐색 결과일 뿐, 머신 전체 미설치 판정 아님; SSH는 조회됨 |
| CI | `.github/workflows/ci.yml`에서 이민성 SG fixture CLI 시험을 실행 | 실제 GitHub run 성공; 앱/DB 시험은 아직 포함하지 않음 |

## 앱 인계 후 채울 계약

| 값 | 담당/필요 시점 | 상태 |
|---|---|---|
| 앱 루트, 작업 디렉터리, `manage.py` 경로 | 요찬; 환경 준비 전 | 미정 |
| settings/WSGI 모듈, 지원 Python/Django/DB driver 버전 | 요찬; 설치 전 | 미정 |
| 의존성 파일과 설치 방법 | 요찬; 깨끗한 venv 구성 전 | 미정 |
| 환경변수 이름·필수 여부·공급 방식 | 요찬+민수; 실행 전 | 미정; 실제 settings와 일치시킬 것 |
| 개발 PostgreSQL 준비 방법·DB 생성 권한 | 민수; migration 전 | 미정; 로컬 개발용으로 한정 |
| migration, 개발 계정 준비, 시험 및 CI 명령 | 요찬; 앱 통합/CI 전 | 미정 |
| 템플릿/static 원본 경로와 연결 계약 | 푸른+요찬; 화면 연결 전 | 미정; 원본을 복사해 이중 관리하지 않음 |

## 실행 순서

앱 인계와 위 계약 확정 후에만 Django 실행 명령을 채운다. 현재 실행 가능한 앱 명령은 확인되지 않았다.

1. 확정한 Python으로 가상환경을 만든다.
2. 앱 담당자가 지정한 의존성 파일을 설치한다.
3. 운영 비밀값을 사용하지 않고 개발용 설정·인증정보를 공급해 개발 전용 PostgreSQL 연결을 확인한다. 실제 비밀값은 Git에 기록하지 않는다.
4. 인계된 migration을 새 개발 DB에 적용하고 가상 시험 계정을 준비한다.
5. 인계된 실행 명령으로 서버를 시작해 로그인·기록 저장·조회·인가 시험을 한다.
6. 앱 시험은 앱 인계 후 CI에 추가한다. 현재 CI는 아래 SG fixture CLI만 실행한다.

## 현재 실행 가능한 독립 CLI 시험

Windows 저장소 루트에서 `py -3.13 -B -m unittest discover -s 이민성/sg_audit -p test_network_audit.py -v`를 실행한다. 격리 설치 재현은 `.venv`의 Python 3.13으로도 완료했다. CI는 Python 3.13에서 동일한 테스트 모듈을 실행하며, 시험 0건도 실패 처리한다.

## 실제 실행 기록

앱·의존성·시험 명령 인계가 없어 앱 실행, migration, 앱 CI는 미확인이다. SG CLI 5개는 기본 Python 3.13 및 깨끗한 `.venv` Python 3.13.15에서 통과했고, `pip check`도 깨끗했다. GitHub CI는 [실행 42211003282](https://github.com/MinsooAhn02/Haven/actions/runs/42211003282)에서 성공했다. 로컬 고의 실패는 exit 1이었다. 별도 임시 디렉터리에 추적 CLI 소스만 내보내고 CI와 같은 runner를 적용해 5건 통과를 재현했으며, mock 0건은 exit 1·성공 fixture는 exit 0·고의 실패 fixture는 exit 1임을 확인했다. 이는 격리 재현이지 팀원/새 PC 재현은 아니다. 이는 SG CLI 범위만 증명한다.


## 차회 운영 준비 절차 (계획; 아직 실행하지 않음)

### 입력 먼저 받기

실제 OS/호스트 식별자·접속 경로·운영 Role·DB/data 경로·앱 commit와 settings/WSGI·migration 명령·중단 허용 시간·복구 대상이 확정되기 전에는 적용할 설치 명령이나 환경파일을 만들지 않는다. DB 연결 포트는 명세의 TCP 5432, Nginx ingress는 HTTP 80 기준이며 보안그룹 변경은 민성 담당이다. DB 인바운드는 Web SG만 허용하는 명세를 따르고 앱은 DB 전용 runtime 인증으로 연결한다.

### DB 역할과 배포/복귀 순서

1. 변경 전 승인된 대상, 현재 앱 commit/schema, 백업 시각, 중단 영향, 되돌릴 앱 버전과 복구 담당을 기록한다. 이 중 하나라도 미정이면 작업을 보류한다.
2. DB 담당 입력에 맞춰 앱 데이터베이스, migration 주체, runtime 주체를 분리한다. runtime에는 CRUD에 필요한 최소 테이블/sequence 권한만 주고 superuser·역할 생성·DDL은 주지 않는다. migration 뒤 runtime CRUD와 DDL 거부를 각각 확인한다.
3. 비root 실행 계정·venv·환경파일 접근 권한과 Nginx → loopback Gunicorn → Django 연결을 확인한다. systemd 실행 사용자·작업 경로·WSGI·자동 기동 및 static 원본 경로는 인계값과 맞춘다. 승인한 migration과 앱 commit을 기록하고 runtime 인증으로 전환한 뒤 서비스를 시작한다. health 응답만으로 완료하지 말고 로그인·생성·조회와 기존 데이터 유지도 확인한다. 승인된 점검 시간에 서비스/서버 재시작 후 자동 기동·SSM·데이터 영속성을 검증한다.
4. 실패하면 우선 트래픽/재시작을 멈추고 로그·현재 버전·오류를 보존한다. 호환되는 앱 버전과 이전 설정으로 복귀해 로그인·기존 데이터 조회를 확인한다. DB를 무조건 역 migration하거나 덮어쓰지 않는다. 데이터/schema 손상이 의심되면 별도 승인된 복원 계획으로 전환한다.

**합격:** 지정 Web에서 DB 연결 성공, 다른 출발지 차단 증거, runtime 인증 성공 및 DDL 거부, 앱 재시작 후 로그인·CRUD·기존 기록 유지, 실패 시 앱 설정 복귀 결과가 기록됨.

### 정합 백업과 격리 복원

1. 승인된 백업 위치·접근 주체·보존 기간·복원 전용 격리 대상·쓰기 중지 시간을 확정한다. 백업 생성 권한과 복원/삭제 권한은 분리해 확인한다.
2. 쓰기를 멈추고 업로드/삭제 작업 완료를 확인한 동일 시점에 PostgreSQL dump와 ACTIVE 첨부를 수집한다. manifest에는 `post_id, attachment_id, storage_key, size_bytes, sha256`와 백업 시각·앱 commit·schema 상태를 기록한다. 부분 실패면 묶음을 유효 백업으로 표시하지 않는다.
3. 운영과 분리된 DB와 비공개 파일 경로로 함께 복원한다. 스키마·행 수·샘플 조회, 각 파일 크기/hash, A/B/C 권한·공유 해제 후 거부를 확인한다. 운영 메일/API 호출을 차단한다.
4. 누락·고아 파일·hash mismatch·권한 오류가 하나라도 있으면 복원 실패로 남기고 원인을 정리한다. 운영으로 덮어쓰지 않는다. 실패한 격리 복원 환경은 증거를 보존하고 승인된 방식으로 폐기한다.

**합격:** 같은 시점의 DB/첨부/manifest 세트 복구, 구조·기록·hash·권한 검사 통과, 실제 조회 확인 및 격리 분리 증거. dump 파일 생성만으로 복원 성공이라 하지 않는다.

### 시험 메일

메일 제공자, 리전, 발신 도메인/주소, 수신 허가, 비용 및 네트워크 egress를 보람·민성과 먼저 확정한다. SES를 선택한다고 가정하지 않는다. 비운영 시험 설정으로 승인된 가상 수신처 하나에 최소 알림을 보낸다. API 성공, 메시지 식별자, 수신함 실제 도착을 각각 기록하고 실패 시 사용자에게 성공 표시가 없는지 확인한다. 반복 발송·실사용자 주소·운영 Secret은 시험에 쓰지 않는다.
