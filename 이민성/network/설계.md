# 이민성 네트워크 설계 (1회차)

상태: 설계 초안 · 실제 생성 전 · 리전/예산/출구는 김보람 확정 후 반영

## 1. VPC와 주소

| 항목 | 값 | 이유 |
|---|---|---|
| 리전 | `ap-northeast-2` 서울 (김보람 권장, 팀장 승인 대기) | 국내 접속·시연 환경 우선. 5.2 가격은 us-east-1 기준이며 서울 기준 NAT 비용은 5.2 하단에 추가 |
| VPC CIDR | `10.20.0.0/16` | 명세 후보값, 서브넷 확장 여유 |
| 중복 확인 | 내 PC: ipconfig 결과 `192.168.70.1`, `192.168.10.1`, `192.168.35.215` → 10.20.x 사용 없음 | 로컬/VPN과 겹치면 연결 시 충돌 |
| DNS hostnames / resolution | 둘 다 켬 | SSM·Endpoint가 DNS 이름을 사용 |

## 2. 서브넷

| 이름 | CIDR | AZ | 종류 | 들어갈 것 | 공인 IP 자동 할당 |
|---|---|---|---|---|---|
| public-a | `10.20.0.0/24` | AZ-a | 공개 | ALB (+ NAT를 고를 경우 NAT) | 끔 |
| public-b | `10.20.1.0/24` | AZ-b | 공개 | ALB | 끔 |
| private-web | `10.20.10.0/24` | AZ-a | 비공개 | Web EC2 1대 | 끔 |
| private-db | `10.20.20.0/24` | AZ-a | 비공개 | DB EC2 1대 | 끔 |

- ALB는 서로 다른 AZ 서브넷 2개가 필요해서 public-a/b를 둔다. (public-b는 ALB가 “AZ 2개 필수” 규칙을 맞추려고 존재. Web 서버는 1대뿐이라 AZ-a의 비공개 서브넷에만 존재)
- Web/DB는 각 1대이므로 고가용성(HA)이나 무중단을 약속하지 않는다.
- Web과 DB를 다른 서브넷으로 나눠 SG/라우팅 규칙을 구분하기 쉽게 한다.
- 공개 서브넷도 자동 공인 IP를 끈다. 공인 IP가 필요한 건 ALB와 NAT Gateway뿐이고, 둘 다 AWS가 따로 붙인다(NAT는 Elastic IP). 실수로 EC2를 공개 서브넷에 띄웠을 때 인터넷에 바로 노출되는 걸 막는 안전장치이기도 하고, 공인 IPv4는 요금도 나간다.

## 3. 라우팅 테이블

| 라우팅 테이블 | 연결 서브넷 | 목적지 | 대상 |
|---|---|---|---|
| rt-public | public-a, public-b | `10.20.0.0/16` | local |
|  |  | `0.0.0.0/0` | IGW |
| rt-private | private-web, private-db | `10.20.0.0/16` | local |
|  |  | `0.0.0.0/0` | NAT Gateway (public-a) (D6 확정 대기) |
|  |  | S3 prefix list | S3 Gateway Endpoint |

- 비공개 라우팅 테이블에는 IGW 경로를 넣지 않는다.
- Interface Endpoint는 라우팅 대상이 아니므로 이 표에 넣지 않는다 (명세 4.1).
- NAT Gateway를 공개 서브넷에 두는 이유: NAT 자신도 인터넷에 나가는 길이 있어야한다. 인터넷으로 나가는 길(0.0.0.0/0 → IGW)은 공개 라우팅 테이블에만 있다.

## 4. 보안 그룹(SG) 연결표

공통: 허용 목록 방식(나머지 거부), IPv4만 사용(IPv6 미사용), 22/3389 개방 없음, 관리 접속은 SSM으로만.

### 4.1 Inbound

| SG | 프로토콜/포트 | 출발지 | 이유 |
|---|---|---|---|
| sg-alb | TCP 443 | `0.0.0.0/0` | 사용자 HTTPS 접속 |
| sg-alb | TCP 80 | `0.0.0.0/0` | HTTPS redirect 전용 (ALB listener에서 443으로 전환) |
| sg-web | TCP 80 | sg-alb | ALB → Nginx만 허용 |
| sg-db | TCP 5432 | sg-web | Web → PostgreSQL만 허용 |

- sg-web 출발지를 sg-alb로 쓴 이유: 반드시 ALB를 거친 요청만 Web에 닿게 하기 위해 즉, ALB SG가 붙은 장비가 보낸 것만 받는다.
- PostgreSQL 포트 번호 5432/TCP
### 4.2 Outbound

| SG | 프로토콜/포트 | 목적지 | 이유 |
|---|---|---|---|
| sg-alb | TCP 80 | sg-web | 요청 전달·health check |
| sg-web | TCP 5432 | sg-db | DB 연결 |
| sg-web | TCP 443 | `0.0.0.0/0` | SSM, 패키지, AWS API, 메일 API |
| sg-db | TCP 443 | `0.0.0.0/0` | SSM, 패키지, 백업 |

- SG는 stateful이므로 응답 트래픽용 규칙은 따로 열지 않는다. (예: DB → Web 응답용 outbound 불필요)
- Amazon DNS, DHCP, 인스턴스 메타데이터, Time Sync 등은 SG가 필터링하지 않는다. 그래서 DNS용 outbound 53 규칙을 따로 열지 않는다. (근거: https://docs.aws.amazon.com/vpc/latest/userguide/VPC_SecurityGroups.html , 2026-11-06 확인)
- 메일은 SES API(443)를 기본으로 하고, SMTP(587)를 쓰게 되면 sg-web outbound에 TCP 587을 추가한다. OS 패키지 저장소가 HTTP(80)를 쓰는 OS를 고르면(안민수 결정) TCP 80도 추가한다.
- DB sg에 outbound 5432가 없는 이유: Web이 DB에 거는 것. DB가 누군가의 5432로 연결을 걸 일이 없음. Web이 보낸 쿼리에 대한 DB의 응답은 SG가 stateful이라 자동으로 나간다.. 그래서 응답용 규칙도 필요 없다.
- Web/DB outbound 443을 `0.0.0.0/0`으로 여는 이유: SSM·pypi·AWS API의 공인 IP가 바뀌어 SG에 IP로 고정할 수 없다. inbound는 계속 차단된다.
- outbound 0.0.0.0/0 443이 괜찮은가: 필요해서 허용하지만, 위험은 남음. 서버가 해킹당하면 공격자가 443으로 아무 서버에나 데이터를 보낼 수 있다. 기본 범위에서는 포트를 443으로 제한하고 로그로 감시하며, 도메인 기반 필터(DNS Firewall/Network Firewall/프록시)는 비용·관리 부담 때문에 심화 후보로 둔다.
- TLS는 ALB에서 종료한다. 사용자→ALB만 HTTPS(443)이고 ALB→Web은 VPC 내부 HTTP(80)이므로, 전 구간 TLS(종단 간 암호화)로 설명하지 않는다. 내부 구간 암호화는 심화 범위다.(인계완료 기준: ALB→Web은 기본 HTTP이며 HTTPS 접속을 전 구간 TLS로 설명하지 않음 내용)

### 4.3 반드시 거부돼야 하는 접근 (2회차 시험 대상)

| 시도 | 기대 결과 | 관련 시험 |
|---|---|---|
| 인터넷 → Web 80 직접 (ALB 우회) | 거부 (공인 IP 없음 + SG) | NET-02 |
| 인터넷 → DB 5432 | 거부 | NET-04 |
| ALB → DB 5432 | 거부 (sg-db는 sg-web만 허용) | NET-04 |
| 같은 VPC의 다른 서버 → DB 5432 | 거부 | NET-04 |
| 어디서든 22/3389 | 거부 (규칙 없음) | SG-01 |

- 공인 IP 없음을 적은 이유: 누가 실수로 SG에 0.0.0.0/0을 열어도, 공인 IP가 없으면 인터넷에서 닿을 수 없다. 반대로 공인 IP가 실수로 붙어도 SG가 막아준다(심층 방어)
- 네트워크 설계 기준의 최소 거부 목록이다. 레드팀(권혁민) 시험에서 추가 경로가 발견되면 이 표에 반영한다.

## 5. 비공개 서버 출구 설계

### 5.1 목적지별 출구

| 목적지 | 포트 | 사용 서버 | 출구 | Endpoint 종류 | IAM/정책 (담당) | 실제 연결 시험 (2회차) |
|---|---|---|---|---|---|---|
| SSM (ssm, ssmmessages, ec2messages) | TCP 443 | Web, DB | NAT | 없음 (NAT 채택 시) | EC2 Role에 SSM 권한 (김보람) | Fleet Manager Online, 세션 시작 (NET-05/06) |
| OS 패키지 저장소 | TCP 443 (OS에 따라 80) | Web, DB | NAT | 해당 없음 | — | 패키지 업데이트 명령 성공 |
| Python 패키지 (pypi.org) | TCP 443 | Web | NAT | 해당 없음 | — | pip 설치 성공 |
| 메일 (SES API 또는 SMTP) | TCP 443 또는 587 | Web | NAT | 선택: SES SMTP Interface Endpoint | 메일 발송 권한 (김보람) | 실제 수신 확인 (EXT-03) |
| 로그/AWS API (CloudWatch Logs 등) | TCP 443 | Web, DB | NAT | 없음 | 로그 권한 (김보람) | 로그 도착 확인 |
| S3 백업 | TCP 443 | DB | S3 Gateway Endpoint | Gateway | Endpoint 정책으로 백업 버킷만 허용 (김보람) | 지정 prefix 업로드 성공 |
| DNS | — | Web, DB | VPC 내부 (Amazon DNS) | 해당 없음 | — | 이름 조회 성공 |

### 5.2 출구 방식 비교 (us-east-1 기준, 2026-11-06 조사)

| 선택지 | 월(730h) | 10일(240h) | 인터넷 가능 | 관리 부담 | 비고 |
|---|---|---|---|---|---|
| A. NAT Gateway 1개 + 공인 IP | 약 $36.5 + 데이터 | 약 $12 + 데이터 | O | 낮음 | 시간당 $0.045 + GB당 $0.045, 공인 IPv4 시간당 $0.005 |
| B. NAT 인스턴스 t4g.nano + 공인 IP | 약 $6.7 + EBS | 약 $2.2 + EBS | O | 높음 | forwarding, src/dst check 해제, 재시작 복구 검증 필요 |
| C. SSM Interface Endpoint 3개 (1 AZ) | 약 $21.9 + 데이터 | 약 $7.2 + 데이터 | X | 중간 | pip/OS 패키지 불가 → 단독 사용 불가 |
| S3 Gateway Endpoint | $0 | $0 | S3만 | 낮음 | 백업 트래픽의 NAT 처리비 절감 |

- 추천: A (NAT Gateway 1개, public-a) + S3 Gateway Endpoint. 예산 제약 시 B.
- NAT를 Web/DB와 같은 AZ-a에 두어 AZ 간 전송 요금을 피한다.
- 리전이 us-east-1이 아니면 가격을 다시 확인한다.
- 미사용 기간에 NAT Gateway를 삭제하면 비용이 줄지만, 재생성 시 라우팅 재설정과 연결 재시험이 필요하다.
- NAT Gateway는 1시간 미만 사용도 1시간으로 청구되며, 처리 요금과 별도로 표준 데이터 전송 요금이 붙는다.
- NAT 인스턴스를 x86으로 해야 하면 t3.nano(시간당 $0.0052)를 대안으로 쓴다.
- 가격 출처 (2026-11-06, us-east-1 직접 확인):
  - NAT Gateway: https://aws.amazon.com/vpc/pricing/
  - Interface Endpoint: https://aws.amazon.com/privatelink/pricing/
  - EC2 온디맨드: https://aws.amazon.com/ec2/pricing/on-demand/
  - 서울(ap-northeast-2) 기준: NAT Gateway 시간당 $0.059 + 공인 IPv4 $0.005 = 약 $0.064/시간, 14일 약 $21.50 (데이터 처리·전송 별도). 크레딧 $120 기준으로 NAT는 구축·배포·시험 기간에만 유지한다(김보람 의견, 2026-11-06). 또한 현재 권장안이기 때문에 표를 수정하지 않는다.
  - 필수적으로 점검해야되는 내용(이민성 김보람에게 내용 설명 완료 2026-11-06)
  - NAT 삭제 시 SSM 관리 접속·패키지 설치·메일 발송이 함께 끊긴다. 따라서 NAT 유지 기간은 서버 구축·배포·시험 기간과 맞춘다.
  - NAT Gateway는 중지 기능이 없어 사용하지 않는 기간에는 삭제한다. 삭제해도 Elastic IP는 해제되지 않으며(별도 해제 필요), rt-private의 0.0.0.0/0 경로는 블랙홀 상태로 남는다. 재생성 시 새 NAT ID로 경로를 수정한다. (근거: https://aws.amazon.com/vpc/pricing/ , https://repost.aws/knowledge-center/vpc-delete-nat-gateway , 2026-11-06 확인)

## 6. 인계·확인 요청

| 대상 | 전달/요청 내용 |
|---|---|
| 김보람 (IAM) | Web/DB EC2 Role에 SSM 권한, 메일·로그 권한, S3 백업 Endpoint 정책 |
| 김보람 (계정·IAM·비용) | 리전 확정, D6 출구(A/B) 예산 승인, 생성 예정 자원: VPC 1, 서브넷 4, IGW 1, NAT Gateway 1(+EIP 1), 라우팅 테이블 2, SG 3, S3 Gateway Endpoint 1. 3회차 추가: ALB 1(공인 IPv4 2개, AZ당 1개) |
