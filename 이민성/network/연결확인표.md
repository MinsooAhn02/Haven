# SSM·Web→DB·필요 출구·직접 접근 거부 확인표

[설계.md](설계.md)의 네트워크·SG 설계가 실제로 동작하는지 확인하는 표다. 기대 결과는 설계와 [기본 명세](../../docs/구현명세/기본프로젝트_구현명세.md) NET-01~06에서 정했고, 실제 결과는 승인·구축 뒤 채운다.

- **상태**: 11/10 1차 실행 (구축 직후). 결과 표시 ✅ 통과 · 🔶 부분/참고 · ⚠️ 남은 위험 · ⏳ 미실시. 기대값은 11/09 작성. 실행은 AWS_운영결정 11번(사전 승인) 범위에서 하며, 되돌릴 수 없는 삭제만 민수 확인
- **실행 환경**: 서울 `ap-northeast-2`, 팀 계정(IAM 사용자, root 아님). AWS 조회는 민성 PC(Git Bash, aws-cli 2.39.6), 서버 안 시험은 민수 SSM 세션
- **대상**: web-1(private-web), db-1(private-db), t3.small, Ubuntu 24.04, Python 3.12.3(web-1, 민수 확인), AMI 11/10 16:36 조회. 인스턴스 ID·IP는 가림
- **ID 규칙**: `NET-`은 명세 ID, `SSM-`·`OUT-`·`RST-`는 이 표의 자체 번호
- **시험용 출발지**: 임시 EC2 t3.micro, 공인 IP 없음. sg-web·sg-alb가 아닌 시험용 SG(아웃바운드 허용)를 붙인다. 시험한 날 삭제하고 인스턴스 ID·생성/삭제 시각을 증거에 기록 (민수 승인 11/09). 출발지 쪽 SG에서 막히지 않아야 목적지 SG를 시험할 수 있다

## B. Web → DB

| ID | 출발지 → 목적지 | 방법 | 기대 결과 | 설계 근거 | 실제 | 증거 |
|---|---|---|---|---|---|---|
| NET-03 | web-1 → db-1:5432 | web-1에 SSM 접속 → `psql -h <db-1 IP> -p 5432 -U haven_app` | 접속 **성공** | 설계 4절 sg-db ← sg-web 5432 | 🔶 부분: TCP 5432 `Connection refused`(exit=1) → **SG 통과**. DB 미설치라 거절. `psql -U haven_app`은 DB 설치 후 | 11/10 민수 SSM 세션 (web-1) |
| NET-03-b | web-1 → db-1:5432 (거부 계정) | 같은 명령, `-U postgres` | TCP 연결은 되고 **DB가 거부** (pg_hba 거부 또는 인증 실패). timeout이면 SG 문제라 FAIL | 명세 NET-03, 민수 pg_hba 설정 | ⏳ 미실시: DB 설치 후 |  |
| NET-04 | 시험용 출발지 → db-1:5432 | `timeout 5 bash -c '</dev/tcp/<db-1 IP>/5432'` | **timeout** (Connection refused면 SG 통과 → FAIL) | 설계 4절 sg-db는 sg-web만 허용 | ⏳ 미실시: 시험용 EC2 필요 (삭제 권한 `ec2:TerminateInstances` 보람 요청 중) |  |
| NET-04-b | 시험용 출발지 → db-1:22 | 같은 명령, 포트 22 | **timeout** | 설계 4절 sg-db 인바운드는 5432만 | ⏳ 미실시: 같음 |  |
| NET-04-c | ALB → db-1 | ALB는 명령 실행 불가 → `describe-security-groups`로 sg-db 규칙 확인 | sg-alb 출처 규칙 **없음** (SG CLI SG-04 위반 없음) | 설계 4.3 ALB→DB 거부 | ✅ 통과: sg-db 인바운드 출처는 sg-web 하나, sg-alb 없음 | 11/10 16:39 민성, `describe-security-groups` |

## C. 필요 출구

| ID | 출발지 → 목적지 | 방법 | 기대 결과 | 설계 근거 | 실제 | 증거 |
|---|---|---|---|---|---|---|
| OUT-01 | web-1 → DNS | `getent hosts ssm.ap-northeast-2.amazonaws.com` | IP 주소 **반환** | 설계 4절 Amazon DNS는 SG로 막히지 않음 | ✅ 통과: IP 반환 | 11/10 민수 SSM 세션 (web-1) |
| OUT-02 | web-1 → SSM 엔드포인트:443 | `curl -sS -o /dev/null -w '%{http_code}' https://ssm.ap-northeast-2.amazonaws.com` | HTTP 응답 코드 **받음** (코드는 무관, timeout 아님) | 설계 5절 NAT 경유 443 | ✅ 통과: `400` 응답 (연결됨) | 11/10 민수 SSM 세션 (web-1) |
| OUT-03 | web-1 → Ubuntu apt 저장소:80 | `sudo apt update` | 저장소 목록 **받아옴**, 오류 없음 | 설계 4.2 sg-web 80, AWS_운영결정 5번 | ✅ 통과: `apt update` 정상 | 11/10 민수 SSM 세션 (web-1) |
| OUT-04 | db-1 → Ubuntu apt 저장소:80 | 같음 | **받아옴** | 설계 4.2 sg-db 80 | ✅ 통과: `apt update` 정상 | 11/10 민수 SSM 세션 (db-1) |
| OUT-05 | private 서브넷 → S3 | `aws ec2 describe-route-tables`로 rt-private 확인 | S3 prefix list(`pl-`) → `vpce-` 경로 **있음** | 설계 3절 S3 Gateway Endpoint | ⏳ 미실시 |  |
| OUT-06 | web-1 → 메일(SES API):443 | `curl -sS -o /dev/null -w '%{http_code}' https://email.ap-northeast-2.amazonaws.com` | HTTP 응답 코드 **받음** (timeout 아님). SES 계정 설정은 3회차 | 설계 4.2 sg-web 443, AWS_운영결정 6번 | ✅ 통과: `404` 응답 (연결됨) | 11/10 민수 SSM 세션 (web-1) |
| OUT-07 | db-1 → 인터넷:8080 (허용 안 한 포트) | `timeout 5 bash -c '</dev/tcp/<외부 IP>/8080'` | **timeout** | 설계 4.2 sg-db outbound는 80·443만 | ✅ 통과: `1.1.1.1:8080` timeout(exit=124), 막힘 | 11/10 민수 SSM 세션 (db-1) |
| OUT-08 | web-1 → 임의 외부 사이트:443 | `curl -sS -o /dev/null -w '%{http_code}' https://example.com` | **성공** — 막는 규칙이 없음. PASS가 아니라 **남은 위험**으로 기록 | 설계 4절 443 잔여 위험 | ⚠️ 남은 위험 확인: `200` (임의 443 사이트 접속 가능) | 11/10 민수 SSM 세션 (web-1) |
| OUT-09 | web-1 → pypi.org:443 | `curl -sS -o /dev/null -w '%{http_code}' https://pypi.org/simple/` | `200` **받음** | 설계 5.1 Python 패키지 | ✅ 통과: `200` | 11/10 민수 SSM 세션 (web-1) |
| OUT-10 | web-1, db-1 → CloudWatch Logs | 로그 설정 후 `aws logs describe-log-streams`로 확인 | 로그 **도착** | 설계 5.1 로그/AWS API (권한 김보람) | ⏳ 미실시: 로그 설정 후 |  |
| OUT-11 | db-1 → S3 백업 버킷 (Gateway) | 지정 prefix에 시험 파일 업로드, 다른 prefix에도 시도 | 지정 prefix **성공**, 다른 버킷·prefix는 **AccessDenied** | 설계 5.1 S3 백업, Endpoint 정책 (김보람) | ⏳ 미실시: 백업 설정 후 |  |
| OUT-12 | web-1, db-1 apt 저장소 주소 | `grep URIs /etc/apt/sources.list.d/ubuntu.sources` | `http://` 주소 (80 포트 사용 확인) | AWS_운영결정 5번 | 🔶 주소 확인: `ap-northeast-2.ec2.archive.ubuntu.com`, `security.ubuntu.com` (web-1·db-1 같음). `http://` 표기는 원문 캡처로 재확인 | 11/10 민수 SSM 세션 (web-1, db-1) |

## D. 직접 접근 거부

| ID | 출발지 → 목적지 | 방법 | 기대 결과 | 설계 근거 | 실제 | 증거 |
|---|---|---|---|---|---|---|
| NET-01 | 인터넷 → 도메인(ALB):443 | `curl -I https://<도메인>` | 정상 응답, 인증서 **유효** | 명세 NET-01, 설계 4절 sg-alb 443 | ⏳ 3회차 (ALB·도메인) |  |
| NET-01-b | 인터넷 → ALB:80 | `curl -I http://<도메인>` | `301` 응답, `Location: https://...`로 **전환** | 설계 4절 sg-alb 80 = HTTPS redirect 전용 | ⏳ 3회차 |  |
| NET-02-a | web-1, db-1 공인 IP | `aws ec2 describe-instances` (PublicIpAddress) | 값 **없음** | 설계 2절 공인 IP 자동 할당 끔 | ✅ 통과: web-1·db-1 PublicIp `None` | 11/10 16:40 민성, `describe-instances` |
| NET-02-b | private 라우팅 | `aws ec2 describe-route-tables` (rt-private) | `0.0.0.0/0 → nat-`, `igw-` 경로 **없음** | 설계 3절 | ✅ 통과: rt-private `0.0.0.0/0 → nat-` active (GatewayId 없음 = igw 아님) | 11/10 16:38 민성, `describe-route-tables` |
| NET-02-c | sg-web 인바운드 | `aws ec2 describe-security-groups` | 80 ← sg-alb **만**, `0.0.0.0/0` 없음 (SG CLI SG-03 위반 없음) | 설계 4절 | ✅ 통과: sg-web 인바운드 80 ← sg-alb 하나 | 11/10 16:39 민성, `describe-security-groups` |
| NET-02-d | 시험용 출발지 → web-1:80 | `timeout 5 bash -c '</dev/tcp/<web-1 IP>/80'` | **timeout** (ALB 우회 불가) | 설계 4절 sg-web은 sg-alb만 허용 | ⏳ 미실시: 시험용 EC2 필요. **보조 시험**: db-1 → web-1:80 timeout(exit=124), 막힘 (출발지 db-1은 80 outbound 허용이라 목적지 sg-web에서 막힌 것) | 11/10 민수 SSM 세션 (db-1) |

## E. 재시작·장애 상황

| ID | 상황 | 방법 | 기대 결과 | 설계 근거 | 실제 | 증거 |
|---|---|---|---|---|---|---|
| NET-06 | web-1 재부팅 후 | 재부팅 → SSM-01·SSM-02·OUT-03 다시 실행 | SSM **Online 복구**, 세션·업데이트 **성공** | 명세 NET-06 | ⏳ 미실시: 앱 배포 전 실행 예정 |  |
| NET-06-b | db-1 재부팅 후 | 재부팅 → SSM-03·OUT-04·NET-03 다시 실행 | SSM **복구**, Web→DB **재접속 성공** | 명세 NET-06 | ⏳ 미실시: 같음 |  |
| RST-01 | NAT Gateway가 없을 때 (비용 때문에 삭제한 기간) | 삭제 기간에 SSM-01·OUT-03·OUT-05 확인 | SSM **Offline**·업데이트 **실패**, S3 경로는 **유지** | 설계 5.2 NAT 삭제·blackhole | ⏳ 미실시: NAT 삭제 기간에 확인되는 대로 |  |
| RST-02 | 아침 `nat-up` 직후 (매일) | `describe-route-tables`(rt-private) + SSM-01 | `0.0.0.0/0 → 새 nat-` (blackhole 아님), web-1·db-1 **Online** | 설계 5.2, 민수 11/09 요청 | ✅ 통과: `nat-up.sh` 확인 줄 `0.0.0.0/0 → nat-… active` (blackhole → 새 NAT 교체), 이후 SSM-01 Online | 11/10 16:33 민성, nat-up 로그 + 16:41 SSM-01 |
| RST-03 | 밤 `nat-down` 직후 (매일) | `describe-nat-gateways` + `describe-addresses`(태그 Project=Haven) | NAT 상태 `deleted`, 태그된 EIP **없음**(해제됨) | 설계 5.2 EIP 별도 해제 | ⏳ 21시 `night.sh` 첫 실행 때 |  |

RST-01은 시험하려고 NAT를 일부러 지우지 않는다. 비용 계획대로 삭제한 기간에 확인되는 대로 기록한다.
NET-06 재부팅 시험은 구축 직후, 앱 배포 전에 실행한다 (민수 승인 11/09). 배포 후 다시 할 때는 Discord에 먼저 알린다.
