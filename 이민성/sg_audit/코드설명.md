# network_audit.py 코드 설명

[README](README.md)의 실행 방법·시험 결과와 함께 본다. 이 문서는 코드가 **어떤 순서로, 어떻게 판정하는지**를 설명한다.

## 1. 전체 흐름

```
main()                 명령어를 읽는다 (fixture? --baseline? --output-dir?)
  └ run_fixture()
      ├ load_json()          baseline.json, fixture 파일을 읽는다
      ├ prepare_output_dir() 출력 폴더가 비었는지 확인한다 (덮어쓰기 금지)
      ├ audit()              ★ 채점한다
      │   ├ flatten_rules()      AWS 모양 규칙을 한 줄씩 펼친다
      │   ├ same_rule()          baseline 규칙과 똑같은지 비교한다
      │   └ classify_violation() 틀렸으면 얼마나 심각한지(check_id) 정한다
      ├ overall_verdict()    전체 판정을 정한다 (ERROR > UNKNOWN > FAIL > PASS)
      ├ write_results()      results.json, findings.csv를 저장한다
      └ return 종료 코드      0=PASS, 1=FAIL, 2=ERROR, 3=UNKNOWN
```

## 2. 함수별 역할

| 함수 | 하는 일 | 관련 명세 |
|---|---|---|
| `load_json` | JSON 파일을 읽는다. 파일이 없거나 문법이 틀리면 ERROR로 멈춘다 | AUD-08 |
| `flatten_rules` | SG의 `IpPermissions`(들어옴), `IpPermissionsEgress`(나감)를 "방향·프로토콜·포트·출발지" 한 줄짜리 규칙으로 펼친다. IPv4, IPv6, SG 참조, prefix list를 구분한다 | 5.1 |
| `same_rule` | 실제 규칙과 허용 규칙의 방향·프로토콜·시작/끝 포트·출발지 종류·출발지 값 6개가 모두 같은지 비교한다 | SG-05 |
| `classify_violation` | 허용표에 없는 규칙의 심각도를 SG-01 → 02 → 03 → 04 → 05 순서로 확인해 처음 걸리는 하나로 정한다 | SG-01~05 |
| `audit` | 자산(서버)마다 역할을 찾고, 붙은 모든 SG 규칙의 합집합을 baseline과 비교해 finding 목록을 만든다 | 5.1, 5.2 |
| `overall_verdict` | finding 전체에서 가장 심각한 판정 하나를 고른다. 결과가 하나도 없으면 PASS가 아니라 UNKNOWN | 5.2 |
| `prepare_output_dir` | 출력 폴더가 이미 차 있으면 덮어쓰지 않고 멈춘다 | 5.1 |
| `write_results` | `results.json`(전체)과 `findings.csv`(표)를 저장한다 | 5.2 |

## 3. audit()이 자산 하나를 채점하는 순서

1. **baseline에 없는 자산이면** 채점하지 않고 UNKNOWN(SG-06)을 붙인다.
2. **기대 SG가 안 붙어 있으면** FAIL(SG-05).
3. 자산에 붙은 **모든 SG의 규칙을 합친다**(합집합). SG 정보를 못 찾으면 UNKNOWN(SG-06).
4. 실제 규칙을 하나씩 baseline과 비교한다. SG 참조(`sg-fixture-web`)는 역할 이름(`web`)으로 바꾼 뒤 비교한다. baseline을 SG ID가 아닌 역할 이름으로 쓴 이유가 이것이다.
   - 일치하면 PASS
   - 없으면 `classify_violation`으로 FAIL의 종류를 정한다
5. **baseline에는 있는데 실제로 없는 규칙**은 FAIL(SG-05). 보안 위반은 아니지만 서비스가 연결되지 않는다.
6. 마지막으로 **어느 자산에도 연결되지 않은 SG**는 UNKNOWN(SG-06).

fixture에 `errors`가 있으면 `audit()`을 아예 실행하지 않고 ERROR로 끝낸다. 반쯤 읽은 데이터로 PASS를 내지 않기 위해서다.

## 4. 예시: fail_public_db가 FAIL이 되는 과정

**① 역할 찾기**: `attachments`의 `db-1` → baseline `assets`에서 역할 `db`.

**② 규칙 펼치기**
```
ingress tcp 5432-5432  sg:sg-fixture-web
ingress tcp 5432-5432  cidr:0.0.0.0/0      ← 추가한 위험 규칙
egress  tcp 443-443    cidr:0.0.0.0/0
```

**③ SG 참조를 역할로**: `sg:sg-fixture-web` → `sg_role:web`

**④ baseline과 비교**

| 실제 규칙 | baseline에 있나 | 결과 |
|---|---|---|
| ingress 5432 `sg_role:web` | 있음 | PASS |
| ingress 5432 `cidr:0.0.0.0/0` | 없음 | 위반 → ⑤ |
| egress 443 `cidr:0.0.0.0/0` | 있음 | PASS |

`same_rule`로 보면:
```
실제:  ingress  tcp  5432  5432  cidr     0.0.0.0/0
허용:  ingress  tcp  5432  5432  sg_role  web
        같음    같음  같음   같음  다름      다름     → 다름(False)
```

**⑤ 심각도**: 들어오는 규칙 + 출발지가 인터넷 전체 + 5432 포함 → **SG-01**

**⑥ 전체 판정**: PASS 8 + FAIL 1 → 가장 심각한 FAIL → **종료 코드 1**

## 5. 입력 파일과 출력 파일

| 종류 | 파일 | 만드는 쪽 | 실행마다 바뀌나 |
|---|---|---|---|
| 입력 | `baseline.json`, `fixtures/*.json` | 사람이 직접 작성 | 바뀌지 않음 |
| 출력 | `out/.../results.json`, `findings.csv` | 프로그램이 자동 생성 | `run_id`와 시각은 바뀜 |

- `run_id`는 `uuid.uuid4()`로 실행마다 새로 만드는 고유 번호다. 영수증 번호처럼 "이번 실행"을 가리키며, 명세의 `evidence/<run-id>/` 증거 정리에 쓴다.
- 같은 입력이면 **판정 내용(findings)과 종료 코드는 항상 같다.** 그래서 `out/`은 Git에 올리지 않고(`.gitignore`), 판정 결과는 README·TODO에 요약한다.

## 6. 아직 구현하지 않은 것
