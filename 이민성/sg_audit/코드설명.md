# network_audit.py 코드 설명

[README](README.md)의 실행 방법·시험 결과와 함께 본다. 이 문서는 코드가 **어떤 순서로, 어떻게 판정하는지**를 설명한다.

## 1. 전체 흐름

```
main()                 명령어를 읽는다 (fixture? --baseline? --output-dir?)
  └ run_fixture()
      ├ load_json()          baseline.json, fixture 파일을 읽는다
      ├ validate_inputs()    입력 구조(목록·필수 칸)가 맞는지 확인한다 (틀리면 ERROR)
      ├ prepare_output_dir() 출력 폴더가 비었는지 확인한다 (덮어쓰기 금지)
      ├ audit()              ★ 채점한다
      │   ├ flatten_rules()      AWS 모양 규칙을 한 줄씩 펼친다
      │   ├ same_rule()          baseline 규칙과 똑같은지 비교한다
      │   └ classify_violation() 틀렸으면 얼마나 심각한지(check_id) 정한다
      ├ overall_verdict()    전체 판정을 정한다 (ERROR > UNKNOWN > FAIL > PASS)
      ├ write_results()      results.json, findings.csv를 저장한다
      └ return 종료 코드      0=PASS, 1=FAIL, 2=ERROR, 3=UNKNOWN
```

## 2. 함수별 역할

| 함수 | 하는 일 | 관련 명세 |
|---|---|---|
| `load_json` | JSON 파일을 읽는다. 파일이 없거나, 문법이 틀리거나, 읽기에 실패하면 ERROR로 멈춘다 | AUD-08 |
| `validate_inputs` | 채점 전에 baseline·fixture의 목록·필수 칸 형식을 확인한다. 틀리면 파이썬 오류로 튕기지 않고 ERROR(2)로 멈춘다 | AUD-05, AUD-08 |
| `flatten_rules` | SG의 `IpPermissions`(들어옴), `IpPermissionsEgress`(나감)를 "방향·프로토콜·포트·출발지" 한 줄짜리 규칙으로 펼친다. IPv4·IPv6 주소, SG 참조, prefix list를 모두 읽는다 | 5.1 |
| `same_rule` | 실제 규칙과 허용 규칙의 방향·프로토콜·시작/끝 포트·출발지 종류·출발지 값 6개가 모두 같은지 비교한다 | SG-05 |
| `classify_violation` | 허용표에 없는 규칙의 심각도를 SG-01 → 02 → 03 → 04 → 05 순서로 확인해 처음 걸리는 하나로 정한다 | SG-01~05 |
| `audit` | 자산(서버)마다 역할을 찾고, 붙은 모든 SG 규칙의 합집합을 baseline과 비교해 finding 목록을 만든다. baseline 자산이 수집 결과에 없으면 UNKNOWN을 남긴다. fixture에 errors가 있어도 읽은 부분은 채점한다 | 5.1, 5.2 |
| `overall_verdict` | finding 전체에서 가장 심각한 판정 하나를 고른다. 결과가 하나도 없으면 PASS가 아니라 UNKNOWN | 5.2 |
| `prepare_output_dir` | 출력 폴더가 이미 차 있으면 덮어쓰지 않고 멈춘다 | 5.1 |
| `write_results` | `results.json`(전체)과 `findings.csv`(표)를 저장한다 | 5.2 |

## 3. audit()이 자산 하나를 채점하는 순서

1. **baseline에 없는 자산이면** 채점하지 않고 UNKNOWN(SG-06)을 붙인다.
2. **기대 SG가 안 붙어 있으면** FAIL(SG-05).
3. 자산에 붙은 **모든 SG의 규칙을 합친다**(합집합). SG 정보를 못 찾으면 UNKNOWN(SG-06).
4. 실제 규칙을 하나씩 baseline과 비교한다. SG 참조(`sg-fixture-web`)는 역할 이름(`web`)으로 바꾼 뒤 비교한다. baseline을 SG ID가 아닌 역할 이름으로 쓴 이유가 이것이다.
    - 일치하면 PASS
    - 참조한 SG의 역할을 모르면 UNKNOWN(SG-06)
    - 없으면 `classify_violation`으로 FAIL의 종류를 정한다
5. **baseline에는 있는데 실제로 없는 규칙**은 FAIL(SG-05). 보안 위반은 아니지만 서비스가 연결되지 않는다.
6. 마지막으로 **baseline에 있지만 수집에서 빠진 자산**과 **어느 자산에도 연결되지 않은 SG**는 UNKNOWN(SG-06).

fixture에 `errors`가 있으면 수집된 개별 finding을 보존하고 전체 판정은 ERROR로 끝낸다. 부분 수집 결과를 전체 PASS로 표시하지 않는다.

## 4. 예시: fail_public_db가 FAIL이 되는 과정

**① 역할 찾기**: `attachments`의 `db-1` → baseline `assets`에서 역할 `db`.

**② 규칙 펼치기**
```
ingress tcp 5432-5432  sg:sg-fixture-web
ingress tcp 5432-5432  cidr:0.0.0.0/0      ← 추가한 위험 규칙
egress  tcp 443-443    cidr:0.0.0.0/0
egress  tcp 80-80      cidr:0.0.0.0/0      ← apt 저장소(11/13 baseline 반영)
```

**③ SG 참조를 역할로**: `sg:sg-fixture-web` → `sg_role:web`

**④ baseline과 비교**

| 실제 규칙 | baseline에 있나 | 결과 |
|---|---|---|
| ingress 5432 `sg_role:web` | 있음 | PASS |
| ingress 5432 `cidr:0.0.0.0/0` | 없음 | 위반 → ⑤ |
| egress 443 `cidr:0.0.0.0/0` | 있음 | PASS |
| egress 80 `cidr:0.0.0.0/0` | 있음 | PASS |

`same_rule`로 보면:
```
실제:  ingress  tcp  5432  5432  cidr     0.0.0.0/0
허용:  ingress  tcp  5432  5432  sg_role  web
        같음    같음  같음   같음  다름      다름     → 다름(False)
```

**⑤ 심각도**: 들어오는 규칙 + 출발지가 인터넷 전체 + 5432 포함 → **SG-01**

**⑥ 전체 판정**: PASS 10 + FAIL 1 → 가장 심각한 FAIL → **종료 코드 1** (11/13 baseline 갱신 전에는 PASS 8)

## 5. 입력 파일과 출력 파일

| 종류 | 파일 | 만드는 쪽 | 실행마다 바뀌나 |
|---|---|---|---|
| 입력 | `baseline.json`, `fixtures/*.json` | 사람이 직접 작성 | 바뀌지 않음 |
| 출력 | `out/.../results.json`, `findings.csv` | 프로그램이 자동 생성 | `run_id`와 시각은 바뀜 |

- `run_id`는 `uuid.uuid4()`로 실행마다 새로 만드는 고유 번호다. 영수증 번호처럼 "이번 실행"을 가리키며 `results.json`에 기록된다.
- 1회차 fixture 결과는 같은 입력이면 판정 내용(findings)과 종료 코드가 항상 같고 명령 한 줄로 다시 만들 수 있으므로, `out/`은 Git에 올리지 않고(`.gitignore`) 판정 결과만 README·TODO에 요약한다.
- 실제 AWS를 점검하는 3회차부터는 그 시점의 설정을 다시 만들 수 없으므로, 명세 9장에 따라 결과를 `evidence/<run-id>/`에 가림 처리해 증거로 남긴다. 현재 코드는 `--output-dir`로 지정한 폴더에 저장하며, 증거 폴더 정리는 3회차에 추가한다.

## 6. live 모드 (11/13 구현)

live는 수집만 새로 하고, 판정(`audit`)·저장(`write_results`)은 fixture와 같은 코드를 쓴다.

| 함수 | 하는 일 |
|---|---|
| `call_paged` | Describe* API를 마지막 페이지(`NextToken`)까지 부른다. 요청 제한(Throttling 등)이면 3번까지 다시 시도하고, 그래도 안 되면 오류 코드만 남긴다 |
| `collect_live` | ① `Project=Haven` VPC 1개 → ② 그 VPC의 SG 전부 → ③ `Name` 태그로 web-1·db-1(종료된 것 제외) → ④ `ELB app/haven-alb/*` ENI로 ALB SG. 결과를 fixture와 같은 모양으로 만든다. 실패한 단계는 `errors`에 남기고 읽은 것은 보존한다 |
| `check_default_sg` | SG-07: default SG에 규칙이 있으면 규칙마다 FAIL, 없으면 PASS 1개 |
| `mask_account` | 계정 번호를 앞 4자리만 남기고 가린다 |
| `run_live` | 출력 폴더 확인(AWS 읽기 전) → 클라이언트 생성(boto3 없으면 ERROR) → 수집 → 판정 → 저장 |

- baseline의 `expected_sg_names`로 실제 SG ID를 찾는다. 같은 이름이 2개면 ERROR, 이름이 없으면 `missing:<이름>`으로 두어 "기대 SG 미연결" FAIL이 된다.
- 예상 못 한 응답 모양이나 자격 증명 문제도 Traceback 없이 ERROR(2)로 끝난다.

## 7. 아직 구현하지 않은 것

- 추가 fixture: 범위 포트(AUD-03), IPv6(AUD-04), 전체 프로토콜·누락 포트(AUD-05), UDP/ICMP(AUD-06), 여러 API 페이지(AUD-07), 정상 SG+추가 공개 SG 합집합(AUD-11)
- 실제 점검 결과의 `evidence/<run-id>/` 증거 정리(manifest, 가림 처리) (3회차)
